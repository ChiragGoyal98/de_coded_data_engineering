Azure Data Factory orchestration patterns

Data orchestration is the process of coordinating and managing complex data workflows to ensure tasks happen in the correct order. In Azure Data Factory (ADF), this means moving beyond simple data copies and creating intelligent pipelines that can handle dependencies, loops, and conditional logic. Think of orchestration as the "brain" of your data movement, deciding when a task should start, what should happen if it fails, and how to process multiple datasets at once.

Why Orchestration Matters

When you first start with data engineering, you might be tempted to run scripts manually. However, as your data environment grows, manual triggers become impossible to manage. Orchestration provides several critical benefits:

  • Efficiency: By running tasks in parallel, you can significantly reduce the total time it takes for a data load to complete.
  • Resilience: Built-in error handling allows pipelines to retry a task or follow an alternative path if a specific service is down.
  • Dependency Management: It ensures that "Step B" only starts after "Step A" has successfully completed, preventing data corruption or incomplete reports.
  • Scalability: Using patterns like looping allows you to process hundreds of files using a single pipeline logic instead of creating a hundred separate pipelines.

Step-by-step Walkthrough of Core Patterns

Understanding orchestration in ADF starts with mastering four fundamental patterns. Here is how to implement them.

1. The Sequential Pattern

This is the most basic pattern where activities run one after another. You create this by dragging a "green connector" (Success) from one activity to the next.

  • Drag a Copy Data activity onto the canvas.
  • Drag a Stored Procedure activity onto the canvas.
  • Connect the output of the Copy activity to the Stored Procedure. The Stored Procedure will now only run if the data copy succeeds.

2. The Parallel Pattern

If two tasks do not depend on each other, they should run at the same time to save time.

  • Place two Copy Data activities on the canvas.
  • Do not connect them to each other.
  • Connect both to a single Trigger. When the pipeline starts, ADF will kick off both activities simultaneously.

3. The Iterative Pattern (ForEach)

This pattern is used when you have a list of items (like 50 SQL tables) and want to perform the same action on all of them.

  • Use a Lookup activity to get a list of table names.
  • Add a ForEach activity to the canvas.
  • Inside the ForEach activity, place a Copy Data activity.
  • ADF will loop through the list from the Lookup activity and run the Copy activity for every item in that list.

4. The Conditional Pattern (If-Condition)

This allows your pipeline to branch based on a specific logic, such as checking if a file is "Large" or "Small."

  • Add an If Condition activity.
  • In the "Expression" box, write your logic (e.g., checking a variable value).
  • Inside the "True" path, add the activities you want to run if the condition is met.
  • Inside the "False" path, add the activities for the alternative scenario.

Code Example: Defining Dependencies

In the underlying JSON of an ADF pipeline, orchestration is defined by the dependsOn property. Here is a snippet showing a "CleanUp" activity that only runs after "CopyData" is finished:


{
    "name": "CleanUpActivity",
    "type": "Delete",
    "dependsOn": [
        {
            "activity": "CopyDataActivity",
            "dependencyConditions": ["Succeeded"]
        }
    ]
}

Common Mistakes

  • Ignoring the "On Failure" Path: Many beginners only use the green "Success" connector. If an activity fails, the pipeline simply stops. Always consider adding a red "Failure" path to send an email notification or log the error.
  • Over-nesting: Avoid putting a ForEach inside another ForEach if possible. This makes pipelines hard to debug and can hit performance limits.
  • Hardcoding Values: Avoid typing specific file names or folder paths directly into activities. Use Parameters and Variables to make your orchestration patterns reusable across different environments (Dev, Test, Prod).

Practice Task

To put these patterns into practice, try building the following scenario in your ADF environment:

The "Validation and Load" Pipeline:

  • Use a Get Metadata activity to check if a specific CSV file exists in your storage account.
  • Use an If Condition activity to check the output of the Get Metadata activity.
  • If the file exists (True), run a Copy Data activity to move it to a SQL Database.
  • If the file does not exist (False), use a Web Activity or Fail Activity to send a custom message indicating the file was missing.
