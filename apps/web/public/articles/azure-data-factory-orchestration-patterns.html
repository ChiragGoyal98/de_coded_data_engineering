Azure Data Factory orchestration patterns

Azure Data Factory is a cloud-based data integration service that allows you to create data-driven workflows for orchestrating and automating data movement and data transformation. Orchestration is essentially the glue that binds individual activities together to form a cohesive, automated pipeline. By understanding common orchestration patterns, you can design workflows that are not only efficient but also resilient to failures and easy to scale as your data needs grow.

Why it matters

Orchestration patterns are important because they prevent your data pipelines from becoming a tangled mess of "spaghetti code." Without a clear pattern, troubleshooting a failed process becomes a nightmare, especially when dealing with hundreds of tables or complex dependencies.

  • Efficiency: Parallel execution patterns ensure you aren't waiting for one task to finish if others can run simultaneously, saving both time and money.
  • Resilience: Error-handling patterns (like Retries or "On Failure" paths) ensure your system can recover gracefully from temporary network glitches.
  • Scalability: Iterative patterns allow you to use a single pipeline to process multiple files or tables dynamically, rather than creating a separate pipeline for every single data source.

Step-by-step walkthrough

Building a robust orchestration flow involves choosing the right sequence and logic for your activities. Here is how to approach the most common patterns.

1. Sequential Chaining

This is the most basic pattern where activities run one after another. You use the green "Success" connector to link them.

  • Drag two activities (e.g., a Copy activity and a Notebook activity) onto the canvas.
  • Click the small green square on the side of the first activity and drag the arrow to the second.
  • The second activity will only start if the first one finishes successfully.

2. Parallel Execution

If two tasks are independent-such as loading "Customer" data and "Product" data-they should run at the same time.

  • Place multiple activities on the canvas.
  • Do not connect them to each other.
  • Connect them both to a single trigger or a preceding "parent" activity. ADF will start them simultaneously, respecting the maximum concurrent activity limit of your Integration Runtime.

3. Iterative Processing (ForEach)

When you have a list of files in a folder and need to process each one, don't create ten Copy activities. Use the ForEach container.

  • Use a Get Metadata activity to retrieve a list of child items (files).
  • Pass that list into a ForEach activity.
  • Inside the ForEach activity, define the logic (like a Copy activity) that should run for every item in that list.

4. Conditional Branching (If Condition)

Sometimes you only want to run a process if a certain condition is met (e.g., if it is the first day of the month).

  • Use an If Condition activity.
  • Under the "Activities" tab, define what happens in the "True" case and the "False" case.
  • This keeps your pipeline logic clean and prevents unnecessary compute costs.

Common mistakes

  • Hardcoding values: Beginners often hardcode file names or folder paths. This makes the pipeline rigid. Always try to use Parameters and Variables to make your orchestration dynamic.
  • Ignoring "On Failure" paths: Most people only plan for success. If your pipeline doesn't have a path for failure (like sending an email or logging the error to a table), you won't know something went wrong until a user complains.
  • Overloading a single pipeline: Putting 50 activities in one pipeline makes it hard to read and manage. Use the Execute Pipeline activity to break your project into smaller, reusable child pipelines.
  • Forgetting about Timeouts: By default, activities have a very long timeout period (7 days). If a process hangs, it can rack up costs. Always set a sensible timeout for your activities.

One practice task

To practice these concepts, try building a "Failure Notification" pattern. Create a pipeline with a Copy activity that is intentionally pointed to a file that doesn't exist. Link it to a Web activity (or a simple Script activity) using the red "On Failure" connector. Configure the second activity to log a message saying "The data load failed." This will teach you how to control the flow of execution based on the outcome of previous steps.
