Azure Data Factory orchestration patterns

Orchestration is the process of coordinating and managing complex data workflows to ensure they run in the correct order, at the right time, and under the specific conditions you define. In Azure Data Factory (ADF), orchestration acts as the conductor of an orchestra, directing individual data movements and transformations so they work together as a cohesive system rather than isolated tasks.

Why it matters

In real-world data engineering, tasks rarely exist in a vacuum. You might need to wait for a file to arrive in a data lake before processing it, or you might need to ensure that a dimension table is updated before a fact table starts loading. Without proper orchestration patterns, data pipelines become brittle, difficult to troubleshoot, and prone to data integrity issues.

Mastering these patterns allows you to:

  • Control the flow of data based on success or failure of previous steps.
  • Run multiple tasks simultaneously to save time.
  • Implement reusable logic that scales as your data environment grows.
  • Reduce manual intervention by automating complex dependencies.

Step-by-step walkthrough

To build effective pipelines, you need to understand the four primary orchestration patterns used in ADF.

1. Sequential Execution

This is the simplest pattern where activities run one after another. You create a dependency by dragging a green "Success" connector from one activity to the next. This ensures that Task B only starts if Task A completes successfully.

2. Parallel Execution

If two tasks do not depend on each other, you should run them in parallel to reduce the overall execution time. In the ADF authoring canvas, simply place two activities without connecting them to each other. They will both start as soon as the pipeline is triggered.

3. Conditional Logic

Sometimes you only want an activity to run if a certain condition is met. The If Condition activity allows you to evaluate an expression (like checking if today is Monday) and provides two branches: True and False. Each branch can contain its own set of activities.

4. Iteration and Looping

When you need to perform the same action on a list of items-such as copying 50 different SQL tables-you use the ForEach activity. This avoids the need to manually create 50 separate copy activities. Inside the ForEach container, you define a single "template" activity that runs for every item in your list.

Here is a simple JSON representation of an "If Condition" activity that checks if a parameter named IsGoldLayer is set to true:


{
    "name": "CheckLayer",
    "type": "IfCondition",
    "typeProperties": {
        "expression": {
            "value": "@equals(pipeline().parameters.IsGoldLayer, true)",
            "type": "Expression"
        },
        "ifTrueActivities": [
            { "name": "ProcessGoldData", "type": "Copy" }
        ]
    }
}

Common mistakes

  • Ignoring Error Paths: Most beginners only use the green "Success" paths. If an activity fails, the pipeline simply stops. Always consider using the red "Failure" path to send an email notification or log the error to a database.
  • Over-nesting Pipelines: While you can call a pipeline from another pipeline (Execute Pipeline activity), nesting them too many levels deep makes debugging extremely difficult. Try to keep your hierarchy flat.
  • Hardcoding Values: Beginners often hardcode folder paths or table names. Use parameters and variables instead to make your orchestration patterns reusable across different environments (Dev, Test, Prod).
  • Default Timeouts: ADF activities often have a default timeout of 7 days. If a process gets stuck, it can waste resources. Always set a realistic timeout (e.g., 2 hours) for your activities.

One practice task

To practice these concepts, try building a "Validation Pipeline" in your ADF environment. Create a pipeline that uses a Get Metadata activity to check if a specific CSV file exists in your Azure Blob Storage. Connect this to an If Condition activity. If the file exists (True branch), trigger a Copy Activity to move it to a different folder. If the file does not exist (False branch), use a Wait Activity to simulate a delay before the pipeline ends.
