Azure Data Factory orchestration patterns

Orchestration is the heart of any data engineering workflow. In Azure Data Factory, it refers to the management of multiple data activities to ensure they run in the correct order, handle errors gracefully, and react to specific conditions. Think of it as the brain that coordinates how data moves from source to destination, whether you are dealing with a simple file transfer or a complex multi-stage transformation process. By mastering orchestration patterns, you move beyond simple one-off tasks and start building resilient, automated data systems.

Why it matters

Building a single data copy activity is easy, but real-world data environments are messy. Orchestration patterns help you manage this complexity by providing:

  • Reliability: Ensuring that if one part of your process fails, the entire system doesn't collapse or produce "dirty" data.
  • Efficiency: Allowing you to run independent tasks simultaneously (parallelism) to save time and reduce compute costs.
  • Modular Design: Breaking large, complex processes into smaller, reusable components that are easier to debug and maintain.
  • Flexibility: Using logic to decide whether to run specific tasks based on the day of the week, the existence of a file, or the success of a previous step.

Step-by-step walkthrough

To build effective orchestration, you need to understand how to connect activities using dependencies and control flow structures. Here are the most common patterns used in Azure Data Factory.

1. Sequential Chaining

The most basic pattern is Sequential Chaining. This is used when Task B must only start after Task A finishes successfully. You create this by dragging the green "Success" connector from the first activity to the second.

2. Parallel Execution

If you have multiple tasks that do not depend on each other-for example, copying data from three different SQL tables into separate folders-you should run them in parallel. In the ADF canvas, simply place the activities side-by-side without connecting them. ADF will trigger them at the same time, significantly reducing the total runtime of your pipeline.

3. Conditional Logic (If-Condition)

Sometimes you only want an activity to run under certain circumstances. The If-Condition activity acts as a gatekeeper. You might use an expression to check if a file exists; if it does (True), the pipeline runs the Copy activity; if it doesn't (False), it sends an email notification.

4. The Iteration Pattern (For Each)

When you need to repeat the same action for a list of items-like processing 50 different CSV files-the For Each activity is your best friend. You pass a collection (like a list of file names) into the activity, and it loops through each item, executing the internal activities for every entry in the list.

5. Error Handling (Try-Catch)

A professional pipeline always accounts for failure. By dragging the red "Failure" connector from an activity to a Web activity (like a Logic App trigger), you can create a "Catch" block. This ensures that if a task fails, you get an immediate alert rather than finding out days later.


{
    "name": "SequentialExample",
    "properties": {
        "activities": [
            {
                "name": "SourceToStaging",
                "type": "Copy",
                "dependsOn": []
            },
            {
                "name": "StagingToWarehouse",
                "type": "SqlUpsert",
                "dependsOn": [
                    {
                        "activity": "SourceToStaging",
                        "dependencyConditions": ["Succeeded"]
                    }
                ]
            }
        ]
    }
}

Common mistakes

  • Hardcoding values: Beginners often type specific file names or folder paths directly into activities. Use Parameters and Variables instead to make your orchestration reusable across different environments.
  • Ignoring "On Failure" paths: Many developers only plan for the "happy path" (success). Always add an activity to handle errors, even if it is just a simple log entry.
  • Over-nesting: Placing too many activities inside For Each or If-Condition blocks makes the pipeline hard to read. If a logic block becomes too complex, move those activities into a separate "Child Pipeline" and use the Execute Pipeline activity to call it.
  • Excessive parallelism: While running tasks in parallel is good, running 100 tasks at once might hit the limits of your source database or your Integration Runtime. Always monitor your "Batch Count" in For Each loops.

One practice task

Create a "Copy and Archive" pattern. Design a pipeline that first copies a file from a 'Landing' folder to a 'SQL Database'. If the copy is successful, use a Delete activity to remove the file from 'Landing'. If the copy fails, use a Copy activity to move that specific file to an 'Error' folder for manual review. This simple pattern teaches you sequential logic, success dependencies, and failure dependencies in one go.
