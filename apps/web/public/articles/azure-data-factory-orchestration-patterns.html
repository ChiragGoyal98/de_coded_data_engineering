Azure Data Factory orchestration patterns

Orchestration in Azure Data Factory is the process of managing and coordinating different data activities to work together as a cohesive workflow. Instead of running individual tasks manually, orchestration allows you to define a logical sequence, handle dependencies, and automate the movement of data from various sources to a destination. It serves as the "brain" of your data integration project, ensuring that every component runs at the right time and in the right order.

Why it matters

Without proper orchestration, data pipelines become brittle and difficult to manage. Orchestration patterns allow you to build resilience into your data engineering workflows. By defining clear patterns, you ensure that a downstream task doesn't start if an upstream task fails, preventing data corruption. Furthermore, efficient orchestration helps in cost optimization; by running tasks in parallel where possible, you reduce the total execution time, and by using conditional logic, you avoid running unnecessary processes, ultimately lowering your Azure consumption costs.

Step-by-step walkthrough

To master orchestration, you need to understand the four primary control flow patterns available in the Azure Data Factory (ADF) canvas.

1. Sequential Execution

This is the most basic pattern where tasks run one after the other. In the ADF UI, you create this by clicking the green "Success" box on an activity and dragging the arrow to the next activity.

  • Success (Green): Runs the next task only if the first one succeeds.
  • Failure (Red): Runs a specific task (like an error-logging script) only if the previous task fails.
  • Completion (Blue): Runs the next task regardless of whether the first one succeeded or failed.

2. Parallel Execution

If you have multiple tasks that do not depend on each other, such as loading ten different small tables from a SQL database to a Data Lake, you should run them in parallel. In ADF, simply place multiple activities on the canvas without connecting them to each other. They will all trigger simultaneously when the pipeline starts.

3. Conditional Logic (If-Condition)

This pattern allows your pipeline to make decisions. For example, you might want to check if a file exists before trying to copy it.

  • Use the Get Metadata activity to check for a file.
  • Use the If Condition activity to evaluate a expression (e.g., if the file count is greater than 0).
  • Inside the "True" case, place your Copy activity. Inside the "False" case, you might send an email notification.

4. Iterative Execution (ForEach)

When you need to perform the same set of actions on a list of items, use the ForEach activity. This is commonly used for "looping" through a list of folder names or table names retrieved from a database.

Here is a short example of how a ForEach activity is defined in the pipeline JSON code to iterate through an array of table names:


{
    "name": "IterateTables",
    "type": "ForEach",
    "typeProperties": {
        "items": {
            "value": "@pipeline().parameters.TableList",
            "type": "Expression"
        },
        "activities": [
            {
                "name": "CopyTableData",
                "type": "Copy",
                "inputs": [ { "referenceName": "SourceDataset", "type": "DatasetReference" } ]
            }
        ]
    }
}

Common mistakes

  • Hardcoding values: Beginners often hardcode file paths or table names inside activities. This makes orchestration difficult to scale. Always use Parameters and Variables to make your patterns dynamic.
  • Ignoring Timeouts: By default, some activities have very long timeout periods (7 days). If a task gets stuck, it will keep your pipeline running and potentially rack up costs. Always set a reasonable timeout (e.g., 1 or 2 hours) for your activities.
  • Over-nesting: Placing too many activities inside an "If Condition" or "ForEach" can make the pipeline hard to debug. If the logic inside a loop becomes complex, consider using the Execute Pipeline activity to call a separate "child" pipeline instead.

One practice task

Scenario: The Validated Copy

Create a pipeline that performs the following sequence:

  • Use a Get Metadata activity to see if a file named input.csv exists in your storage account.
  • Add an If Condition activity that checks the output of the Get Metadata activity.
  • If the file exists (True), trigger a Copy Activity to move it to a "processed" folder.
  • If the file does not exist (False), trigger a Wait Activity for 5 seconds to simulate a "skip" action.

This exercise will help you understand how to combine metadata, logic, and execution in a single orchestration flow.
