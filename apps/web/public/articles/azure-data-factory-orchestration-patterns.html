Azure Data Factory orchestration patterns

Azure Data Factory (ADF) is a cloud-based data integration service that allows you to create data-driven workflows. Orchestration is the process of coordinating these workflows to ensure that data moves from source to destination in a specific order, at the right time, and under certain conditions. Think of it as a logical map that tells your data where to go and what to do when it gets there. Without orchestration, your data tasks would be isolated scripts rather than a cohesive, automated system.

Why it matters

Orchestration is the backbone of any production-grade data architecture for several reasons:

  • Efficiency: It allows you to run tasks in parallel when they aren't dependent on each other, saving significant time.
  • Reliability: You can build in retry logic and error handling so that if one step fails, the system knows how to respond without manual intervention.
  • Modularity: Instead of one giant, messy pipeline, you can create small, reusable "child" pipelines that are called by a "parent" pipeline.
  • Cost Control: By controlling when and how long compute resources are active, you can minimize your Azure consumption costs.

Step-by-step walkthrough: The Parent-Child Pattern

The Parent-Child pattern is the most common orchestration method. It involves a main pipeline (the Manager) that triggers several smaller pipelines (the Workers).

1. Create the Child Pipeline

First, build a simple pipeline that performs a specific task, such as moving a single table from a SQL database to a Data Lake. Define parameters for this pipeline (like TableName) so it can be reused for different tables.

2. Create the Parent Pipeline

Create a new pipeline in the ADF Studio. This will serve as your orchestrator.

3. Add the 'Execute Pipeline' Activity

Drag the Execute Pipeline activity onto the canvas. In the settings, select the child pipeline you created in step 1.

4. Configure Parameters

If your child pipeline requires parameters, the Parent pipeline will prompt you to provide them. You can pass values dynamically using expressions.

5. Add Dependencies

Drag a second Execute Pipeline activity. To make it run only after the first one succeeds, click the green box on the first activity and drag the connector to the second one. This creates a sequential dependency.

Example Code: Execute Pipeline Definition

In ADF, activities are defined as JSON. Here is what an Execute Pipeline activity looks like when calling a child pipeline named CopySalesData:


{
    "name": "TriggerChildPipeline",
    "type": "ExecutePipeline",
    "typeProperties": {
        "pipeline": {
            "referenceName": "CopySalesData",
            "type": "PipelineReference"
        },
        "waitOnCompletion": true,
        "parameters": {
            "SourceTable": "Sales_2023"
        }
    }
}

Common mistakes

  • Hardcoding values: Beginners often type table names or folder paths directly into activities. Always use parameters and global variables to make your pipelines flexible.
  • Forgetting "Wait on completion": In the Execute Pipeline activity, there is a checkbox for "Wait on completion." If you uncheck this, the parent pipeline will start the child and immediately move to the next step without waiting to see if the child succeeded.
  • Ignoring Error Paths: Most users only connect the green (Success) path. You should also use the red (Failure) path to trigger alerts or log errors to a database.
  • Deep Nesting: While you can have a parent call a child, which calls a grandchild, going too deep makes debugging extremely difficult. Try to keep your hierarchy to two or three levels.

One practice task

Create an orchestration pattern that handles a "Cleanup" task. Build a pipeline with two activities:

  • A Copy Data activity that moves a dummy file.
  • A Stored Procedure activity (or a Script activity) that updates a log table.

The Challenge: Configure the pipeline so that the log activity runs regardless of whether the Copy Data activity succeeds or fails. (Hint: Look into "Completed" dependencies, which are represented by a blue connector).
