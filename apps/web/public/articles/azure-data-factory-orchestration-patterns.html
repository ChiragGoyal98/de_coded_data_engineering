Azure Data Factory orchestration patterns

In the world of cloud data engineering, moving data from point A to point B is rarely a straight line. Often, you need to ensure one task finishes before another starts, or perhaps you need to run several tasks simultaneously to save time. This coordination is known as orchestration. Azure Data Factory (ADF) serves as the conductor of this data symphony, using pipelines to manage the flow, timing, and dependencies of various data activities. Understanding orchestration patterns allows you to build workflows that are resilient, scalable, and easy to maintain.

Why Orchestration Patterns Matter

Orchestration is the difference between a collection of isolated scripts and a professional data platform. By using established patterns, you ensure that your data remains consistent. For example, if a transformation starts before the source data has finished loading, your reports will be inaccurate. Orchestration also allows for efficient resource management. Instead of running every task at once and hitting performance bottlenecks, or running them one-by-one and taking hours, you can find the perfect balance of parallel and sequential execution. Furthermore, good orchestration patterns include built-in error handling, ensuring that a single minor failure doesn't crash your entire data estate without notice.

Step-by-Step Walkthrough: Common Patterns

1. Sequential Execution (Chaining)

This is the most basic pattern where activities happen one after another. You use this when Activity B depends on the output of Activity A. In the ADF canvas, you simply drag the green connector (Success) from the first activity to the second.

  • Use a Copy Activity to move data from an API to Blob Storage.
  • Connect it to a Data Flow that transforms that data.
  • Connect that to a Stored Procedure that updates a final report table.

2. Parallel Execution

If two tasks are independent, running them at the same time reduces the total execution time. In ADF, any activities not connected by a dependency line will start simultaneously when the pipeline begins.

  • Drag three separate Copy Activities onto the canvas.
  • Leave them unconnected to each other.
  • When triggered, ADF will attempt to run all three at once, subject to your integration runtime limits.

3. Iteration and Looping (The For-Each Pattern)

When you have a list of items-like fifty different CSV files or ten database tables-you shouldn't create fifty different activities. Instead, use the Lookup activity to get a list of names and pass them into a ForEach activity.

  • Lookup Activity: Queries a configuration table to get a list of filenames.
  • ForEach Activity: Takes that list and runs a "Copy" task for every item in that list.

4. Conditional Branching

Sometimes you only want to run a task if a certain condition is met. The If Condition activity acts as a gatekeeper.

  • Use a Get Metadata activity to check if a file exists.
  • Inside the If Condition, use an expression to check the exists property.
  • If true, proceed to the "True" activities; otherwise, trigger an email notification in the "False" path.

Dynamic Expressions Code Example

A key part of orchestration is making your pipelines "smart" using dynamic expressions. Instead of hardcoding a filename, you can use a parameter passed through the orchestration chain.


// Example of a dynamic expression inside a ForEach activity 
// to point to a specific folder dynamically
{
    "folderPath": "@item().TargetFolder",
    "fileName": "@concat(item().FileName, '_', pipeline().TriggerTime, '.csv')"
}

Common Mistakes

  • Hardcoding Values: Beginners often type specific file paths or table names directly into activities. This makes the pipeline rigid. Always use parameters and variables to make your orchestration reusable.
  • Ignoring Dependency Colors: ADF has four dependency types: Green (Success), Red (Failure), Blue (Completion), and Grey (Skipped). Using "Completion" instead of "Success" can lead to data corruption if the second task runs even after the first one failed.
  • Over-nesting: Putting a ForEach inside an If-Condition inside another ForEach makes debugging nearly impossible. Keep pipelines modular by using the Execute Pipeline activity to call "child" pipelines.
  • Missing Timeouts: Default timeouts are often very long (7 days). If an activity hangs, it can consume your budget. Always set a reasonable timeout (e.g., 2 hours) based on your expected data volume.

Practice Task: The "Batch Processor"

To practice these patterns, try building a pipeline with the following logic:

  • Create a Lookup activity that returns a hardcoded array of three strings: ["Sales", "HR", "Finance"].
  • Connect this to a ForEach activity.
  • Inside the ForEach, add an If Condition.
  • Set the condition to check if the current item is equal to "Finance".
  • In the True path of the If Condition, add a Wait activity for 5 seconds (simulating a specific process for Finance).
  • In the False path, add a Wait activity for 2 seconds.

This exercise will help you understand how to pass data from a lookup into a loop and use logic to branch your orchestration path.
