Azure Data Factory orchestration patterns

In the world of cloud data engineering, moving data from point A to point B is rarely a single, isolated step. Usually, it involves a complex sequence of events where tasks must happen in a specific order, or only if certain conditions are met. This management of workflows is known as orchestration. In Azure Data Factory (ADF), orchestration is the logic that acts as the "brain" of your data integration, ensuring that your copy activities, transformations, and notifications all fire off in harmony.

Why it matters

Orchestration is what transforms a collection of individual tasks into a reliable, automated pipeline. Without structured orchestration patterns, data engineers would have to manually monitor processes and trigger steps one by one. By mastering these patterns, you ensure that your data stays consistent, error handling is automated, and resources are used efficiently. It allows you to build systems that can scale-handling five files today and five thousand tomorrow-without rewriting your logic. Furthermore, proper orchestration makes your pipelines easier to debug because you can clearly see where a specific link in the chain broke.

Step-by-step walkthrough

To build effective pipelines, you need to understand the basic building blocks of ADF orchestration. Here are the most common patterns and how to implement them.

1. Sequential vs. Parallel Execution

The simplest orchestration pattern is deciding whether tasks should run one after another or at the same time.

  • Sequential: Drag an output green arrow (Success) from Activity A to Activity B. Activity B will only start once Activity A finishes successfully.
  • Parallel: Leave two activities disconnected from each other. ADF will trigger both simultaneously, which is great for saving time when tasks don't depend on one another.

2. Conditional Logic (If Condition)

Sometimes you only want to run an activity if a specific criteria is met-for example, only loading data if today is the first day of the month.

  • Drag the If Condition activity onto your canvas.
  • In the "Expression" box, write your logic (e.g., checking a variable).
  • Inside the "True" or "False" activities boxes, add the tasks you want to execute based on that result.

3. Iteration (ForEach Activity)

If you have a folder full of 50 files and need to process each one, you don't create 50 copy activities. Instead, you use the ForEach activity.

  • Use a Get Metadata activity to get a list of child items (files) in a folder.
  • Pass that list into a ForEach activity.
  • Inside the ForEach loop, place a single Copy Activity. ADF will repeat that copy action for every file in your list.

4. Dependency Constraints

You can control the flow based on more than just "Success." ADF provides four dependency types:

  • Success (Green): Runs if the previous activity succeeds.
  • Failure (Red): Runs only if the previous activity fails (useful for sending error emails).
  • Completion (Blue): Runs regardless of success or failure.
  • Skipped (Grey): Runs if the previous activity was not executed.

Code Example: If Condition JSON

While most ADF work is done in the visual UI, it is helpful to see the underlying JSON structure for a conditional pattern.


{
    "name": "CheckDataQuality",
    "type": "IfCondition",
    "typeProperties": {
        "expression": {
            "value": "@equals(variables('RecordCount'), 0)",
            "type": "Expression"
        },
        "ifTrueActivities": [
            {
                "name": "SendAlert",
                "type": "WebActivity",
                "typeProperties": { "url": "https://youralertsystem.com" }
            }
        ]
    }
}

Common mistakes

  • Ignoring the "Sequential" setting in ForEach: By default, the ForEach activity runs tasks in parallel (up to 50 at once). If your tasks depend on each other (like writing to the same log table), you must check the "Sequential" box in the settings to avoid data conflicts.
  • Hardcoding values: Beginners often type file names directly into activities. Instead, use parameters and variables to make your orchestration patterns reusable across different environments.
  • Over-nesting: Avoid putting loops inside loops inside if-conditions. This makes pipelines hard to read and debug. If your logic gets too complex, break it into "Child Pipelines" and use the Execute Pipeline activity.
  • Forgetting Timeouts: If an activity gets stuck, it might run for hours (and cost money). Always set a reasonable timeout value in the activity settings.

One practice task

To practice your orchestration skills, create a "Safe Copy" pipeline.

  • Create a Copy Activity that moves a file from one folder to another.
  • Connect a Web Activity (or a simple Wait activity acting as a placeholder) to the Copy Activity using the Red (Failure) arrow.
  • Configure the second activity to represent an "Error Notification."
  • Test the pipeline by intentionally providing a wrong file name to the Copy Activity.
  • Verify that the "Error Notification" activity triggers correctly while the copy fails.
