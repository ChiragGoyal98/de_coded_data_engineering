Azure Data Factory orchestration patterns

In the world of cloud data engineering, Azure Data Factory (ADF) serves as the central nervous system for data movement and transformation. Orchestration is the process of arranging these complex movements into a synchronized, automated workflow. Instead of manually running individual tasks, orchestration patterns allow you to build logic that decides when, how, and in what order your data pipelines should execute. This is essential for turning simple data transfers into robust, enterprise-grade integration solutions.

Why it matters

Orchestration patterns are the difference between a fragile script and a resilient data platform. Using standardized patterns provides several critical benefits:

  • Scalability: Patterns like the "Metadata-Driven" approach allow you to handle hundreds of tables using a single pipeline instead of creating a hundred separate ones.
  • Maintainability: When logic is decoupled into smaller, modular pipelines, troubleshooting becomes significantly easier.
  • Error Handling: Proper orchestration ensures that if a step fails, the system knows whether to retry, stop, or alert the engineering team.
  • Cost Efficiency: By orchestrating tasks to run in parallel or only when specific conditions are met, you optimize your compute usage and reduce Azure costs.

Step-by-step walkthrough: The Parent-Child Pattern

The Parent-Child (or Master-Sub) pattern is the most fundamental orchestration technique. It involves a "Parent" pipeline that manages the flow and a "Child" pipeline that performs the actual unit of work.

1. Create the Child Pipeline

Start by building a pipeline that performs a specific task, such as copying a single table from a SQL database to Data Lake Storage. Instead of hardcoding the table name, create a Parameter (e.g., tableName) in the Parameters tab. Use this parameter in your dataset connection settings.

2. Create the Parent Pipeline

Create a new pipeline that will act as the orchestrator. This pipeline will use the Execute Pipeline activity. This activity allows you to call your Child pipeline from within the Parent.

3. Implement Iteration (The ForEach Activity)

If you have multiple tables to process, add a Lookup activity to the Parent pipeline to fetch a list of table names from a configuration file or SQL table. Link the output of the Lookup to a ForEach activity.

4. Connect the Logic

Inside the ForEach activity, place the Execute Pipeline activity. Map the current item from the ForEach loop to the parameter defined in the Child pipeline.

5. Code Example: Execute Pipeline JSON

The following JSON snippet demonstrates how an Execute Pipeline activity is structured within a Parent pipeline to pass a parameter:


{
    "name": "Execute_Child_Pipeline",
    "type": "ExecutePipeline",
    "dependsOn": [],
    "typeProperties": {
        "pipeline": {
            "referenceName": "ChildCopyPipeline",
            "type": "PipelineReference"
        },
        "waitOnCompletion": true,
        "parameters": {
            "tableName": "@item().sourceTableName"
        }
    }
}

Common mistakes

  • Hardcoding Values: Beginners often hardcode folder paths or database names inside activities. This forces you to create new pipelines for every new requirement. Always use parameters.
  • Ignoring "Wait on Completion": In the Execute Pipeline activity, the "Wait on Completion" checkbox is often overlooked. If unchecked, the Parent pipeline will continue to the next step immediately, even if the Child task is still running, which can lead to data dependency errors.
  • Lack of Dependency Constraints: Connecting activities only with "Success" (green) lines is a mistake. You should also plan for "Failure" (red) paths to log errors or send notifications when a task doesn't go as planned.
  • Overloading a Single Pipeline: Putting 20+ activities in a single pipeline makes it unreadable. Break them into modular sub-pipelines.

One practice task

To practice your orchestration skills, try building a "Validation Pattern." Create a Parent pipeline that first uses a Get Metadata activity to check if a specific file exists in your Azure Blob Storage. Use an If Condition activity to check the exists property. If the file exists, trigger an Execute Pipeline activity to process the data; if it does not exist, trigger a Web activity to send a basic alert or simply log the missing file requirement.
