Azure Data Factory orchestration patterns

Orchestration is the process of coordinating various tasks to ensure data flows correctly from source to destination. In Azure Data Factory (ADF), this means managing the dependencies between different activities, such as copying data from a database or running a transformation script in Databricks. Instead of triggering every task manually, orchestration allows you to automate the entire sequence based on logic, timing, and success or failure conditions. It acts as the "conductor" of your data symphony, ensuring every instrument plays at the right time.

Why it matters

Building a single pipeline to move one file is easy, but enterprise data environments are rarely that simple. Orchestration patterns allow you to handle complexity efficiently. By using structured patterns, you ensure that a data warehouse update doesn't start until the data extraction has finished successfully, preventing data corruption. Furthermore, good orchestration allows for parallel processing, which significantly reduces the time required for large data loads. It also provides a framework for error handling, so if one part of the process fails, the system can automatically send an alert or attempt a retry.

Step-by-step walkthrough

To master ADF orchestration, you need to understand how to connect activities using the following core patterns.

1. Sequential Chaining

The most basic pattern is the sequential flow. You connect activities using "success" connectors (the green arrows). In this setup, Activity B will only start once Activity A has finished successfully. This is ideal for processes where the output of one task is the required input for the next.

2. Parallel Execution

If you have multiple tasks that do not depend on each other-for example, moving three independent tables from an on-premises server to the cloud-you should run them in parallel. In the ADF canvas, simply place the activities without connecting them to each other. They will start simultaneously when the pipeline is triggered, saving significant execution time.

3. Conditional Logic (If-Condition)

Sometimes you only want to run an activity if a certain condition is met. The If-Condition activity allows you to branch your logic. For example, you might check if a file exists in a storage account; if it does (True), you run the copy activity; if it doesn't (False), you send an email notification.

4. The Parent-Child Pattern

For complex workflows, putting everything into one pipeline makes it hard to manage. Instead, use the Execute Pipeline activity. This allows you to create "Child" pipelines for specific tasks and a "Parent" pipeline to coordinate them.

Below is a JSON snippet of how an Execute Pipeline activity looks in the code behind the ADF UI:


{
    "name": "Trigger Child Pipeline",
    "type": "ExecutePipeline",
    "dependsOn": [],
    "userProperties": [],
    "typeProperties": {
        "pipeline": {
            "referenceName": "ChildPipeline_CopyData",
            "type": "PipelineReference"
        },
        "waitOnCompletion": true,
        "parameters": {
            "TableName": "Sales_Data"
        }
    }
}

5. Iteration (ForEach)

When you need to perform the same action on a collection of items (like a list of 50 tables), use the ForEach activity. You pass an array to the activity, and it repeats the internal logic for every item in that array.

Common mistakes

  • Hardcoding Values: Beginners often type table names or folder paths directly into activities. Use Parameters and Variables instead to make your orchestration patterns reusable.
  • Ignoring Failure Paths: Most users only use the green "Success" connector. Remember to use the red "Failure" connector to trigger logging or alerts when something goes wrong.
  • Over-nesting: Avoid putting too many loops inside loops. This makes debugging extremely difficult and can hit ADF's concurrency limits.
  • Missing Timeouts: By default, activities can run for a very long time. Always set a reasonable "Timeout" value so a stuck process doesn't waste your budget.

One practice task

To practice these concepts, try building a "Validation and Load" pattern. Create a pipeline with a Lookup activity that checks a SQL table for a "Status" value. Follow this with an If-Condition activity. If the status is "Ready," use an Execute Pipeline activity to run a separate data loading pipeline. If the status is anything else, use a Web activity to send a basic notification to a URL (or just a dummy script). This will help you understand dependency, conditional logic, and the parent-child structure.
