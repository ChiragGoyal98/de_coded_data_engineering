Azure Data Factory orchestration patterns

Azure Data Factory acts as the central engine for managing data movement and transformation across various services. Orchestration refers to the coordination and scheduling of these individual tasks to ensure they run in the correct order and handle errors gracefully. Rather than just running a single copy activity, orchestration allows you to build complex workflows that react to data changes and dependencies.

Why it matters

Orchestration is what transforms a collection of isolated scripts into a robust data platform. Without proper patterns, data pipelines become brittle and difficult to maintain. By using established orchestration patterns, you gain:

  • Resilience: Pipelines can automatically retry failed tasks or send alerts if something goes wrong.
  • Scalability: Instead of creating 50 separate pipelines for 50 different tables, you can use a single metadata-driven pipeline that loops through a list.
  • Cost Efficiency: You can ensure expensive compute resources (like Databricks clusters) only start when the data is actually ready for processing.
  • Modularity: Breaking large workflows into smaller, reusable "child" pipelines makes debugging significantly easier.

Step-by-step walkthrough: The Parent-Child Pattern

The most fundamental orchestration pattern is the Parent-Child (or Master-Worker) pattern. This involves a high-level "Master" pipeline that controls the logic and calls several "Child" pipelines to do the actual work.

Step 1: Create the Child Pipeline

Create a simple pipeline (e.g., Copy_Blob_To_SQL) that performs one specific task. Add a parameter called TableName to this pipeline so it isn't hardcoded to one destination.

Step 2: Create the Master Pipeline

Create a new pipeline named Master_Orchestrator. This pipeline will contain the logic for when and how the child tasks run.

Step 3: Add the Execute Pipeline Activity

From the Activities menu, drag the Execute Pipeline activity onto the canvas. In the "Settings" tab, select your child pipeline from the dropdown.

Step 4: Configure Dependencies

If you have multiple activities, connect them using the colored arrows:

  • Green (Success): Runs the next task only if the current one succeeds.
  • Red (Failure): Runs a task (like an error-logging script) only if the current one fails.
  • Blue (Completion): Runs the next task regardless of the outcome.

Step 5: Pass Parameters

In the "Settings" tab of the Execute Pipeline activity, you will see the parameters required by the child. You can pass values dynamically using expressions:


{
    "name": "Call_Child_Pipeline",
    "type": "ExecutePipeline",
    "settings": {
        "pipeline": {
            "referenceName": "Copy_Blob_To_SQL",
            "type": "PipelineReference"
        },
        "parameters": {
            "TableName": "Sales_Data_2023"
        }
    }
}

Common mistakes

  • Ignoring Timeouts: By default, activities have very long timeouts. If a source system hangs, your pipeline might run for days, consuming costs. Always set a reasonable timeout (e.g., 1 or 2 hours).
  • Hardcoding Values: Beginners often type file names directly into activities. Use Parameters and Global Parameters to make your pipelines reusable across Dev, Test, and Production environments.
  • Over-nesting: Avoid putting "ForEach" loops inside other "ForEach" loops. This makes it incredibly difficult to track which iteration failed during monitoring.
  • Forgetting the "Wait" Activity: When dealing with external APIs or asynchronous processes, beginners often fail to give the external system time to respond, leading to "File Not Found" errors.

One practice task

The Dynamic Folder Processor

  • Create a storage account with a container named uploads.
  • Inside uploads, create three folders: Inbound, Processed, and Error.
  • Create a pipeline that uses a Get Metadata activity to check if any files exist in the Inbound folder.
  • Use an If Condition activity:
  • If files exist, trigger a child pipeline to move them to Processed.
  • If no files exist, trigger a Web activity to send a "No data found" notification to a dummy URL (like a logic app or a webhook).
