Azure Data Factory orchestration patterns

Azure Data Factory (ADF) is widely known as a cloud-based ETL service, but its true strength lies in its ability to coordinate complex workflows. This coordination is called orchestration. Rather than just running a single task, orchestration allows you to define the order, conditions, and dependencies of multiple tasks to ensure data moves reliably across your ecosystem. Understanding these patterns is the difference between a fragile script and a professional data pipeline.

Why Orchestration Matters

In a production environment, data rarely moves in a single, straight line. You might need to wait for a file to arrive, check if a database table exists, or run three different processes at the same time to save time. Orchestration patterns allow you to:

  • Handle Dependencies: Ensure Task B only starts after Task A successfully finishes.
  • Error Handling: Define exactly what happens if a step fails (e.g., send an email or log the error).
  • Efficiency: Run independent tasks in parallel to reduce the total runtime of your pipeline.
  • Scalability: Use loops to process hundreds of files using a single logic block instead of creating hundreds of individual pipelines.

Step-by-Step Walkthrough: Common Patterns

1. Sequential Execution

This is the most basic pattern where tasks run one after another. In the ADF UI, this is represented by connecting the green box (on success) of one activity to the next activity. Use this when the output of the first task is required for the second task to begin.

2. Parallel Execution

If you have five tables to copy and they don't depend on each other, running them sequentially is a waste of time. To execute tasks in parallel, simply add multiple activities to the canvas without connecting them to each other. ADF will trigger them simultaneously, limited only by your integration runtime capacity.

3. Conditional Logic (If-Condition)

Sometimes you only want to run an activity if a certain criteria is met. For example, if a "Check File" activity finds a file, proceed to "Copy Data"; otherwise, "Wait" for ten minutes. The If Condition activity acts as a fork in the road, directing the flow based on a true/false expression.

4. The Iterative Pattern (ForEach)

When you need to perform the same action on a list of items-such as a list of folder names or a list of database tables-you use the ForEach activity.

Below is a short JSON representation of how a ForEach activity is structured to iterate over an array of table names:


{
    "name": "IterateTables",
    "type": "ForEach",
    "typeProperties": {
        "items": {
            "value": "@pipeline().parameters.TableList",
            "type": "Expression"
        },
        "activities": [
            {
                "name": "CopyTableData",
                "type": "Copy"
                // Activity details here
            }
        ]
    }
}

5. Execute Pipeline Pattern (Parent-Child)

As your project grows, your pipeline can become cluttered. The Execute Pipeline activity allows you to call one pipeline from another. This promotes reusability; you can build one "Standard Logging" pipeline and call it from every other pipeline in your project.

Common Mistakes

  • Ignoring the "On Failure" Path: Many beginners only connect the green (success) paths. If an activity fails, the pipeline simply stops. Always consider adding a red (on failure) path to alert your team.
  • Over-nesting: Putting a ForEach inside another ForEach can make debugging extremely difficult and may hit ADF concurrency limits.
  • Hardcoding Values: Avoid typing specific file names or folder paths directly into activities. Use parameters and variables to make your orchestration patterns flexible.
  • Circular Dependencies: Trying to make Activity A depend on Activity B, while Activity B also depends on Activity A, will cause a validation error.

Practice Task: The "Safe Copy" Workflow

To practice these patterns, try building the following workflow in your ADF environment:

  • Validation: Add a Validation activity to check if a specific CSV file exists in your Blob Storage.
  • Success Path: Connect the "Success" output to a Copy Activity that moves the file to a "Processed" folder.
  • Failure Path: Connect the "Failure" output of the Validation activity to a Web Activity that sends a dummy notification (or use a Wait activity as a placeholder).
  • Final Step: Regardless of success or failure, use the blue "Completion" connector to trigger a Script activity that logs the end time of the attempt into a SQL table.
