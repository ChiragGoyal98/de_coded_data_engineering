Databricks Delta Lake best practices

Delta Lake has become the standard storage layer for modern data engineering because it combines the best of data warehouses and data lakes. It provides the reliability of ACID transactions with the low cost and scalability of cloud storage. However, simply using Delta Lake isn't enough to ensure a performant system. To get the most out of Databricks, you need to follow specific management patterns that keep your data organized and your queries fast.

Why it matters

Without proper management, a data lake can quickly turn into a "data swamp." Performance degrades as the number of small files grows, and cloud storage costs can spike if old, unused data versions are never cleaned up. Following best practices ensures that your data pipelines remain scalable, your costs stay predictable, and your analysts can query data without waiting for hours.

Step-by-step walkthrough of best practices

1. Optimize Partitioning

Partitioning is the process of dividing your data into physical folders based on a specific column. A common mistake is partitioning by a column with too many unique values (like user_id or timestamp).

  • Best Practice: Only partition on columns where you have a manageable number of values (e.g., year, month, or region).
  • Rule of Thumb: Avoid partitioning tables that are smaller than 1 TB. For smaller tables, Delta Lake's built-in data skipping is usually faster.

2. Compact Small Files

Every time you write data to a table, Delta Lake creates new files. Over time, thousands of tiny files can accumulate, which slows down read operations significantly.

  • Best Practice: Regularly run the OPTIMIZE command. This merges small files into larger, more efficient chunks (aiming for ~1GB per file).

3. Use Z-Ordering for Faster Queries

Z-Ordering is a technique used to colocate related information in the same set of files. This drastically reduces the amount of data Databricks needs to read.

  • Best Practice: Z-Order by columns that are frequently used in your WHERE clauses (e.g., customer_id).

4. Manage Data Retention with Vacuum

Delta Lake keeps history for "Time Travel," allowing you to see previous versions of your data. If you never clean this up, you pay for storage you don't need.

  • Best Practice: Use the VACUUM command to delete data files no longer referenced by a Delta table and older than a specific retention period (default is 7 days).

5. Enable Auto-Optimize

In many production environments, you can't manually run optimize commands every hour.

  • Best Practice: Enable "Auto Optimize" and "Auto Compact" in your Spark configuration. This tells Databricks to automatically handle file sizing during write operations.

Code example

Here is how you would apply the OPTIMIZE and ZORDER commands to a sales table to improve performance for queries filtering by date and store location.


-- Consolidate small files and organize data by store_id
OPTIMIZE sales_data
WHERE transaction_date >= '2023-01-01'
ZORDER BY (store_id);

-- Remove files older than 7 days to save on storage costs
VACUUM sales_data;

Common mistakes

  • Over-partitioning: Creating thousands of partitions (e.g., partitioning by date for 10 years of data) creates massive metadata overhead and slows down the Spark optimizer.
  • Running Vacuum too frequently: If you vacuum with a retention period of 0, you lose the ability to go back in time and might break concurrent read operations.
  • Neglecting Schema Evolution: Users often manually try to change table schemas. Instead, use the .option("mergeSchema", "true") setting in your Spark write command to allow Delta to handle new columns gracefully.

Practice task

To test your knowledge, try the following in a Databricks notebook:

  • Create a dummy Delta table with at least 10,000 rows.
  • Run the DESCRIBE HISTORY table_name command to see the different versions created.
  • Run an OPTIMIZE command on a specific column you think would be used for filtering.
  • Use the VACUUM command with a retention period (note: you may need to set a Spark configuration to allow a retention period shorter than 168 hours if testing on a fresh table).
