SDK patterns for production-grade AI integrations

When you first start working with Large Language Models (LLMs), it is tempting to just copy-paste a basic API call from the documentation and call it a day. However, building a professional application requires more than just getting a single response. To move from a prototype to a production environment, you need to implement specific patterns that ensure your application is reliable, cost-effective, and easy to debug. Software Development Kits (SDKs) provided by companies like OpenAI or Anthropic offer tools to manage these complexities, but knowing how to structure your code around them is the key to success.

Why it matters

In a production environment, "it works on my machine" is not enough. Reliability is the primary concern because LLM APIs are external services that can experience latency, rate limits, or occasional downtime. Without proper SDK patterns, a single failed network request could crash your entire application. Furthermore, production-grade code must be maintainable; if you decide to switch from one model provider to another, a well-structured SDK integration allows you to make that change in one place rather than rewriting your entire codebase.

Step-by-step walkthrough

1. Centralize Client Initialization

Never initialize your API client inside a function that gets called repeatedly. Instead, use a Singleton pattern or a centralized configuration module. This ensures you aren't wasting resources recreating the client and provides a single place to manage authentication keys.

2. Implement Resiliency with Retries

Network flakiness and rate limits (429 errors) are common when dealing with LLM APIs. Most modern SDKs have built-in retry logic, but you should explicitly configure "Exponential Backoff." This means that if a request fails, the system waits a short time before trying again, increasing the wait time with each failure to avoid overwhelming the server.

3. Enforce Structured Outputs

For a UI to display data correctly, you cannot rely on the LLM's "chatty" nature. Use SDK features like "JSON Mode" or "Function Calling" (Tools) combined with validation libraries like Pydantic. This forces the model to return data in a specific format that your code can reliably parse.

4. Set Timeouts and Deadlines

LLMs can sometimes take a long time to generate a response. In production, you don't want a user's request hanging indefinitely. Always set a maximum timeout in your SDK configuration. If the model doesn't respond within 30 seconds, for example, the SDK should trigger an error so your app can show a "try again" message.

5. Environment-Based Configuration

Use environment variables (.env files) to manage API keys and model versions. This allows you to use cheaper, faster models (like GPT-4o-mini) for development and testing, while reserving the more powerful, expensive models for your production deployment.

Code Example: Robust Client Wrapper


import os
from openai import OpenAI
from tenacity import retry, stop_after_attempt, wait_exponential

# Initialize client using environment variables
client = OpenAI(api_key=os.getenv("OPENAI_API_KEY"))

# Use a decorator to handle retries automatically
@retry(stop=stop_after_attempt(3), wait=wait_exponential(multiplier=1, min=2, max=10))
def get_completion(prompt):
    try:
        response = client.chat.completions.create(
            model="gpt-4o",
            messages=[{"role": "user", "content": prompt}],
            timeout=30.0  # Ensure the request doesn't hang forever
        )
        return response.choices[0].message.content
    except Exception as e:
        print(f"Logging error: {e}")
        raise e

Common mistakes

  • Hardcoding API Keys: Never put your secret keys directly in the code. If you push that code to GitHub, your account will be drained within minutes by bots.
  • Ignoring Token Limits: Every model has a maximum "context window." If you send too much text, the API will fail. Always implement a check or a "truncation" strategy for long inputs.
  • Lack of Logging: When an LLM gives a "bad" answer, you need to know exactly what prompt was sent to fix it. Always log your inputs and outputs (safely, without PII) in production.
  • No Streaming for Long Tasks: For longer responses, users hate staring at a loading spinner. Failing to use "Streaming" (the typewriter effect) makes your app feel slow and unresponsive.

One practice task

Create a Python script that uses an LLM SDK to summarize a paragraph. Modify the script to include a timeout of 1 second. Run the script and observe it fail. Then, wrap the call in a try/except block that catches the timeout error and prints a friendly message: "The server is taking too long, please try again later." This teaches you how to handle the inevitable "real world" failures of cloud APIs.
