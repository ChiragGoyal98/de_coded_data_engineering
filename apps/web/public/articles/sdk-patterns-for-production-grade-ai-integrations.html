SDK patterns for production-grade AI integrations

When you first start building with Large Language Models, it is tempting to just copy and paste the quickstart code from an API provider and call it a day. However, moving from a experimental script to a production-grade application requires a more structured approach. Integrating an LLM API into a software product means you have to account for network instability, varying response times, and the need for maintainable code. By using specific Software Development Kit patterns, you can ensure your application remains robust and easy to update as new models are released.

Why it matters

Using professional patterns for SDK integration is the difference between a prototype that crashes during a peak in traffic and a resilient service. In production, LLM calls are often the most fragile part of your stack because they rely on external servers and high-latency processes.

A standardized integration pattern allows you to:

  • Swap model providers (e.g., moving from OpenAI to Anthropic) without rewriting your entire codebase.
  • Implement central logging and monitoring for token usage and costs.
  • Automatically handle temporary network failures or rate limits.
  • Keep your API keys secure and managed in one place.

Step-by-step walkthrough

1. The Client Singleton Pattern

Avoid creating a new instance of the SDK client every time you want to make a request. Creating a client involves overhead like setting up connection pools. Instead, initialize the client once and reuse it across your application.

2. Create an Abstraction Wrapper

Instead of calling openai.chat.completions.create directly in your business logic, wrap it in a custom service class. This "Adapter" pattern ensures that if the SDK changes its method names in a future version, you only have to fix your code in one file.

3. Implement Robust Error Handling

Production code must anticipate that the API will fail. You should wrap your SDK calls in a try-except block that specifically looks for timeout errors, rate limit errors (429), and authentication issues.

4. Use Exponential Backoff

If an API call fails due to a rate limit, the SDK should not just try again immediately. Use a strategy where the wait time between retries increases (e.g., 1 second, then 2, then 4) to give the API provider time to recover.

5. Standardize Data Models

Use tools like Pydantic in Python to define exactly what your "Input" and "Output" should look like. This prevents your application from crashing if the LLM returns an unexpected JSON format.

Code Example: A Production-Grade Wrapper


import os
from openai import OpenAI
from tenacity import retry, stop_after_attempt, wait_exponential

class AIService:
    def __init__(self):
        # Initialize client once (Singleton-style)
        self.client = OpenAI(api_key=os.getenv("OPENAI_API_KEY"))

    @retry(wait=wait_exponential(multiplier=1, min=4, max=10), stop=stop_after_attempt(3))
    def get_summary(self, text: str):
        # Abstraction layer with built-in retry logic
        try:
            response = self.client.chat.completions.create(
                model="gpt-3.5-turbo",
                messages=[{"role": "user", "content": f"Summarize: {text}"}]
            )
            return response.choices[0].message.content
        except Exception as e:
            print(f"Logging error for monitoring: {e}")
            raise

Common mistakes

  • Hardcoding API Keys: Never place your secret keys directly in the code. Always use environment variables or a secret management service.
  • Ignoring Timeouts: By default, some SDKs wait indefinitely. Always set a maximum timeout so your application doesn't hang forever if the model provider is slow.
  • Lack of Cost Tracking: In production, it is easy to rack up bills. Implement a pattern that logs the "usage" metadata returned by the SDK (prompt tokens and completion tokens) to a database.
  • Direct Logic Coupling: Do not let the specific quirks of one SDK leak into your front-end or main business logic. Use an internal data format to pass messages around.

One practice task

Create a Python script that uses the "Service" pattern described above. Define a class called ModelProvider that initializes an LLM client. Add a method that takes a string input and returns a response, but include a check that raises a custom error if the input string is empty. This will help you practice encapsulating validation and SDK logic in a single, reusable module.
