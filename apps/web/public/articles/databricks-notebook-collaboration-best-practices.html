Databricks notebook collaboration best practices

Databricks notebooks are more than just a place to write code; they serve as a collaborative workspace where data engineers and scientists build solutions together. Much like a shared document, these notebooks allow multiple people to edit, comment, and run cells simultaneously. However, without a set of established best practices, this shared environment can quickly become chaotic with overwritten code or lost logic. Learning how to manage these shared spaces effectively ensures that your team remains productive and your codebase stays clean.

Why it matters

Collaboration in Databricks is powerful, but it comes with risks. When multiple engineers work on the same notebook, there is a high chance of "code stomping," where one person's changes are accidentally erased by another. Proper collaboration practices provide:

  • Version Control: Tracking changes over time so you can revert to a working version if something breaks.
  • Code Quality: Peer reviews and comments help catch bugs before they reach production.
  • Knowledge Sharing: Using markdown and comments within notebooks makes it easier for new team members to understand the logic.
  • Accountability: Built-in history tools allow teams to see who made specific changes and why.

Step-by-Step Walkthrough

1. Connect to Databricks Repos (Git Integration)

The most important rule for collaboration is to never rely solely on the notebook's autosave. You should link your Databricks workspace to a Git provider like GitHub, GitLab, or Azure DevOps.

  • Go to the Repos tab in the sidebar.
  • Create a new Repo and link it to your remote Git repository.
  • Use branches! Just like standard software development, create a feature branch (e.g., feature/user-cleanup) instead of working directly on the main branch.

2. Use Markdown Cells for Documentation

A notebook without context is difficult for a collaborator to follow. Use Markdown cells to explain the "why" behind your code.

  • Use ## for section headers.
  • Use bullet points to list dependencies or requirements.
  • Use bold text to highlight important warnings or parameters.

3. Leverage Real-Time Co-authoring and Presence

Databricks shows you who else is currently viewing or editing a notebook via icons in the top right corner.

  • If you see a colleague's cursor in a cell, avoid editing that specific cell simultaneously.
  • Use the Comments feature (the speech bubble icon) to leave feedback or questions on specific lines of code rather than writing notes inside the code cells themselves.

4. Use Databricks Widgets for Parameterization

When collaborating, your teammates might want to run your notebook with different dates or file paths. Instead of asking them to change the code, use Widgets.


# Create a text widget for a department name
dbutils.widgets.text("department", "Sales", "Enter Department")

# Access the value in your code
dept_name = dbutils.widgets.get("department")
print(f"Filtering data for: {dept_name}")

5. Check Revision History

If a collaborator makes a mistake, you don't need to panic.

  • Click the Revision History button (the clock icon) on the right sidebar.
  • You can compare the current version with any previous version and click Restore this version to roll back changes instantly.

Common Mistakes

  • Hardcoding Personal Paths: Using paths like /Users/your-name/data.csv makes the notebook break for everyone else. Always use shared paths or parameters.
  • Leaving Large Outputs: Saving a notebook with thousands of rows of printed data makes the file heavy and slow to load for others. Clear your cell outputs before committing to Git.
  • Working in the "Shared" Folder without Branches: This leads to multiple people editing the same file without a safety net. Always use the Repos feature for production-level work.
  • Ignoring Secrets: Never type passwords or API keys directly into a notebook cell. Use Databricks Secrets so collaborators can run the code without seeing the sensitive credentials.

Practice Task

To get comfortable with these practices, try this simple workflow with a teammate:

  • Create a new notebook in a shared folder or a Repo.
  • Add a Markdown cell at the top describing a simple task (e.g., "This notebook calculates average sales").
  • Create a widget that accepts a number as input.
  • Have your teammate open the notebook and use the Comments feature to suggest a change to your code.
  • Open the Revision History and practice restoring the notebook to the version before your teammate's comment.
