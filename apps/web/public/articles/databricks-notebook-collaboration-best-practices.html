Databricks notebook collaboration best practices

Databricks notebooks are more than just a place to write code; they are a shared workspace where data engineers and scientists build solutions together. While the platform allows multiple people to type in the same notebook at once, working effectively as a team requires more than just shared access. Without a clear strategy, you might find yourself overwriting a colleague's work or struggling to understand why a certain block of code was changed. Learning how to collaborate properly ensures that your data pipelines remain stable and your team stays productive.

Why it matters

When working in a professional environment, "moving fast" should not come at the expense of "breaking things." Collaboration best practices matter because they:

  • Prevent Code Conflicts: They stop two people from accidentally deleting each other's progress.
  • Improve Code Quality: Peer reviews and comments help catch bugs before they reach production.
  • Maintain Security: Proper permission settings ensure that sensitive data and configurations are only accessible to the right people.
  • Ensure Reproducibility: By using version control, you can always jump back to a previous version if a new change breaks the workflow.

Step-by-step walkthrough

1. Set up Databricks Repos

The most important step for collaboration is moving away from standalone workspace notebooks and using Databricks Repos. This allows you to link your notebooks to a Git provider like GitHub, GitLab, or Azure DevOps.

  • Open the "Repos" tab in the sidebar.
  • Click "Add Repo" and clone your team's repository.
  • Create a new branch for your specific task. This prevents you from making changes directly to the "main" branch that everyone else is using.

2. Use the Built-in Commenting System

Instead of sending screenshots in Slack or Teams, use the built-in commenting tool.

  • Highlight a specific line of code or a markdown cell.
  • Click the speech bubble icon on the right side of the cell.
  • Tag your teammate using the @ symbol to notify them. This keeps the conversation right next to the logic it refers to.

3. Manage Permissions Carefully

Not everyone needs full control over every notebook. Use the "Share" button at the top right to assign specific roles:

  • Can Run: Best for stakeholders who only need to execute the notebook to see results.
  • Can Edit: For active contributors.
  • Can Manage: For team leads who need to control sharing settings.

4. Modularize Code with Widgets

To avoid hardcoding values (like file paths or dates) that your teammates might need to change, use Databricks Widgets. This allows others to interact with your notebook without touching the core code.


# Create a text widget for a database name
dbutils.widgets.text("database_name", "default_db", "Target Database")

# Access the value in your code
target_db = dbutils.widgets.get("database_name")
print(f"Loading data into: {target_db}")

Common mistakes

  • Hardcoding Secrets: Never type passwords or API keys directly into a notebook. Use Databricks Secrets so your teammates can run the code without seeing the actual credentials.
  • Ignoring the Revision History: If someone makes a mistake, don't panic. Use the "Revision History" clock icon at the top right to compare versions and restore previous work.
  • Gigantic Notebooks: Collaboration becomes difficult when a notebook is thousands of lines long. If a notebook gets too big, break it into smaller, specialized notebooks and call them using %run.
  • Working on 'Main' Simultaneously: If two people edit the same cell on the same branch at the exact same time, Git conflicts will occur. Always communicate which section you are working on.

One practice task

To get comfortable with collaboration, try this exercise with a teammate:

  • Create a new notebook in a shared folder.
  • Create a "Text Widget" at the top of the notebook.
  • Have your teammate add a comment to a specific line of code asking for a change.
  • Reply to the comment, make the change, and then use the Revision History to see exactly what changed between your version and theirs.
