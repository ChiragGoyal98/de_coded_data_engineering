Databricks notebook collaboration best practices

Databricks notebooks are powerful tools that allow data engineers and data scientists to write code, visualize data, and document processes in one place. One of their most significant features is the ability to collaborate in real-time, much like a shared Google Doc. However, without a clear strategy, multiple people working on the same notebook can quickly lead to overwritten code, confusing version histories, and broken pipelines. Understanding how to manage shared workspaces effectively is essential for any team looking to maintain a professional data environment.

Why Collaboration Best Practices Matter

In a fast-moving data team, the "wild west" approach-where everyone edits files wherever they please-leads to several critical issues. First, it creates versioning nightmares; if two people edit the same cell at the same time, the last person to save might accidentally delete their colleague's work. Second, without proper permissions, a junior developer might accidentally modify a production-level notebook.

By following best practices, teams ensure code quality through peer reviews and maintain a clear audit trail of who changed what and why. This level of organization is the difference between a project that scales effortlessly and one that becomes a liability.

Step-by-Step Walkthrough for Collaboration

1. Integrate with Databricks Repos

Instead of saving notebooks in the general "Workspace" folder, use Databricks Repos. This allows you to sync your notebooks with a Git provider like GitHub, GitLab, or Azure DevOps.

  • Navigate to the Repos tab in the sidebar.
  • Click Add Repo and clone your team's repository.
  • Use branches for individual features. Never work directly on the main branch. This allows you to use Pull Requests (PRs) for code review before merging changes.

2. Use the Built-in Commenting System

Communication should happen where the code lives. Databricks has a native commenting feature that allows you to highlight specific lines of code.

  • Highlight a block of code and click the Comment icon that appears on the right.
  • Use this to ask questions or explain complex logic to your teammates.
  • Resolve comments once the issue has been addressed to keep the workspace clean.

3. Implement Access Control Lists (ACLs)

Not every team member needs the same level of access. Use the "Permissions" settings (top right of a notebook) to assign roles:

  • Can View: Good for stakeholders who only need to see results.
  • Can Run: Best for analysts who need to execute the code but shouldn't change it.
  • Can Edit: For active developers on the project.
  • Can Manage: Reserved for team leads or admins.

4. Parameterize with Widgets

When sharing notebooks, avoid hardcoding values like dates or file paths. Use Databricks Widgets so that collaborators can input their own parameters without changing the underlying code.


# Create a text widget for a database name
dbutils.widgets.text("database_name", "default_db", "Target Database")

# Access the value in your code
target_db = dbutils.widgets.get("database_name")
print(f"Loading data into: {target_db}")

5. Standardize Notebook Organization

A collaborative notebook should be easy to read. Use Markdown cells to create headers (#, ##, ###) and provide a brief table of contents at the top. Always include a "Purpose" cell at the very beginning to explain what the notebook does.

Common Mistakes

  • Editing in the Shared Workspace: Many beginners edit notebooks in the shared "Users" folder. This is dangerous because there is no version control. Always use a Git branch.
  • Leaving Secrets in Cells: Never write passwords or API keys in a notebook cell. Use Databricks Secrets and dbutils.secrets.get() to keep credentials safe from teammates who might have "View" access but shouldn't see passwords.
  • Ignoring Revision History: Databricks keeps a local history of changes. If you accidentally delete a cell, click the "Revision History" clock icon at the top right to restore a previous version.
  • Massive Notebooks: Collaborative notebooks become hard to manage when they are thousands of lines long. Break large tasks into smaller, modular notebooks and use %run or specialized Python files to link them.

Practice Task

To get comfortable with these practices, try the following exercise:

  • Create a new notebook in your personal folder.
  • Create a "Dropdown" widget at the top with three options: Development, Staging, and Production.
  • Add a Markdown cell at the top describing the purpose of the notebook.
  • Share the notebook with a colleague (or a second test account) and grant them "Can Run" permissions only.
  • Ask them to leave a comment on a specific cell and then attempt to resolve that comment yourself.
