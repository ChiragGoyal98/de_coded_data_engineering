Databricks notebook collaboration best practices

Databricks notebooks offer a powerful environment where data engineers and scientists can build pipelines together in real-time. However, when multiple people work on the same logic simultaneously, it is easy to run into conflicts or lose track of changes. Establishing a clear set of collaboration rules ensures that the team remains productive and the codebase stays clean while preventing the accidental deletion of critical work.

Why it matters

Collaboration is the backbone of modern data engineering. Without standard practices, teams often face "code drift," where different versions of the same notebook exist across various user folders. This lead to errors in production and hours of wasted time debugging which version is the source of truth. By following best practices, you ensure that code is peer-reviewed, version-controlled, and easily accessible to anyone on the team, regardless of who originally wrote it.

Step-by-step walkthrough

1. Leverage Databricks Repos for Git Integration

The most important practice is moving away from keeping notebooks in private "User" folders. Instead, use Databricks Repos to connect your workspace to a Git provider like GitHub, GitLab, or Azure DevOps.

  • Create a new Repo in the Databricks sidebar.
  • Link it to your team's Git repository.
  • Always create a new branch for your changes rather than working directly on the main branch.

2. Use Built-in Commenting for Code Reviews

Databricks notebooks allow you to highlight code and leave comments. This is similar to Google Docs.

  • Highlight a specific line of code.
  • Click the comment icon on the right margin.
  • Use @mentions to notify a specific team member. This keeps the discussion context-specific and avoids long, confusing email chains.

3. Modularize Your Code

To prevent notebooks from becoming massive and unreadable, break your logic into smaller, reusable notebooks. You can call one notebook from another using the %run magic command. This allows one person to work on "data_cleaning" while another works on "feature_engineering" without interfering with each other's cells.


# Example: Calling a utility notebook to share functions
# This command runs the 'utils' notebook and makes its functions available here.

%run ./utils_notebook

# Now you can use a function defined in that notebook
df_cleaned = clean_column_names(raw_data_df)

4. Manage Permissions Carefully

Not everyone needs "Can Manage" access to every notebook. Use the "Permissions" settings (top right of the notebook) to assign appropriate levels:

  • Run: For users who only need to execute the logic.
  • Edit: For collaborators actively writing code.
  • Manage: For team leads who need to control access and deletions.

5. Utilize Revision History

If someone accidentally deletes a cell or breaks a function, don't panic. Click on the "Revision History" clock icon at the top right. You can see a list of every version saved, compare versions side-by-side, and restore the notebook to a previous healthy state.

Common mistakes

  • Hardcoding Secrets: Never write passwords or API keys directly in a notebook cell. If a teammate clones your notebook, they might accidentally push those secrets to Git. Use Databricks Secrets (dbutils.secrets) instead.
  • Working in the Same Cell: While Databricks allows real-time co-authoring, having two people typing in the exact same cell simultaneously can lead to synchronization lag. It is better to work in separate cells.
  • Ignoring the Table of Contents: Large notebooks are hard to navigate. Failing to use Markdown headers (##) to organize the notebook makes it difficult for collaborators to find specific logic.
  • Manual Backups: Avoid exporting notebooks as .dbc files to your local computer as a "backup." This creates versioning silos. Stick to Git.

One practice task

To get started with effective collaboration, try this exercise:

  • Create a new folder in your Databricks Workspace called "Team_Project."
  • Create a notebook inside called Global_Config.
  • Define a simple Python variable inside it, such as bronze_path = "/mnt/data/bronze".
  • Create a second notebook and use the %run command to import the Global_Config notebook.
  • Verify that you can print the bronze_path variable in the second notebook. This is the first step toward building a modular, team-friendly codebase.
