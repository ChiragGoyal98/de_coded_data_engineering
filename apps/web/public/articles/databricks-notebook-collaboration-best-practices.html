Databricks notebook collaboration best practices

Databricks notebooks serve as a dynamic workspace where multiple users can write code, visualize data, and document processes simultaneously. While the platform makes it easy to share work, working in a shared environment requires a specific set of habits to ensure code quality and prevent team conflicts. By following collaboration best practices, beginners can transform a chaotic shared folder into a streamlined development pipeline.

Why it matters

Collaboration in Databricks isn't just about typing in the same window; it is about maintaining a reliable and scalable codebase. When teams ignore best practices, several issues arise:

  • Code Overwrites: Without proper version control, one person's changes might accidentally delete another person's work.
  • Lack of Context: Code without comments or documentation is difficult for team members to troubleshoot or update later.
  • Security Risks: Poor sharing habits often lead to hardcoded credentials being exposed to the whole team.
  • Bottlenecks: If only one person understands how a notebook works, the entire project stalls when that person is away.

Step-by-step walkthrough

1. Leverage Databricks Repos for Git Integration

The most important step for any team is to move away from "Workspace" notebooks and into "Repos." This allows you to link your Databricks environment to GitHub, GitLab, or Bitbucket.

  • Open the "Repos" tab in the sidebar.
  • Click "Add Repo" and clone your team's Git repository.
  • Use branches for individual features to avoid breaking the main production code.

2. Use Built-in Commenting and Mentions

Instead of sending screenshots in chat apps, use the native commenting tool. Highlight a block of code, click the message icon in the right margin, and type your feedback. You can use "@" to tag a teammate, which sends them an email notification with a direct link to the notebook cell.

3. Modularize Code with Widgets

To make notebooks reusable for others, avoid hardcoding values like dates or file paths. Use Databricks Widgets to create input fields at the top of the notebook.


# Create a text input widget for the team to specify a folder path
dbutils.widgets.text("input_path", "/mnt/training/data", "Data Path")

# Access the value in your code
current_path = dbutils.widgets.get("input_path")
print(f"Loading data from: {current_path}")

4. Organize with Markdown and Headers

A collaborative notebook should read like a story. Use Markdown cells (starting with %md) to explain why a certain transformation is happening. Use # and ## headers; Databricks automatically generates a Table of Contents on the left sidebar based on these headers, making it easy for teammates to navigate long notebooks.

5. Standardize Access Control

Don't give everyone "Can Manage" permissions. Use the "Permissions" button at the top right of the notebook to assign roles:

  • Can View: For stakeholders.
  • Can Run: For analysts who need to see results.
  • Can Edit: For active developers on the project.

Common mistakes

  • Hardcoding Credentials: Never type passwords or API keys in a notebook. Use Databricks Secrets so others can run your code without seeing sensitive information.
  • Ignoring Version History: Beginners often forget that Databricks tracks every change. If you accidentally delete a cell, click "Revision History" at the top right to restore it.
  • Giant Notebooks: Working in a notebook with hundreds of cells is difficult for collaborators. If a notebook becomes too long, split it into smaller, logical parts and use %run or Python packages to link them.
  • Leaving "Draft" Code: Leaving half-finished cells or "print(df.head())" debugging code everywhere makes the notebook messy for others. Clean up your workspace before pushing changes to Git.

One practice task

To practice collaborative workflows, try setting up a parameterized notebook. Create a new notebook, add a dropdown widget using dbutils.widgets.dropdown("environment", "dev", ["dev", "prod", "test"]), and then write a simple print statement that displays the selected environment. Share this notebook with a colleague (or a second test account) with "Can Run" permissions and ask them to change the dropdown and run the cell.
