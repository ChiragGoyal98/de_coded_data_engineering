Databricks notebook collaboration best practices

Working in Databricks often means moving from a solo developer mindset to a team-oriented environment. Because Databricks notebooks are cloud-based and live-synced, multiple engineers can edit the same file simultaneously. However, without a clear strategy, this real-time collaboration can lead to confusion, broken code, and lost progress. Establishing clear protocols ensures that every team member can contribute effectively while maintaining a clean and functional codebase.

Why it matters

Collaboration is the backbone of modern data engineering. In Databricks, poor collaboration habits result in "notebook sprawl," where dozens of versions of the same file exist with names like clean_data_v1_final_v2.

  • Reliability: Proper versioning ensures you can always roll back to a working state if a colleague's changes break the pipeline.
  • Security: Best practices prevent sensitive information, like API keys or database passwords, from being accidentally shared or committed to a repository.
  • Efficiency: Shared standards mean any team member can open a notebook and understand the logic immediately, reducing time spent on hand-offs and troubleshooting.

Step-by-step walkthrough

1. Set up Workspace Permissions

Before sharing a notebook, define who needs what level of access. Databricks provides several permission levels:

  • Can View: Good for stakeholders who only need to see results.
  • Can Run: For teammates who need to execute the logic but shouldn't change the code.
  • Can Edit: For active collaborators.
  • Can Manage: For leads who need to control permissions for others.

2. Use Databricks Repos for Git Integration

While Databricks has a built-in "Revision History," it is not a substitute for formal version control. Connect your Databricks Workspace to a Git provider (like GitHub, GitLab, or Azure DevOps).

  • Create a branch for your specific feature or bug fix.
  • Commit and push changes regularly.
  • Use Pull Requests (PRs) for code reviews before merging into the main branch.

3. Leverage Built-in Commenting

Instead of sending screenshots over Slack or Teams, use the built-in commenting feature in the notebook.

  • Highlight a specific line of code.
  • Click the comment icon on the right sidebar.
  • Use @mentions to notify a specific teammate. This keeps the conversation linked directly to the logic being discussed.

4. Manage Secrets Securely

Never hardcode passwords or access keys in a shared notebook. If a colleague clones your notebook, they shouldn't see your credentials. Use the Databricks Secret Utility.


# Best practice: Fetch credentials from a secret scope
# instead of typing them as plain text strings
database_password = dbutils.secrets.get(scope="finance_project", key="db_password")

# Use the variable in your connection string
connection_url = f"jdbc:mysql://server.address:3306/db?password={database_password}"

5. Modularize with %run or Python Files

To keep notebooks from becoming thousands of lines long, split logic into smaller, functional notebooks. You can call one notebook from another using the %run magic command. Even better, for complex logic, use shared Python files (.py) in your Repos that can be imported like standard libraries.

Common mistakes

  • Leaving "Dirty" Workspaces: Forgetting to delete temporary testing notebooks or leaving "Clone of Clone" files in shared folders.
  • Manual Versioning: Saving files as notebook_july_12.py instead of using Git branches.
  • Hardcoding Paths: Using absolute paths like /Users/your.name@company.com/data instead of shared mount points or Unity Catalog paths that everyone can access.
  • Ignoring Cluster Specs: Sharing a notebook that requires a high-memory cluster without notifying colleagues, leading to high costs or execution errors on smaller clusters.

One practice task

To practice these habits, perform the following sequence with a teammate:

  • Create a new notebook in a shared folder and connect it to a Git repository.
  • Write a simple PySpark transformation but leave one intentional logic error.
  • Use the Comments button to tag your teammate and ask them to fix the error.
  • Have your teammate fix the error, commit the change to a new branch, and show you the "Version History" to see how the changes were tracked.
