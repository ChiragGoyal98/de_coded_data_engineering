Databricks notebook collaboration best practices

Databricks notebooks are powerful tools for data engineering and data science, allowing multiple users to work on the same logic simultaneously. However, without a clear strategy, working together can quickly lead to messy code, lost progress, or conflicting changes. Learning how to collaborate effectively ensures that your team remains productive and that your codebase stays reliable as your project grows.

Why it matters

Collaboration in a data environment is about more than just sharing a screen. When teams follow established best practices, they avoid the "it works on my machine" syndrome. Proper collaboration ensures:

  • Version Control: You can track who changed what and revert to previous versions if something breaks.
  • Code Quality: Peer reviews and comments help catch bugs early before they reach production.
  • Security: Managing permissions prevents unauthorized users from modifying or deleting critical pipelines.
  • Reproducibility: Standardizing how notebooks are parameterized makes it easier for teammates to run your code with different inputs.

Step-by-step walkthrough

1. Integrate with Databricks Repos

The most important step for any team is moving away from standalone notebooks and using Databricks Repos. This feature allows you to sync your notebooks with a Git provider like GitHub, GitLab, or Azure DevOps.

  • Open the Repos tab in the sidebar.
  • Click Add Repo and link your Git provider.
  • Create branches for your individual features rather than working directly on the main branch. This prevents your "work in progress" from breaking the main codebase.

2. Use Markdown for Documentation

Notebooks shouldn't just be blocks of code. Use Markdown cells to explain the "why" behind your logic.

  • Use ## for section headers.
  • Use bullet points to list dependencies or data sources.
  • This helps a teammate understand your workflow without needing you to jump on a call to explain it.

3. Parameterize with Widgets

Instead of hardcoding values like dates or file paths, use Databricks Widgets. This allows your colleagues to change inputs through a user-friendly UI at the top of the notebook without touching the code.


# Create a text widget for a database name
dbutils.widgets.text("database_name", "default_db", "Target Database")

# Access the value in your code
target_db = dbutils.widgets.get("database_name")
print(f"Loading data into: {target_db}")

4. Manage Permissions

Collaboration requires the right level of access. Use the Share button at the top right of your notebook to manage permissions:

  • Can View: Good for stakeholders who only need to see results.
  • Can Run: For teammates who need to execute the logic but shouldn't change the code.
  • Can Edit: For active co-developers.
  • Can Manage: For leads who need to control sharing settings.

5. Utilize Comments for Peer Review

If you see a block of code that needs improvement, don't just change it. Highlight the code, right-click, and select Comment. This starts a thread where you can discuss changes with your teammate, much like a code review in a traditional software development environment.

Common mistakes

  • Hardcoding Secrets: Never type passwords or API keys directly into a notebook cell. Use Databricks Secrets to retrieve them securely.
  • Simultaneous Cell Editing: While Databricks allows multiple people to type in the same notebook, editing the exact same cell at the same moment can lead to sync conflicts. It is better to work on different cells.
  • Leaving Notebooks "Dirty": Always clear your cell outputs before committing to Git if they contain sensitive data or massive tables that make the file size unnecessarily large.
  • Ignoring the Revision History: If you aren't using Repos yet, remember that the Revision History button (the clock icon) can save you if a teammate accidentally deletes your work.

One practice task

To get comfortable with collaborative features, try this exercise with a teammate:

  • Create a new notebook and share it with your teammate giving them Can Edit permissions.
  • Create a text widget at the top of the notebook that asks for a "User Name."
  • Ask your teammate to leave a Comment on a specific line of code suggesting a change.
  • Open the Revision History and identify which changes were made by you and which were made by your teammate.
