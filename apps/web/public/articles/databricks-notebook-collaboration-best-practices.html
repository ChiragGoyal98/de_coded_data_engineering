Databricks notebook collaboration best practices

Working in a shared Databricks environment allows data teams to build complex pipelines quickly. However, because these notebooks are live and interactive, collaborating without a plan often leads to overwritten code, broken dependencies, or security leaks. Mastering collaboration is about balancing the speed of real-time editing with the safety of professional software development workflows.

Why it matters

Collaboration in Databricks is unique because it combines the live environment of a Google Doc with the execution power of a cluster. If your team does not follow best practices, you risk deleting hours of work with a single accidental cell execution. Good collaboration habits ensure that code is peer-reviewed, historical versions are preserved, and sensitive data remains protected. By standardizing how you share and edit, you turn a chaotic workspace into a reliable production engine.

Step-by-step walkthrough

1. Configure Workspace Permissions

The first step is controlling who can do what. Click the "Share" button at the top right of any notebook. Instead of giving everyone "Can Manage" access, follow the principle of least privilege:

  • Can View: Best for stakeholders who only need to see results.
  • Can Run: For users who need to execute the logic but shouldn't change it.
  • Can Edit: For active contributors.
  • Can Manage: Reserved for lead engineers who need to change permissions.

2. Set Up Databricks Git Folders

Relying on the "Revision History" is not enough for professional teams. Use Databricks Git Folders (formerly Repos) to connect your workspace to GitHub, GitLab, or Azure DevOps.

  • Create a new Git Folder in your user workspace.
  • Create a separate branch for every feature or bug fix.
  • Push your changes and use Pull Requests for peer review before merging into the main branch.

3. Use Widgets for Parameterization

When multiple people use the same notebook, they often need to point to different data paths or dates. Instead of hardcoding these values (which forces others to change your code), use Databricks Widgets. This allows users to input their own variables through a UI at the top of the notebook without modifying the logic.


# Create a text widget for a database name
dbutils.widgets.text("database_name", "default_db", "Enter Database Name")

# Access the value in your code
current_db = dbutils.widgets.get("database_name")
print(f"Querying data from: {current_db}")

4. Leverage Real-time Co-authoring and Comments

Databricks allows multiple users to be in the same notebook simultaneously. To collaborate effectively:

  • Look for the user icons in the top right to see who else is active.
  • Use the Comments feature (the speech bubble icon on the right sidebar) to leave feedback on specific lines of code rather than writing notes in Markdown cells that might be accidentally deleted.

Common mistakes

  • Editing the 'Main' Branch Directly: Always work in a personal branch. Making direct changes to the production branch in a Git Folder can lead to broken pipelines for the entire team.
  • Hardcoding Credentials: Never type passwords or API keys in a shared notebook. Use Databricks Secrets and dbutils.secrets.get() to keep your credentials hidden from collaborators.
  • Simultaneous Cell Editing: While Databricks supports co-authoring, having two people edit the exact same cell at the same time can cause sync issues. Communicate with your team about which section you are working on.
  • Ignoring Cluster Impact: Running a heavy notebook on a shared cluster can slow down your colleagues. Always check the cluster load before executing large data transformations.

Practice task

  • Create a new notebook in your personal folder.
  • Add a "Dropdown" widget that lets a user choose between 'Development' and 'Production'.
  • Use the dbutils.widgets.get() command to print a message based on the selection.
  • Share the notebook with a teammate and grant them "Can Run" permissions only.
  • Ask them to change the widget selection and run the notebook to verify they can interact with it without editing the code cells.
