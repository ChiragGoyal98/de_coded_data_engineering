Databricks notebook collaboration best practices

Databricks notebooks are powerful tools that let data engineers and scientists work together in real-time. Much like a shared document, multiple people can edit code simultaneously, which speeds up development but can also lead to confusion if not managed properly. Establishing a clear set of rules ensures that team members can contribute without stepping on each other's toes. By following collaborative best practices, teams can move from messy, experimental code to production-ready pipelines that are easy to maintain and audit.

Why it matters

Without a collaborative framework, working in Databricks can quickly become chaotic. When multiple engineers work on the same notebook, there is a high risk of overwriting critical logic or accidentally deleting someone else's progress.

Furthermore, "notebook sprawl" often occurs, where dozens of copies of the same notebook (e.g., analysis_v1, analysis_final_v2) clutter the workspace. This makes it nearly impossible to track which version is the "source of truth." Standardizing how you collaborate ensures code quality, improves security by managing permissions correctly, and makes it much easier to onboard new team members to a project.

Step-by-step walkthrough

1. Enable Databricks Repos (Git Integration)

The most important step for collaboration is moving away from standalone notebooks and using Databricks Repos. This allows you to sync your workspace with a Git provider like GitHub, GitLab, or Azure DevOps.

  • Open the "Repos" tab in the sidebar.
  • Link your Git provider via Personal Access Token (PAT).
  • Clone your team's repository.
  • Use branches! Never work directly on the main branch. Create a feature branch (e.g., dev-username-feature) so your changes stay isolated until they are reviewed.

2. Use Built-in Commenting

Databricks has a built-in commenting system similar to Google Docs. Instead of leaving "TODO" comments inside the code cells, highlight a piece of code and click the comment icon on the right side of the cell.

  • Use @mentions to notify specific team members.
  • Resolve comments once the feedback has been addressed to keep the workspace clean.

3. Organize with Markdown and Headings

Collaborative notebooks should be readable. Use Markdown cells to explain the "why" behind your code.

  • Use ## for section titles and ### for sub-sections.
  • Add a "Table of Contents" at the beginning of long notebooks.
  • Describe the expected input and output of the notebook in the first cell.

4. Parameterize with Widgets

Instead of hardcoding values like dates or file paths, use Databricks Widgets. This allows your teammates to run your notebook with their own parameters without changing your code.


# Create a text widget for a department name
dbutils.widgets.text("department", "Sales", "Enter Department")

# Access the value in your code
dept_name = dbutils.widgets.get("department")
print(f"Filtering data for: {dept_name}")

5. Manage Permissions

Not everyone needs "Can Manage" access. Follow the principle of least privilege:

  • Can View: For stakeholders who only need to see results.
  • Can Run: For testers who need to execute the logic but shouldn't change it.
  • Can Edit: For active contributors.
  • Can Manage: For project leads who manage permissions and Git settings.

Common mistakes

  • Hardcoding Secrets: Never type passwords or API keys directly into a notebook cell. Use Databricks Secrets and dbutils.secrets.get() so others can run your code safely.
  • Leaving Large Outputs: Large tables or charts saved in notebook cells can make the file size huge and slow down the UI for others. Clear your outputs before committing to Git.
  • Ignoring the Revision History: Databricks automatically saves versions. If you accidentally delete a cell, don't panic; click "Revision History" at the top right to restore a previous state.
  • Working in the "Shared" Folder: The "Shared" folder is often a dumping ground. Instead, use a structured folder hierarchy within a Repo to keep production code separate from experiments.

Practice task

To put these practices into action, try this exercise with a teammate:

  • Create a new notebook and add a Markdown cell at the top describing a fake data cleaning task.
  • Create a "Dropdown" widget that lets a user select a "Year" (e.g., 2022, 2023, 2024).
  • Use the dbutils.widgets.get() function to print a sentence using that year.
  • Share the notebook with your teammate and give them "Can Edit" permissions.
  • Ask your teammate to add a comment to your code cell using the @mention feature.
  • Practice "Resolving" the comment once you have seen it.
