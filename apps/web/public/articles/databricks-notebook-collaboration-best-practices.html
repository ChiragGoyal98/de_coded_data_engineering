Databricks notebook collaboration best practices

Databricks notebooks are more than just a place to write code; they are dynamic, shared environments where teams build data pipelines together. In a modern data engineering workflow, the ability to work on the same logic simultaneously is a game-changer. However, without a clear strategy, collaboration can quickly lead to messy code, deleted work, or logic conflicts. This guide explores how to use built-in Databricks features to ensure your team stays synchronized and productive.

Why it matters

Collaboration in data engineering isn't just about sharing a file. It is about maintaining a "single source of truth" for your data logic. When teams collaborate effectively:

  • Development cycles are shorter because multiple engineers can work on different cells of the same notebook.
  • Peer reviews happen in real-time through comments and version comparisons.
  • Knowledge silos are broken down, as team members can easily follow the logic and documentation left by others.
  • Errors are reduced by utilizing Git-backed version control rather than manual file exports.

Step-by-step walkthrough

1. Manage Workspace Permissions

The first step in collaboration is controlling who can do what. Databricks uses Access Control Lists (ACLs). To share a notebook, click the Share button at the top right.

  • Can View: Users can read the code and results but cannot run or change anything.
  • Can Run: Users can execute the notebook to see results but cannot modify the code.
  • Can Edit: Users can change code and run cells. This is standard for active collaborators.
  • Can Manage: Users can change permissions and delete the notebook. Limit this to lead engineers.

2. Use Real-Time Comments

Instead of sending screenshots in Slack or Teams, use the built-in commenting system.

  • Highlight a specific line of code.
  • Click the message icon that appears in the right margin.
  • Tag a teammate using the @ symbol to notify them. This keeps the conversation linked directly to the code logic.

3. Leverage Revision History

If a teammate accidentally deletes a cell or breaks a function, don't panic.

  • Click the Revision History (clock icon) in the right sidebar.
  • You can see a list of every save point, identified by the user who made the change.
  • You can compare two versions side-by-side or "Restore this version" to revert the notebook to a previous state.

4. Connect to Git with Databricks Repos

For professional teams, the standard practice is to use Databricks Repos. This allows you to sync your notebooks with GitHub, GitLab, or Azure DevOps.

  • Go to the Repos tab in the sidebar.
  • Add a new Repo and paste your Git URL.
  • This allows you to use branches. Each developer can work on their own branch and merge changes via a Pull Request, just like traditional software development.

5. Parameterize with Widgets

When sharing notebooks, avoid hardcoding values like dates or file paths. Use widgets so your teammates can run the notebook with their own inputs without changing your code.


# Create a text widget for a folder name
dbutils.widgets.text("folder_name", "raw_data", "Enter Folder Name")

# Access the value in your code
input_folder = dbutils.widgets.get("folder_name")

print(f"Loading data from: /mnt/storage/{input_folder}")

Common mistakes

  • Hardcoding User Paths: Avoid using paths like /Users/your_name/test_file.csv. Use shared locations or mount points so the code runs for everyone.
  • Simultaneous Cell Editing: While two people can edit the same notebook, editing the exact same cell at the same time can lead to "clobbering" (one person's changes overwriting the other).
  • Leaving Large Results: Large data frames or visualizations saved in the notebook can make it slow to load for others. Use display() thoughtfully or clear cell outputs before a major save.
  • Ignoring the "Trash" folder: Deleted notebooks are moved to a Trash folder in the Workspace. If you can't find a shared file, check there before assuming it is gone forever.

One practice task

To get comfortable with collaboration, perform the following exercise:

  • Create a new notebook and create a simple widget (like the code example above).
  • Click Share and grant "Can Edit" permissions to a teammate.
  • Ask your teammate to add a comment to your code using the @ mention feature.
  • Open the Revision History and identify the change made by your teammate, then try to "Restore" your original version.
