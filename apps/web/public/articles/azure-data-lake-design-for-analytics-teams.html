Azure Data Lake design for analytics teams

Introduction

Azure Data Lake Storage (ADLS) Gen2 is the backbone of modern data engineering on the Microsoft cloud. At its simplest level, a data lake is a centralized repository that allows you to store all your structured and unstructured data at any scale. Unlike traditional databases that require data to be formatted before it is stored, a data lake allows you to store data as-is and define the structure later when you are ready to analyze it. For analytics teams, ADLS Gen2 is unique because it combines the massive scalability of object storage with a hierarchical file system, making it easier to organize data into folders and manage security at a granular level.

Why it matters

A poorly designed data lake quickly turns into a data swamp. Without a clear organizational strategy, analytics teams spend 80% of their time searching for data rather than analyzing it. A structured design ensures that data is discoverable, secure, and cost-effective. Proper design also impacts performance; for example, how you partition your folders can significantly speed up your SQL queries or Spark jobs. By following best practices, you ensure that your data infrastructure can grow from a few gigabytes to several petabytes without needing a complete redesign.

Step-by-step walkthrough

1. Choose the Medallion Architecture

The most common way to organize a data lake is the Medallion (or multi-hop) architecture. This separates data into three distinct layers based on its quality and readiness for use:

  • Bronze (Raw): This is the landing zone. Store data exactly as it comes from the source (APIs, databases, logs). Never delete or modify files here; keep them in their original format (usually JSON or CSV).
  • Silver (Cleansed/Filtered): In this layer, you clean the data. This involves removing duplicates, fixing null values, and ensuring date formats are consistent. Data is typically converted to Parquet format here for better performance.
  • Gold (Curated): This is the business-ready layer. Data is aggregated and joined to answer specific business questions. This layer is what the data analysts and Power BI reports will connect to.

2. Implement a Logical Folder Structure

Within each layer, you should follow a consistent naming convention. A standard approach is:

Layer / SourceSystem / Entity / Year / Month / Day /

For example:

Bronze / SalesApp / Orders / 2023 / 10 / 24 /

This structure allows tools like Azure Synapse or Databricks to "prune" partitions, meaning they only read the specific folders needed for a query, saving both time and money.

3. Select the Right File Formats

While the Bronze layer keeps data in its native format, the Silver and Gold layers should almost always use Apache Parquet. Parquet is a columnar storage format that is highly compressed and optimized for analytical queries. It allows the system to read only the columns required for a specific calculation rather than the entire row.

4. Manage Security with ACLs

Security in ADLS Gen2 is handled in two ways:

  • RBAC (Role-Based Access Control): Used for broad permissions (e.g., "This person is a Storage Blob Data Contributor").
  • ACLs (Access Control Lists): Used for fine-grained permissions. You can give a specific team access to only the Gold / Finance folder without letting them see the Bronze raw data.

5. Writing Data to the Lake

When moving data from Silver to Gold, you will often use Python or Spark. Below is a short example of how to write a cleaned DataFrame to a specific folder in your Data Lake using PySpark:


# Saving a cleaned sales report to the Gold layer in Parquet format
gold_path = "abfss://gold@mystorageaccount.dfs.core.windows.net/finance/daily_sales/"

df_cleaned.write \
    .mode("overwrite") \
    .partitionBy("year", "month") \
    .parquet(gold_path)

Common mistakes

  • The "Everything" Root Folder: Putting thousands of files in a single root folder. This causes "throttling" and makes it impossible for tools to list files efficiently.
  • Ignoring Lifecycle Management: Data lakes can grow expensive. Failing to set up "Lifecycle Management" policies to move old, unused data to "Cool" or "Archive" storage tiers is a common budget killer.
  • Manual Permissions: Assigning permissions to individual users. Always use Azure Active Directory (Microsoft Entra ID) groups. If a team member leaves, you just remove them from the group rather than updating dozens of folder permissions.
  • Small File Problem: Storing thousands of tiny 1KB files. Big data engines prefer fewer, larger files (ideally 256MB to 1GB) for optimal processing.

One practice task

Create a conceptual folder map for a "Customer Experience" project. Imagine you have two data sources: a Website Log (JSON) and a CRM Database (CSV).

  • List the folders you would create in the Bronze layer to store the daily raw files.
  • Decide which columns you would use for partitioning in the Silver layer.
  • Define who should have access to the Gold layer vs. the Bronze layer.

By mapping this out on paper or a whiteboard, you'll start to see how data flows from a messy "raw" state to a polished "analytical" state.
