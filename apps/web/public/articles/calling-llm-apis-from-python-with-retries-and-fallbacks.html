Calling LLM APIs from Python with retries and fallbacks

When building applications powered by Large Language Models, developers often rely on external APIs like those provided by OpenAI, Anthropic, or Google. While these services are powerful, they are not perfect. Network glitches, rate limits, and server overloads can cause your application to crash if you do not handle errors properly. Learning how to build resilient systems ensures that your AI features remain stable even when the underlying service experiences a hiccup.

Why it matters

Reliability is the difference between a prototype and a production-ready application. LLM APIs are prone to specific types of failures that differ from traditional databases.

  • Rate Limiting: Most providers restrict how many requests you can send per minute. If you exceed this, the API will reject your calls.
  • Transient Errors: Sometimes a server is simply busy or a packet gets lost. These are temporary and usually resolve themselves if you try again a second later.
  • Model Downtime: Even the biggest providers experience outages. Having a fallback (a secondary model) ensures your app keeps working even if your primary model is offline.
  • Cost and Latency: Without a retry strategy, a failed request might result in a "dead end" for your user, forcing them to manual refresh and causing frustration.

Step-by-step walkthrough

1. Setting up the environment

To handle retries gracefully in Python, the community standard is a library called tenacity. It allows you to add retry logic to any function using simple "decorators." You will also need your LLM library of choice (we will use openai for this example).


pip install openai tenacity

2. Implementing Retries with Exponential Backoff

An "Exponential Backoff" strategy means that if a request fails, the code waits a short time before trying again. If it fails a second time, it waits even longer. This prevents you from "spamming" an already overloaded server.

3. Adding a Fallback Mechanism

A fallback is your "Plan B." If the primary model (e.g., GPT-4o) fails repeatedly, the code should automatically switch to a cheaper or more stable model (e.g., GPT-4o-mini) to fulfill the request.

Code Example: Resilient LLM Call


import openai
from tenacity import retry, stop_after_attempt, wait_exponential, retry_if_exception_type

client = openai.OpenAI(api_key="your_api_key")

# We only want to retry on specific errors like Rate Limits or Server Errors
@retry(
    retry=retry_if_exception_type((openai.RateLimitError, openai.APIConnectionError)),
    wait=wait_exponential(multiplier=1, min=4, max=10),
    stop=stop_after_attempt(3)
)
def call_llm(model_name, prompt):
    print(f"Attempting request with {model_name}...")
    response = client.chat.completions.create(
        model=model_name,
        messages=[{"role": "user", "content": prompt}]
    )
    return response.choices[0].message.content

def safe_llm_request(prompt):
    try:
        # Plan A: High-performance model
        return call_llm("gpt-4o", prompt)
    except Exception as e:
        print(f"Primary model failed: {e}. Switching to Fallback...")
        # Plan B: Fast, reliable fallback model
        return call_llm("gpt-4o-mini", prompt)

# Usage
result = safe_llm_request("Write a poem about Python programming.")
print(result)

Common mistakes

  • Retrying on Logic Errors: Do not retry if the error is a "401 Unauthorized" or "400 Bad Request." If your API key is wrong or your prompt is formatted incorrectly, retrying 100 times will not fix it.
  • Infinite Loops: Always set a stop_after_attempt limit. Without it, a permanent outage could cause your script to run forever, potentially racking up costs or hung processes.
  • Ignoring Logs: If your fallback kicks in, you need to know about it. Always log when a retry or fallback occurs so you can investigate if your primary service is becoming unstable.

One practice task

Modify the code example provided above to include a third "Plan C." If both the primary and fallback models fail, make the function return a pre-written "hardcoded" response (e.g., "I'm sorry, I'm having trouble connecting to my brain right now. Please try again later.") instead of crashing the program.
