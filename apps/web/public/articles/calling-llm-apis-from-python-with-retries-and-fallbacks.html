Calling LLM APIs from Python with retries and fallbacks

Integrating Large Language Model (LLM) APIs into your Python applications is an exciting step toward building intelligent tools. However, unlike traditional local functions, API calls are prone to external failures. You might encounter rate limits, temporary server outages, or network hiccups that can cause your script to crash. To build a production-ready application, you need to handle these interruptions gracefully.

Why it matters

Building robustness into your LLM calls is essential for several reasons:

  • Reliability: APIs frequently return errors like 429 (Too Many Requests) or 503 (Service Unavailable). Without handling these, your application will stop working.
  • User Experience: A brief network flicker shouldn't force a user to restart their entire workflow.
  • Cost and Efficiency: If a script fails halfway through a long sequence of tasks, you may lose progress while still having paid for the tokens used in previous steps.
  • Redundancy: Fallbacks allow you to switch to a cheaper or faster model if your primary model is down, ensuring your service stays online.

Step-by-step walkthrough

1. Setting up the environment

Before writing logic, you need a way to manage retries. While you could write your own loops, the Python library tenacity is the industry standard for this task. You will also need your preferred LLM library, such as openai.


pip install openai tenacity

2. Implementing Retries

A retry strategy tells your code to try the operation again if it fails. The most effective method is "Exponential Backoff," where the wait time increases between each attempt. This prevents you from overwhelming the API provider further.

3. Adding Fallbacks

A fallback is your "Plan B." If a specific model (like GPT-4o) is currently overloaded or failing, your code can catch that error and try the request again using a different model (like GPT-3.5 or a local Llama model).

4. Combining both strategies

The following example demonstrates how to use the @retry decorator from tenacity to handle rate limits and a standard try-except block to handle a fallback model.


import openai
from tenacity import retry, wait_random_exponential, stop_after_attempt

client = openai.OpenAI(api_key="your_api_key")

@retry(wait=wait_random_exponential(min=1, max=60), stop=stop_after_attempt(3))
def call_llm_with_retry(model, prompt):
    # This function will automatically retry up to 3 times with increasing delays
    return client.chat.completions.create(
        model=model,
        messages=[{"role": "user", "content": prompt}]
    )

def smart_llm_call(prompt):
    try:
        # Attempt the primary, high-quality model
        return call_llm_with_retry("gpt-4o", prompt)
    except Exception as e:
        print(f"Primary model failed: {e}. Switching to fallback...")
        # Fallback to a faster, more available model
        return call_llm_with_retry("gpt-3.5-turbo", prompt)

Common mistakes

  • Retrying on every error: Do not retry if the error is a "401 Unauthorized" or "400 Bad Request." These are client-side errors that will never succeed no matter how many times you try. Only retry on 429 (rate limits) or 5xx (server errors).
  • Infinite loops: Always set a stop_after_attempt or a timeout. Otherwise, if the API provider has a major outage, your script will run forever and potentially rack up unexpected compute costs.
  • Ignoring logs: When a fallback occurs, make sure to log it. If you don't, you might not realize your application is running on a lower-quality model for days.
  • Hardcoding API keys: Never hardcode your keys in the script. Use environment variables or a .env file to keep them secure.

One practice task

Create a script that attempts to summarize a paragraph of text. Implement a retry strategy that waits 2 seconds between attempts and stops after 5 tries. If all retries fail, the script should print "Summary unavailable at this time" instead of crashing with a traceback error.
