Calling LLM APIs from Python with retries and fallbacks

Building applications that rely on Large Language Models (LLMs) requires a different mindset than traditional software development. When you call a standard database or a local function, you expect a near-instant and reliable response. However, LLM APIs like OpenAI, Anthropic, or Google Gemini are remote services subject to network instability, strict rate limits, and occasional downtime. If your code isn't prepared for these hiccups, your application will crash or hang, leading to a poor user experience.

Why it matters

Reliability is the backbone of any production-grade AI application. Without a strategy for handling errors, your program is fragile. There are three main reasons why retries and fallbacks are essential:

  • Rate Limiting: Most providers limit how many requests you can send per minute. If you exceed this, the API will reject your request.
  • Transient Errors: Sometimes a server is simply overwhelmed for a fraction of a second. A quick retry often fixes the issue.
  • Cost and Availability: If a high-end model like GPT-4 is down or too slow, falling back to a faster, cheaper model like GPT-4o-mini ensures your app stays functional.

Step-by-step walkthrough

To handle these issues gracefully, we use two main patterns: Retries (trying the same thing again after a short wait) and Fallbacks (trying a different model or method if the first one fails).

1. Setting up your environment

You will need the openai library and a library called tenacity, which is the industry standard for adding retry logic to Python functions.


pip install openai tenacity

2. Implementing Retries

The tenacity library uses "decorators" to wrap your functions. You can tell it how many times to retry and how long to wait between attempts. We use "exponential backoff," which means the wait time increases after every failure (e.g., wait 1s, then 2s, then 4s) to avoid spamming the API.

3. Adding a Fallback

A fallback is your "Plan B." If the primary model fails even after multiple retries, you catch the error and route the request to a different model.

Code Example: Secure API Calling


import openai
from tenacity import retry, stop_after_attempt, wait_exponential

client = openai.OpenAI(api_key="your_api_key_here")

# This decorator tells Python to retry up to 3 times
# It waits 1 second, then 2, then 4 between tries
@retry(wait=wait_exponential(multiplier=1, min=4, max=10), stop=stop_after_attempt(3))
def call_primary_model(prompt):
    print("Attempting to call GPT-4o...")
    return client.chat.completions.create(
        model="gpt-4o",
        messages=[{"role": "user", "content": prompt}]
    )

def smart_llm_call(prompt):
    try:
        # Try the main model first with retries
        return call_primary_model(prompt)
    except Exception as e:
        print(f"Primary model failed: {e}. Switching to fallback...")
        # Fallback to a cheaper/faster model
        return client.chat.completions.create(
            model="gpt-4o-mini",
            messages=[{"role": "user", "content": prompt}]
        )

# Usage
response = smart_llm_call("Explain quantum physics in one sentence.")
print(response.choices[0].message.content)

Common mistakes

  • Retrying on the wrong errors: Do not retry if the error is "Invalid API Key" or "Context Length Exceeded." Those won't fix themselves with a retry. Only retry on network timeouts or 500-level server errors.
  • Fixed wait times: If a server is overloaded and 100 users all retry at exactly 1 second, the server will crash again. Always use exponential backoff with a bit of "jitter" (randomness).
  • Forgetting the user: If a request takes too long because of multiple retries, your user might think the app is frozen. Always provide a loading state in your UI.

One practice task

Modify the code example above to include a third "Final Fallback." If even the GPT-4o-mini model fails, the function should return a hardcoded string like: "I'm sorry, I'm having trouble connecting to my brain right now. Please try again later." This ensures the code never crashes the entire program.
