Calling LLM APIs from Python with retries and fallbacks

Interacting with Large Language Models (LLMs) through APIs is the foundation of modern AI applications. However, these services are not always available or consistent. Network glitches, rate limits, and server overloads can cause your Python scripts to crash if they are not built to handle errors gracefully. Learning how to implement retries and fallbacks ensures your application remains robust even when an API provider experiences downtime.

Why it matters

When you call an LLM API, you are making a request over the internet to a remote server. This process is prone to several points of failure:

  • Rate Limiting: Providers like OpenAI or Anthropic limit how many requests you can send per minute. Once reached, they return a 429 error.
  • Server Overload: High-demand periods can cause 503 errors, meaning the model is too busy to respond.
  • Network Timeouts: Your local internet connection or the provider's routing might drop the connection.

Without retry logic, your program stops immediately upon hitting an error. Without a fallback, your application goes offline if a specific model provider has a major outage. Using these patterns makes your code production-ready.

Step-by-step walkthrough

1. Handling Retries with Tenacity

The most efficient way to handle retries in Python is using the tenacity library. It allows you to wrap your API calls in a "decorator" that automatically attempts the call again if it fails.

First, install the necessary libraries:

pip install openai tenacity

2. Implementing Exponential Backoff

You shouldn't retry a failed request immediately. If the server is overloaded, hitting it again one millisecond later only makes the problem worse. Instead, use "exponential backoff," which increases the wait time between each attempt.

3. Setting Up a Fallback Model

A fallback is a backup plan. If your primary model (e.g., GPT-4) is unavailable after several retries, the code should automatically switch to a different model or provider (e.g., GPT-3.5 or a local model) to ensure the user still gets a response.

Code Example

The following script demonstrates how to retry a call up to three times and then switch to a secondary model if the primary one fails.


import openai
from tenacity import retry, stop_after_attempt, wait_random_exponential, retry_if_exception_type

client = openai.OpenAI(api_key="YOUR_API_KEY")

# Retry logic: Wait 1-20s between retries, stop after 3 attempts
@retry(wait=wait_random_exponential(min=1, max=20), stop=stop_after_attempt(3))
def call_llm(model_name, prompt):
    print(f"Attempting call with {model_name}...")
    response = client.chat.completions.create(
        model=model_name,
        messages=[{"role": "user", "content": prompt}]
    )
    return response.choices[0].message.content

def safe_llm_call(prompt):
    try:
        # Primary attempt
        return call_llm("gpt-4", prompt)
    except Exception as e:
        print(f"GPT-4 failed: {e}. Switching to fallback.")
        # Fallback attempt
        return call_llm("gpt-3.5-turbo", prompt)

# Usage
result = safe_llm_call("Explain quantum physics in one sentence.")
print(result)

Common mistakes

  • Retrying on Authentication Errors: Do not retry if the error is a 401 (Unauthorized). If your API key is wrong, retrying 10 times will not fix it; it will only get your IP temporarily blocked.
  • Infinite Loops: Always set a stop_after_attempt limit. Retrying forever can lead to massive API bills if your code gets stuck in a loop during a provider outage.
  • Ignoring Logs: If a fallback is triggered, you need to know about it. Always log or print when a primary model fails so you can investigate the cause later.
  • Not defining specific exceptions: It is better to retry only on specific errors (like RateLimitError) rather than all exceptions, to avoid masking bugs in your own code.

One practice task

Modify the code example provided above to include a third fallback. If both "gpt-4" and "gpt-3.5-turbo" fail, the function should return a pre-written string: "The AI service is currently unavailable. Please try again later." This ensures that even if the entire API provider is down, your code returns a clean message instead of a messy error trace.
