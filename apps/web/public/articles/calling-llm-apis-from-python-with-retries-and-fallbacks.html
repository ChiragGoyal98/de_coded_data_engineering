Calling LLM APIs from Python with retries and fallbacks

When building applications with Large Language Models (LLMs), you quickly realize that the internet and remote servers are not always reliable. Sometimes an API server is busy, your internet connection hiccups, or you hit a rate limit. If your Python script simply crashes every time one of these issues occurs, your application will frustrate users and fail in production. Learning how to handle these interruptions gracefully is a fundamental skill for any developer working in the AI space.

Why it matters

Reliability is the difference between a hobby project and a professional tool. LLM APIs often experience "transient errors"-temporary glitches that resolve themselves within seconds. If you don't have a retry mechanism, a single 503 Service Unavailable error will terminate your entire process.

Furthermore, rate limits are a reality of using paid APIs. Instead of failing immediately when you hit a limit, a "retry with exponential backoff" strategy allows your code to wait a few seconds and try again. Fallbacks provide an extra layer of safety; if your primary, high-performance model (like GPT-4) is down, your code can automatically switch to a faster, cheaper, or secondary model (like GPT-3.5 or Claude) to keep the service running.

Step-by-step walkthrough

To handle these issues in Python, we typically use a library called tenacity for retries and standard try-except blocks for fallbacks.

1. Setting up Retries

The most common way to handle retries is "Exponential Backoff." This means that if a request fails, the script waits 1 second, then 2 seconds, then 4 seconds, and so on. This prevents you from "spamming" an already struggling server.

2. Implementing the Code

In the example below, we use the tenacity library to decorate our API call function. We tell it to retry only on specific errors and to stop after a certain number of attempts.


import openai
from tenacity import retry, wait_exponential, stop_after_attempt, retry_if_exception_type

# Define which errors should trigger a retry
@retry(
    wait=wait_exponential(multiplier=1, min=2, max=10),
    stop=stop_after_attempt(3),
    retry=retry_if_exception_type(openai.RateLimitError)
)
def call_llm(model_name, prompt):
    client = openai.OpenAI(api_key="your_api_key")
    response = client.chat.completions.create(
        model=model_name,
        messages=[{"role": "user", "content": prompt}]
    )
    return response.choices[0].message.content

def get_completion_with_fallback(prompt):
    try:
        # Primary attempt with the "best" model
        return call_llm("gpt-4", prompt)
    except Exception as e:
        print(f"Primary model failed: {e}. Switching to fallback...")
        # Fallback attempt with a secondary model
        return call_llm("gpt-3.5-turbo", prompt)

3. Handling Fallbacks

In the code above, the get_completion_with_fallback function acts as a safety net. If call_llm fails three times (as defined by the decorator), it raises an exception. The try-except block catches that exception and tries the call again using a different, often more available model.

Common mistakes

  • Retrying on logic errors: Do not retry if the error is a BadRequestError (e.g., your prompt is too long). This is an error in your code or data, and retrying 100 times will not fix it.
  • Infinite loops: Always set a stop_after_attempt limit. Without it, your code might run forever, consuming resources and potentially costing you money.
  • Ignoring specific status codes: Not all errors are created equal. You should retry on "Rate Limit" (429) and "Server Error" (5xx), but never on "Unauthorized" (401), which usually means your API key is wrong.
  • Hardcoding API keys: Beginners often leave their API keys inside the script. Always use environment variables or a .env file to keep your credentials safe while testing your retry logic.

One practice task

Create a Python script that simulates an API call using the random library. Write a function that has a 50% chance of "failing" (raising an error). Use the tenacity library to ensure that the function eventually succeeds by retrying up to 5 times. Once you have that working, wrap it in a fallback that prints "Emergency Fallback Triggered" if all 5 attempts fail.
