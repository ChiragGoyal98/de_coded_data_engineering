Calling LLM APIs from Python with retries and fallbacks

When building applications powered by Large Language Models (LLMs), connecting to an API is just the first step. In a perfect world, every request would return a successful response instantly. However, real-world networks are unpredictable, and API providers often impose rate limits or experience brief outages. To build a production-ready application, you need to handle these interruptions gracefully using two key strategies: retries and fallbacks.

Why it matters

API calls can fail for many reasons that have nothing to do with your code. You might hit a Rate Limit (HTTP 429) because you sent too many requests at once, or the provider might experience a "500 Internal Server Error" due to high traffic.

If your code simply crashes when this happens, the user experience suffers. Implementing retries allows your code to automatically try again after a short pause, which often fixes issues caused by temporary glitches. Fallbacks go a step further; if your primary model (like GPT-4) is completely unavailable, your code can automatically switch to a secondary model (like Claude or a smaller local model) to ensure the application keeps running.

Step-by-step walkthrough

1. Handling Retries with Tenacity

The most efficient way to handle retries in Python is using a library called tenacity. It allows you to define rules for when and how many times a function should be retried.

A common pattern is "Exponential Backoff." This means the script waits a little longer after each failure (e.g., 1s, 2s, 4s) to avoid overwhelming the API server further.


import openai
from tenacity import retry, stop_after_attempt, wait_exponential

client = openai.OpenAI(api_key="your_key")

@retry(wait=wait_exponential(multiplier=1, min=2, max=10), stop=stop_after_attempt(3))
def call_llm_with_retry(prompt):
    return client.chat.completions.create(
        model="gpt-3.5-turbo",
        messages=[{"role": "user", "content": prompt}]
    )

2. Implementing Fallbacks

A fallback is your "Plan B." You wrap your primary logic in a try-except block. If the primary API fails after all retry attempts, the code moves to the except block to call a different model.


def robust_llm_call(prompt):
    try:
        # Attempt primary model with retries
        return call_llm_with_retry(prompt)
    except Exception as e:
        print(f"Primary model failed: {e}. Switching to fallback...")
        # Attempt fallback model (e.g., a faster/cheaper model)
        return client.chat.completions.create(
            model="gpt-3.5-turbo-0125",
            messages=[{"role": "user", "content": prompt}]
        )

Common mistakes

  • Infinite Retries: Never set your code to retry indefinitely. If the API is down for an hour, your program will hang and potentially rack up high compute costs. Always set a stop_after_attempt limit.
  • Ignoring Error Types: Not all errors should trigger a retry. If you have an "Authentication Error" (invalid API key), retrying 10 times won't fix it. Only retry on network timeouts or rate limits.
  • Missing Timeouts: By default, some requests might wait forever for a response. Always set a timeout parameter in your API call so the code knows when to give up and try again.
  • Hard-coding Keys: Never put your API keys directly in the script. Use environment variables or a .env file to keep your credentials secure.

One practice task

Create a Python script that attempts to summarize a short paragraph using a "Primary" function.

  • Use the tenacity library to retry the call 3 times if it fails.
  • If it still fails after 3 attempts, write a fallback block that returns a pre-written string: "Error: Service currently unavailable. Please try again later." instead of letting the program crash.
