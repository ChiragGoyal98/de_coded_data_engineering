Calling LLM APIs from Python with retries and fallbacks

When building applications powered by Large Language Models (LLMs), developers quickly realize that these services are not always 100% reliable. Unlike traditional database queries that complete in milliseconds, LLM requests are heavy, prone to network timeouts, and strictly rate-limited. To build a production-ready application, you need to handle these interruptions gracefully. This guide will show you how to implement two essential stability patterns: retries (trying again) and fallbacks (having a Plan B).

Why it matters

If your application relies on a single API call without any safety nets, it becomes fragile. If the provider experiences a "500 Internal Server Error" or if you hit a rate limit during a period of high traffic, your entire feature breaks for the user.

By implementing retries, you allow the system to recover from "transient" errors-short-lived glitches that resolve themselves in a few seconds. By implementing fallbacks, you ensure that even if a specific model (like GPT-4o) is down or too busy, your application can switch to a different model (like Claude 3 Haiku or a smaller local model) to keep the service running.

Step-by-step walkthrough

1. Handling Retries with Tenacity

While you could write your own while loops to retry failed requests, the Python community generally uses a library called tenacity. It allows you to define exactly how many times to retry and how long to wait between attempts.

First, install the necessary libraries:

pip install openai tenacity

Here is how to wrap an LLM call with an exponential backoff strategy, which waits longer between each subsequent attempt to avoid hammering the server:


from openai import OpenAI
from tenacity import retry, stop_after_attempt, wait_exponential

client = OpenAI()

@retry(wait=wait_exponential(multiplier=1, min=4, max=10), stop=stop_after_attempt(3))
def call_llm_with_retry(prompt):
    return client.chat.completions.create(
        model="gpt-4o",
        messages=[{"role": "user", "content": prompt}]
    )

2. Implementing Fallbacks

A fallback is a secondary plan used when the primary method fails even after retries. This usually involves switching to a different model provider or a cheaper, faster model.


def get_completion(prompt):
    try:
        # Attempt the primary, high-quality model
        return client.chat.completions.create(
            model="gpt-4o",
            messages=[{"role": "user", "content": prompt}]
        )
    except Exception as e:
        print(f"Primary model failed: {e}. Switching to fallback...")
        # Fallback to a different model
        return client.chat.completions.create(
            model="gpt-3.5-turbo",
            messages=[{"role": "user", "content": prompt}]
        )

3. Combining Both

In a real-world scenario, you want to combine these. You retry the primary model a few times; if it still fails, you move to the fallback model.

Common mistakes

  • Retrying on every error: You should only retry on errors that might actually succeed the second time (like 429 Rate Limit or 500 Server Error). Retrying a 401 Unauthorized error is pointless because the API key won't magically become valid.
  • Immediate retries: If you hit a rate limit and retry instantly, you will likely hit it again. Always use "exponential backoff" to give the server breathing room.
  • Infinite loops: Never set retries to infinite. If the service is truly down, your code will hang forever and rack up a massive queue of processes.
  • Ignoring costs: If your fallback model is significantly more expensive than your primary model, a long outage could result in an unexpected bill.
