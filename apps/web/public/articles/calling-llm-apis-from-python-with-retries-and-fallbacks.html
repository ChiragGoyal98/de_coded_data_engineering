Calling LLM APIs from Python with retries and fallbacks

Interacting with Large Language Model (LLM) APIs is a core skill for modern developers. However, unlike local functions, API calls are prone to external issues like network timeouts, temporary server outages, or rate limiting. If your code isn't prepared to handle these hiccups, your entire application could crash just because a server was busy for a split second. To build professional-grade applications, you need to implement strategies that allow your code to try again or switch to a backup plan automatically.

Why it matters

When you send a request to a provider like OpenAI, Anthropic, or Google, several things can go wrong:

  • Rate Limiting: You have sent too many requests in a short period.
  • Server Overload: The provider is currently handling too much traffic.
  • Network Glitches: A temporary lapse in your internet connection.

Without retries, your user sees an error message and the process stops. Without fallbacks, if a specific model (like GPT-4o) is having a major outage, your app becomes useless. Implementing these patterns ensures "high availability," meaning your app stays functional even when the primary service provider is struggling.

Step-by-step walkthrough

To handle these issues gracefully in Python, we often use a library called tenacity for retrying and simple try-except blocks for fallbacks.

1. Setting up Retries

A retry strategy tells your code: "If this fails with a specific error, wait a moment and try again." We use Exponential Backoff, which means we wait longer between each subsequent attempt (e.g., 1s, 2s, 4s) to avoid spamming a struggling server.

2. Setting up Fallbacks

A fallback is your "Plan B." If your primary model fails after all retry attempts, the code catches the error and switches to a different model-perhaps a cheaper or faster one-to ensure the user still gets a response.

3. Integrated Code Example

The following example uses the openai library and tenacity to create a robust calling function.


import openai
from tenacity import retry, stop_after_attempt, wait_random_exponential, retry_if_exception_type

# Define which errors are worth retrying (e.g., Rate Limits or Server Errors)
@retry(
    retry=retry_if_exception_type((openai.RateLimitError, openai.APIConnectionError)),
    wait=wait_random_exponential(min=1, max=60),
    stop=stop_after_attempt(3)
)
def call_primary_llm(prompt):
    client = openai.OpenAI(api_key="YOUR_API_KEY")
    return client.chat.completions.create(
        model="gpt-4",
        messages=[{"role": "user", "content": prompt}]
    )

def robust_llm_call(prompt):
    try:
        # Attempt the primary model with retries
        return call_primary_llm(prompt)
    except Exception as e:
        print(f"Primary failed after retries: {e}. Switching to fallback...")
        # Fallback to a different model (Plan B)
        client = openai.OpenAI(api_key="YOUR_API_KEY")
        return client.chat.completions.create(
            model="gpt-3.5-turbo",
            messages=[{"role": "user", "content": prompt}]
        )

Common mistakes

  • Retrying on "User Errors": Never retry a 401 Unauthorized (wrong API key) or 400 Bad Request (wrong syntax). These will never succeed no matter how many times you try; you are just wasting time and tokens.
  • Infinite Loops: Always set a stop_after_attempt limit. Without it, a permanent outage could cause your script to run forever, potentially racking up costs or freezing your system.
  • Silent Failures: If the fallback also fails, ensure you log the error or notify the user. Don't let the application crash without an explanation.
  • Ignoring Latency: Every retry adds seconds to the user's wait time. Balance your "stop" limit with the user experience you want to provide.

One practice task

The "Safety Net" Challenge:

Modify the code example above to include a "hard-coded" fallback. If both GPT-4 and GPT-3.5 fail (perhaps due to a total internet outage), the function should return a pre-written string: "I'm currently having trouble connecting to my brain. Please try again in a few minutes!" This ensures the application always returns a string instead of crashing with a traceback.
