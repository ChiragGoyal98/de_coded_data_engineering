Calling LLM APIs from Python with retries and fallbacks

Category: LLM APIs

When building an application powered by a Large Language Model (LLM), you eventually need to move beyond simple chat interfaces and connect directly to an API. While sending a request and receiving a response seems simple, the internet and remote servers are unpredictable. Network blips, rate limits, or server downtime can break your application if you do not handle these interruptions gracefully. Learning how to build robust communication layers is a foundational skill for any AI developer.

Why it matters

Reliability is the difference between a prototype and a production-ready application. LLM APIs are prone to specific types of failure that standard web APIs might not experience as frequently:

  • Rate Limiting: Most providers restrict how many tokens or requests you can send per minute. If you exceed this, the API will reject your request.
  • Timeouts: LLMs generate text token by token, which can take a long time. If the server is busy, the connection might drop.
  • Model Downtime: Even the biggest providers experience outages. If your app relies on a single model, an outage means your service is completely offline.

By implementing retries and fallbacks, you ensure that temporary glitches are handled automatically and that your users experience minimal disruption.

Step-by-step walkthrough

To handle these issues efficiently in Python, we use a library called tenacity for retries and standard try-except blocks for fallbacks.

1. Setting up the environment

First, you need to install the necessary libraries. We will use the OpenAI library as our primary example.


pip install openai tenacity

2. Implementing Retries with Tenacity

Retrying a request shouldn't happen instantly. If a server is overloaded, hitting it again immediately will only make the problem worse. We use "exponential backoff," which means we wait longer between each successive attempt.


from openai import OpenAI
from tenacity import retry, stop_after_attempt, wait_random_exponential

client = OpenAI()

@retry(wait=wait_random_exponential(min=1, max=60), stop=stop_after_attempt(3))
def call_llm_with_retry(prompt):
    return client.chat.completions.create(
        model="gpt-4o",
        messages=[{"role": "user", "content": prompt}]
    )

In this code:

  • wait_random_exponential prevents "thundering herd" problems by adding a bit of randomness to the wait time.
  • stop_after_attempt(3) ensures we don't loop forever if the service is truly dead.

3. Adding Fallbacks

A fallback is your "Plan B." If GPT-4 is failing even after three retries, you might want to try a faster, cheaper, or different model to ensure the user gets some kind of result.


def robust_llm_call(prompt):
    try:
        # Attempt the primary model with retries
        return call_llm_with_retry(prompt)
    except Exception as e:
        print(f"Primary model failed: {e}. Switching to fallback.")
        # Plan B: Use a different model or a canned response
        return client.chat.completions.create(
            model="gpt-3.5-turbo",
            messages=[{"role": "user", "content": prompt}]
        )

Common mistakes

  • Retrying on 401 Errors: Don't retry if the error is "Unauthorized." If your API key is wrong, retrying 10 times won't fix it; it will only waste time.
  • Infinite Loops: Always set a stop condition in your retry logic.
  • Ignoring Costs: If you are retrying heavy requests, remember that each successful attempt costs money. Monitor your usage to ensure a bug in your retry loop isn't draining your credits.
  • Not Logging: When a fallback is triggered, you should log it. If you don't, you might never realize your primary model is failing 50% of the time.

One practice task

Create a Python script that attempts to call an LLM API. Implement a retry strategy that attempts the call 5 times. If all 5 attempts fail, instead of crashing the program, have it return a string that says: "The AI is currently resting. Please try again later." This teaches you how to provide a graceful "fail-soft" experience for your users.
