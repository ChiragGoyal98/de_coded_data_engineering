Calling LLM APIs from Python with retries and fallbacks

Working with Large Language Models (LLMs) like GPT-4 or Claude via their APIs is a core skill for modern developers. However, unlike traditional databases, external APIs live on the open internet and are subject to rate limits, network hiccups, and temporary outages. If your Python script simply sends a request and expects a 100% success rate, your application will eventually crash. Building robust applications requires a strategy to handle these inevitable failures gracefully.

Why it matters

In a production environment, reliability is just as important as the quality of the LLM's output. If you are building a chatbot or an automated report generator, a single "429 Too Many Requests" error shouldn't stop the entire process.

Implementing retries allows your code to wait a few seconds and try again when the server is busy. Fallbacks take this a step further by providing a "Plan B"-such as switching to a smaller, cheaper model or a different provider entirely-if the primary model remains unavailable. Together, these techniques ensure your application remains functional even when the primary API provider experiences turbulence.

Step-by-step walkthrough

To implement these patterns effectively, we will use the openai library for the API calls and a popular library called tenacity to manage the retry logic.

1. Setting up the environment

First, ensure you have the necessary libraries installed in your Python environment:


pip install openai tenacity

2. Implementing Retries with Exponential Backoff

The most effective way to retry is "exponential backoff." This means instead of retrying every 1 second, you double the wait time between each attempt (1s, 2s, 4s...). This prevents you from spamming the API and getting blocked further.


from openai import OpenAI
from tenacity import retry, stop_after_attempt, wait_random_exponential

client = OpenAI(api_key="your_api_key_here")

@retry(wait=wait_random_exponential(min=1, max=60), stop=stop_after_attempt(3))
def completion_with_retry(prompt):
    return client.chat.completions.create(
        model="gpt-4o",
        messages=[{"role": "user", "content": prompt}]
    )

In this example, the @retry decorator handles everything. If the API fails, it waits a random exponential time and tries up to 3 times before finally giving up.

3. Implementing Fallbacks

A fallback is your safety net. If the primary model (like GPT-4o) fails after all retry attempts, you can catch the error and try a different model (like GPT-4o-mini).


def get_llm_response(prompt):
    try:
        # Attempt the high-quality model first
        return completion_with_retry(prompt)
    except Exception as e:
        print(f"Primary model failed: {e}. Switching to fallback...")
        # Fallback to a different model
        return client.chat.completions.create(
            model="gpt-4o-mini",
            messages=[{"role": "user", "content": prompt}]
        )

Common mistakes

  • Retrying on every error: You should only retry on "retryable" errors, like rate limits (429) or server errors (500). If you have an "Authentication Error" (401), retrying 10 times won't fix your wrong API key.
  • Infinite loops: Always set a stop_after_attempt limit. Without it, a prolonged outage could cause your script to run forever, potentially consuming resources or crashing your server.
  • Ignoring logs: When a fallback triggers, make sure to log it. If your app is constantly relying on the fallback, you might have a configuration issue or a depleted API credit balance that you aren't aware of.

One practice task

Create a Python script that attempts to summarize a paragraph using an intentionality "broken" API key. Use the tenacity library to attempt the call 3 times. Use a try/except block to catch the final failure and print a message saying: "All attempts failed. Please check your API key or connection." This will help you visualize exactly how the retry logic loops before finally hitting the exception handler.
