Calling LLM APIs from Python with retries and fallbacks

When you build applications powered by Large Language Models (LLMs), your code relies on a connection to a remote server. Unlike local functions, API calls can fail for many reasons: your internet might flicker, the provider might be overloaded, or you might hit a rate limit. To build a production-ready tool, you must assume these failures will happen and write code that can recover gracefully.

Why it matters

Building resilience into your API calls is the difference between a professional application and a fragile script. If an API call fails and your code isn't prepared, the entire program crashes, leading to a poor user experience.

  • Reliability: Retries allow your application to handle "transient" errors-short-lived glitches that resolve themselves in seconds.
  • Cost and Performance: Fallbacks allow you to switch to a cheaper or faster model if your primary choice is unavailable or too slow.
  • Compliance: Many API providers enforce rate limits (requests per minute). Fallbacks and smart retries help you stay within these bounds without losing data.

Step-by-step walkthrough

To implement these patterns in Python, the most effective approach involves using a dedicated library like tenacity for retries and standard try-except blocks for fallbacks.

1. Setting up Retries with Exponential Backoff

A common mistake is retrying a failed call immediately. If the server is overloaded, hitting it again instantly makes the problem worse. Instead, use "Exponential Backoff," which increases the wait time between each attempt.

2. Implementing a Fallback Model

A fallback is your "Plan B." If your primary model (like GPT-4) is down or returns an error, your code should automatically catch that error and attempt the request using a different model (like GPT-3.5 or Claude Haiku).

3. The Resilient Implementation

Here is a concise way to combine both strategies using the OpenAI Python library as an example:


import openai
from tenacity import retry, wait_random_exponential, stop_after_attempt

# Strategy: Retry up to 3 times with increasing wait times
@retry(wait=wait_random_exponential(min=1, max=60), stop=stop_after_attempt(3))
def call_llm(model_name, prompt):
    client = openai.OpenAI(api_key="YOUR_API_KEY")
    return client.chat.completions.create(
        model=model_name,
        messages=[{"role": "user", "content": prompt}]
    )

def robust_request(prompt):
    try:
        # Attempt primary model
        return call_llm("gpt-4", prompt)
    except Exception as e:
        print(f"Primary model failed: {e}. Trying fallback...")
        # Fallback to a secondary model
        return call_llm("gpt-3.5-turbo", prompt)

Common mistakes

  • Infinite Retries: Never set your retries to run forever. If the API key is invalid or the prompt violates safety guidelines, the code will loop indefinitely and potentially rack up unnecessary compute costs.
  • Catching Everything: Avoid using a bare except:. Try to catch specific errors like RateLimitError or APITimeoutError so you don't accidentally hide bugs in your own logic.
  • Ignoring Latency: Each retry adds time to the user's wait. If your app is user-facing, provide a loading indicator or a "please wait" message to manage expectations during retries.

One practice task

Create a script that attempts to summarize a paragraph of text. Set the retry logic to attempt the call 5 times. To simulate a failure for testing, try passing an incorrect API key first, then update it to a correct one mid-run, or use a non-existent model name to trigger your fallback logic. Ensure your script prints a message to the console every time a retry or a fallback occurs so you can see the resilience in action.
