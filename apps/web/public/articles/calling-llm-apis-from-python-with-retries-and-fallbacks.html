Calling LLM APIs from Python with retries and fallbacks

Interacting with Large Language Models (LLMs) through APIs like OpenAI, Anthropic, or Google Gemini is a core skill for modern developers. However, unlike traditional internal functions, API calls are prone to external failures. A server might be overloaded, your internet might flicker, or you might hit a rate limit. If your code isn't prepared for these hiccups, your entire application could crash or leave the user staring at an error message.

Why it matters

Building a production-ready application requires moving beyond "happy path" coding. In the world of LLMs, reliability is the difference between a prototype and a product.

  • Rate Limits: Most providers limit how many requests you can send per minute. If you exceed this, the API will temporarily block you.
  • Server Downtime: Even the biggest tech companies experience outages or high-latency periods where requests time out.
  • Cost Management: Sometimes a high-end model like GPT-4o fails. Instead of failing completely, you might want to "fall back" to a cheaper, faster model like GPT-4o-mini to keep the service running.
  • User Experience: Users expect apps to be resilient. Implementing retries ensures that a 1-second network glitch doesn't ruin the user's session.

Step-by-step walkthrough

To handle these issues effectively, we use two main strategies: Retries (trying the same thing again after a short wait) and Fallbacks (trying a different approach if the first one fails).

1. Setting up your environment

The most popular library for handling retries in Python is tenacity. It allows you to add retry logic to any function using simple "decorators." You will also need the openai library (or your provider of choice).


pip install openai tenacity

2. Implementing Exponential Backoff

When an API tells you it's busy, the worst thing you can do is hit it again immediately. We use "exponential backoff," which means we wait longer and longer between each attempt (e.g., 1s, 2s, 4s, 8s).

3. Adding a Fallback

A fallback is your Plan B. If the primary model is down or your retries have exhausted themselves, you catch the error and call a different model or return a pre-written "safe" response.

Code Example: Resilient API Call


import openai
from tenacity import retry, stop_after_attempt, wait_random_exponential, retry_if_exception_type

client = openai.OpenAI(api_key="your_api_key_here")

# We only want to retry on specific errors like Rate Limits or Server Errors
@retry(
    wait=wait_random_exponential(min=1, max=60), 
    stop=stop_after_attempt(3),
    retry=retry_if_exception_type((openai.RateLimitError, openai.APIConnectionError))
)
def call_llm_with_retry(model, prompt):
    return client.chat.completions.create(
        model=model,
        messages=[{"role": "user", "content": prompt}]
    )

def smart_request(prompt):
    try:
        # Try the premium model first
        print("Attempting primary model...")
        return call_llm_with_retry("gpt-4o", prompt)
    except Exception as e:
        print(f"Primary model failed: {e}. Switching to fallback...")
        # Fallback to a faster/cheaper model if the primary fails
        return call_llm_with_retry("gpt-4o-mini", prompt)

# Usage
response = smart_request("Explain quantum physics to a five-year-old.")
print(response.choices[0].message.content)

Common mistakes

  • Retrying on Authentication Errors: If your API key is wrong, retrying 10 times won't fix it. Only retry on "transient" errors like network issues or 500-level server errors.
  • Infinite Loops: Always set a stop_after_attempt limit. Without it, your code might run forever, potentially costing you money if the API partially functions.
  • Ignoring the Logs: If a fallback triggers, you should log that event. If you don't, you might never realize your primary model is failing 50% of the time.
  • Hardcoding Keys: Never put your API keys directly in the script. Use environment variables or a .env file.

One practice task

Try to modify the code example provided above to include a "Max Budget" fallback. Create a variable called attempts. If the function fails after 3 retries of the premium model, instead of calling a second model, make the function return a string that says: "The AI is currently busy. Please try again in a few minutes." This simulates a "graceful degradation" of service for your users.
