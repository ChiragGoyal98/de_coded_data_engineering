Calling LLM APIs from Python with retries and fallbacks

Interacting with Large Language Models (LLMs) through APIs is a core skill for modern developers. However, these external services are not always reliable. You might encounter temporary network hiccups, rate limits, or even complete service outages. Building a production-ready application requires a strategy to handle these hiccups gracefully so your users do not see a system error every time a server blinks.

Why it matters

Reliable code is the difference between a prototype and a product. Implementing retries ensures that brief connection issues or rate limit triggers are resolved automatically without failing the entire request. Fallbacks go a step further by switching to a different model or provider if the primary one remains unavailable. This strategy maintains uptime, provides a smoother user experience, and allows you to use more accessible models as backups for premium ones during peak traffic.

Step-by-step walkthrough

Building a resilient LLM call involves two main layers: a retry loop for temporary errors and a fallback mechanism for permanent failures.

1. Setting up the Retry Logic

Instead of writing complex loops manually, the Python library tenacity is the industry standard for handling retries. It allows you to define how many times to try and how long to wait between attempts.


from tenacity import retry, stop_after_attempt, wait_random_exponential
import openai

# This decorator tells Python to retry the function if it fails
@retry(wait=wait_random_exponential(min=1, max=60), stop=stop_after_attempt(3))
def call_primary_llm(prompt):
    client = openai.OpenAI(api_key="YOUR_KEY")
    response = client.chat.completions.create(
        model="gpt-4o",
        messages=[{"role": "user", "content": prompt}]
    )
    return response.choices[0].message.content

2. Implementing the Fallback

If the primary model fails after all retry attempts, we use a try-except block to catch the error and route the request to a secondary model (the fallback).


def get_completion_resilient(prompt):
    try:
        # Try the premium model first with retries
        return call_primary_llm(prompt)
    except Exception as e:
        print(f"Primary model failed: {e}. Switching to fallback...")
        # Use a cheaper or different model as a backup
        client = openai.OpenAI(api_key="YOUR_KEY")
        response = client.chat.completions.create(
            model="gpt-3.5-turbo",
            messages=[{"role": "user", "content": prompt}]
        )
        return response.choices[0].message.content

3. Using Different Providers

To be truly resilient, your fallback should ideally point to a different company (e.g., Anthropic or Google Gemini) in case the entire primary provider goes down.

Common mistakes

  • Retrying on logic errors: Do not retry if the error is a "400 Bad Request" (like a typo in your prompt). Retries only help with "500" series server errors or "429" Rate Limit errors.
  • Infinite loops: Always set a stop_after_attempt limit. Retrying forever will result in massive API bills and a frozen application.
  • Leaking API keys: Beginners often hardcode keys in the script. Always use environment variables or a .env file.
  • Ignoring latency: Every retry adds time to the user's wait. If your app needs to be fast, keep the retry count low (2 or 3 attempts).

One practice task

Create a Python function that attempts to summarize a short paragraph using a "Premium" model. If the API returns a rate limit error, the function should wait and try again. If it fails three times, it should return the summary from a "Basic" model instead. To simulate a failure for testing, try using an invalid model name in your primary function.
