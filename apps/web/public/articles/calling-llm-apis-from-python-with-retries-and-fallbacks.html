Calling LLM APIs from Python with retries and fallbacks

When you build applications using Large Language Models (LLMs), you quickly discover that the internet is a messy place. Unlike a local function that runs on your computer, an API call travels across servers, through firewalls, and into the hands of a provider that might be experiencing heavy traffic. If your code assumes the API will always respond instantly with a 200 OK status, your application will eventually crash. Building resilient code means expecting things to go wrong and having a plan to handle those hiccups gracefully.

Why it matters

In a production environment, reliability is just as important as the quality of the LLM's response. There are three main reasons why you need retries and fallbacks:

  • Rate Limiting: Popular providers like OpenAI or Anthropic limit how many requests you can send per minute. If you exceed this, the API will temporarily block you.
  • Transient Errors: Sometimes a server is momentarily overloaded or a network packet gets dropped. These are "glitches" that usually resolve themselves if you simply try again a second later.
  • Cost and Availability: High-end models (like GPT-4o) are more prone to latency or outages than smaller, faster models. Having a fallback ensures your user gets an answer from a "smaller" model instead of an error message.

Step-by-step walkthrough

To handle these issues in Python, we generally use a combination of the tenacity library for retries and standard try-except blocks for fallbacks.

1. Implementing Smart Retries

You don't want to retry every error. For example, if your API key is wrong, retrying won't fix it. You only want to retry on "retryable" errors like rate limits (429) or server errors (5xx).

We use Exponential Backoff, which means we wait longer between each attempt (e.g., 1s, 2s, 4s). This prevents us from spamming a server that is already struggling.

2. Setting up the Fallback

A fallback is your "Plan B." If the primary model fails after all retry attempts, your code should catch that failure and attempt the request using a different, more reliable, or cheaper model.

3. Putting it into code

Here is a concise way to implement both using the tenacity library:


import openai
from tenacity import retry, stop_after_attempt, wait_exponential, retry_if_exception_type

client = openai.OpenAI(api_key="your_key_here")

# Define which errors are worth retrying
retry_on_these_errors = (
    openai.RateLimitError, 
    openai.APIConnectionError, 
    openai.Timeout
)

@retry(
    retry=retry_if_exception_type(retry_on_these_errors),
    wait=wait_exponential(multiplier=1, min=2, max=10),
    stop=stop_after_attempt(3)
)
def call_llm_with_retry(model, prompt):
    return client.chat.completions.create(
        model=model,
        messages=[{"role": "user", "content": prompt}]
    )

def robust_llm_call(prompt):
    try:
        # Try the premium model first
        return call_llm_with_retry("gpt-4o", prompt)
    except Exception as e:
        print(f"Primary model failed: {e}. Switching to fallback...")
        # Fallback to a faster, more available model
        return call_llm_with_retry("gpt-3.5-turbo", prompt)

Common mistakes

  • Retrying indefinitely: If you don't set a stop_after_attempt limit, your code might get stuck in an infinite loop, burning through your resources or hanging the application.
  • Broad exception handling: Avoid using except Exception: for your retry logic. If you have a syntax error in your code, you don't want the program to retry that-it will never succeed. Only retry network and API-specific errors.
  • Ignoring the "Retry-After" header: Some APIs tell you exactly how many seconds to wait. While tenacity handles general timing, more advanced setups look at the API response headers to be even more efficient.
