Calling LLM APIs from Python with retries and fallbacks

When building applications powered by Large Language Models (LLMs), the connection between your code and the AI provider is often the weakest link. APIs can fail for many reasons: temporary network glitches, rate limiting, or server-side maintenance. Relying on a single, direct API call is a recipe for a fragile application that crashes the moment a server hiccups. To build professional-grade AI tools, you must prepare for these failures by implementing strategies that allow your code to try again or switch to a backup plan.

Why it matters

In a local development environment, an API error is a minor annoyance. In a production environment, it results in lost users and broken workflows.

  • Stability: Networks are inherently unreliable. A "503 Service Unavailable" error might last only a second; a retry mechanism ensures your application survives that second without crashing.
  • Rate Limiting: LLM providers impose strict limits on how many requests you can send per minute. Instead of failing when you hit a limit, your code can wait and retry automatically.
  • Redundancy: If one provider (like OpenAI) experiences a major outage, a fallback mechanism can automatically switch your request to a different provider (like Anthropic or Google), keeping your service online.

Step-by-step walkthrough

Handling errors manually with if/else statements can quickly become messy. Instead, we can use industry-standard libraries and patterns to manage these failures cleanly.

1. Setting up Retries with Tenacity

The tenacity library is the gold standard for retrying tasks in Python. It allows you to define how many times to retry and how long to wait between attempts using "exponential backoff"-a technique where the wait time increases after each failure to avoid overwhelming the server.


import openai
from tenacity import retry, stop_after_attempt, wait_exponential

client = openai.OpenAI(api_key="your_key")

@retry(
    stop=stop_after_attempt(3), 
    wait=wait_exponential(multiplier=1, min=4, max=10)
)
def call_llm_with_retry(prompt):
    return client.chat.completions.create(
        model="gpt-3.5-turbo",
        messages=[{"role": "user", "content": prompt}]
    )

2. Implementing a Fallback Strategy

A fallback is your "Plan B." If the primary model fails after all retry attempts, the code should catch the error and try a different model or provider. This is often done using a simple try-except block wrapped in a coordinator function.

3. Combining both patterns

The most robust approach is to attempt a retry on your primary model first, and if that ultimately fails, trigger the fallback model.


def robust_llm_call(prompt):
    try:
        # Attempt primary model with retries
        return call_llm_with_retry(prompt)
    except Exception as e:
        print(f"Primary model failed: {e}. Switching to fallback...")
        # Fallback to a different model or provider
        return client.chat.completions.create(
            model="gpt-3.5-turbo-0125", # A different version or model
            messages=[{"role": "user", "content": prompt}]
        )

Common mistakes

  • Retrying on 400-level errors: You should only retry on server errors (500-level) or rate limits. If you receive a "401 Unauthorized" or "400 Bad Request," retrying will not help because the issue is with your credentials or your code, not the server's availability.
  • Infinite loops: Always set a stop_after_attempt limit. Without it, a permanent outage could cause your script to run forever, potentially racking up unexpected compute costs.
  • Ignoring the payload: When falling back to a different model (e.g., from GPT-4 to Claude), remember that different models might require different prompt formatting or have different token limits.
  • Lack of logging: If your fallback is working perfectly, you might never realize your primary provider is failing 50% of the time. Always log when a retry or fallback occurs so you can monitor the health of your dependencies.

One practice task

Create a Python script that attempts to call an LLM API. Use the tenacity library to retry the call up to 3 times. If all 3 attempts fail, the script should return a hardcoded "Safety Response" (e.g., "I'm sorry, I'm having trouble connecting to my brain right now.") instead of crashing the program. Bonus: Print the attempt number every time a retry happens.
