Calling LLM APIs from Python with retries and fallbacks

When building applications that rely on Large Language Models (LLMs), developers quickly learn that the cloud is not always reliable. API requests can fail for many reasons: your internet might flicker, the AI provider might be overloaded, or you might hit a rate limit because you sent too many requests too quickly. If your Python script simply stops working when these errors occur, your application will feel broken to the user. Learning how to handle these hiccups gracefully is a fundamental skill for any AI developer.

Why it matters

Reliability is the difference between a prototype and a production-ready tool. When you call an LLM API, you are making a network request to a remote server that you do not control.

Implementing retries ensures that temporary glitches-often called "transient errors"-don't kill your program. Instead of failing, the script waits a moment and tries again. Fallbacks take this a step further: if your primary model (like GPT-4) is down or too slow, your code can automatically switch to a secondary model (like GPT-3.5 or Claude) to finish the job. This approach keeps your application running even during major provider outages.

Step-by-step walkthrough

To handle these patterns efficiently in Python, the community favorite library is tenacity. It allows you to add retry logic to any function using simple decorators.

1. Setting up retries with Exponential Backoff

The most effective way to retry is "exponential backoff." This means the script waits a short time after the first failure, but increases that wait time after every subsequent failure. This prevents you from "spamming" the API provider.


import openai
from tenacity import retry, wait_random_exponential, stop_after_attempt

@retry(wait=wait_random_exponential(min=1, max=60), stop=stop_after_attempt(5))
def call_llm_with_retry(prompt):
    client = openai.OpenAI()
    response = client.chat.completions.create(
        model="gpt-3.5-turbo",
        messages=[{"role": "user", "content": prompt}]
    )
    return response.choices[0].message.content

In the example above, tenacity will attempt the request up to 5 times. It will start with a short random wait and gradually increase it up to 60 seconds between tries.

2. Implementing a Fallback

A fallback is your "Plan B." You can use a try-except block to catch the final failure of your primary model and immediately trigger a request to a different model.

  • Attempt to call the high-performance model with retries.
  • If the retries fail (or if the model returns a specific error), catch the exception.
  • Inside the except block, call a cheaper or more available model as a backup.

3. Filtering which errors to retry

You should not retry every error. For example, if your API key is invalid (a 401 error), retrying five times will not fix the problem. You should only retry on status codes like 429 (Rate Limit) or 500/503 (Server Error).

Common mistakes

  • Retrying forever: Always set a stop_after_attempt limit. An infinite loop of API calls can lead to massive bills or getting your account banned.
  • Ignoring the error type: Beginners often use a "bare" except block (except:). This is dangerous because it hides bugs in your code (like typos) by treating them as network errors.
  • Fixed wait times: If you set a fixed 2-second wait, you might still hit rate limits. Using "jitter" (randomness) in your wait times helps distribute traffic more evenly.
  • No logging: If your script is retrying in the background, you might not realize there is an issue. Always print or log a message when a retry is triggered so you can monitor the health of your connection.

One practice task

Create a Python function that attempts to summarize a paragraph using an LLM. Use the tenacity library to implement a retry strategy that attempts the task 3 times. If all 3 attempts fail, the function should return a pre-written "Summary currently unavailable" string instead of crashing the program. Generate a fake error inside your function (using raise Exception("API Down")) to test that your fallback string actually appears.
