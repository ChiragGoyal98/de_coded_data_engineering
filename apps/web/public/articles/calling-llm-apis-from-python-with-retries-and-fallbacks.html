Calling LLM APIs from Python with retries and fallbacks

When building applications powered by Large Language Models (LLMs), the connection between your code and the AI provider is the most fragile link. Unlike local functions that execute almost instantly, API calls travel across the internet, depend on remote server stability, and are subject to strict usage limits. If a provider's server is overloaded or your internet connection flickers for a split second, your entire application could crash. To build professional-grade AI tools, you must prepare for these inevitable interruptions.

Why it matters

Reliability is the difference between a prototype and a production-ready tool. LLM providers often enforce rate limits, which restrict how many requests you can send per minute. Additionally, high-demand periods can cause "503 Service Unavailable" errors.

If your script stops every time a minor network error occurs, you lose data and provide a poor user experience. Implementing retries allows your code to "try again" automatically after a short pause. Adding fallbacks ensures that if your primary model (like GPT-4) is down, your application can automatically switch to a secondary model (like Claude or a smaller GPT-3.5 model) to keep the service running.

Step-by-step walkthrough

To handle these issues cleanly, we use a combination of Python's try-except blocks and a popular library called tenacity, which is designed specifically for retrying tasks.

1. Setting up the environment

First, you need to install the necessary libraries. For this tutorial, we will use the OpenAI client and Tenacity.

pip install openai tenacity

2. Implementing smart retries

A "smart" retry doesn't just spam the server. It uses "exponential backoff," meaning it waits longer between each attempt (e.g., 1s, 2s, 4s) to give the server time to recover.

3. Adding a fallback model

If the retries fail after a certain number of attempts, we wrap the logic in a secondary function. If the expensive or primary model fails, the except block catches the error and triggers a call to a different model.

Code Example: Robust API Call

The following example demonstrates how to retry a call up to three times with a delay, then switch to a backup model if it still fails.


import openai
from tenacity import retry, stop_after_attempt, wait_random_exponential

client = openai.OpenAI(api_key="YOUR_API_KEY")

@retry(wait=wait_random_exponential(min=1, max=60), stop=stop_after_attempt(3))
def call_primary_model(prompt):
    # This will retry up to 3 times if it hits a RateLimit or Server Error
    return client.chat.completions.create(
        model="gpt-4o",
        messages=[{"role": "user", "content": prompt}]
    )

def safe_generate(prompt):
    try:
        return call_primary_model(prompt)
    except Exception as e:
        print(f"Primary model failed: {e}. Switching to fallback...")
        # Fallback to a different, often cheaper/more available model
        return client.chat.completions.create(
            model="gpt-3.5-turbo",
            messages=[{"role": "user", "content": prompt}]
        )

result = safe_generate("Write a poem about coding.")
print(result.choices[0].message.content)

Common mistakes

  • Retrying on every error: Do not retry if the error is a "401 Unauthorized" (wrong API key) or "400 Bad Request" (syntax error). These will never succeed no matter how many times you try. Only retry on 429 (Rate Limit) or 5xx (Server Errors).
  • Infinite loops: Always set a stop_after_attempt limit. Without it, a prolonged outage could keep your script running forever, potentially costing you money or consuming system resources.
  • Hardcoding API Keys: Avoid putting keys directly in the code. Use environment variables or .env files to keep your credentials secure while testing your retry logic.

One practice task

Modify the code example provided above to include a "Logging" statement inside the try-except block. Create a list of three different prompts and use a for loop to process them using the safe_generate function. To simulate a failure and test your fallback, try temporarily changing the primary model name to something that doesn't exist (like "gpt-fake-model") and observe how the code automatically switches to the backup.
