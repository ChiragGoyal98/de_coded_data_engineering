Calling LLM APIs from Python with retries and fallbacks

When you start building applications with Large Language Models, you often assume the API will work perfectly every time. However, in a real-world setting, network issues, rate limits, and server-side timeouts are common occurrences. Relying on a single request without a backup plan can make your application feel buggy or unreliable to users. Learning how to handle these hiccups programmatically is a fundamental skill for any developer working with AI. By implementing retries and fallbacks, you ensure your app remains functional even when the AI provider is having a bad day.

Why it matters

In a production environment, "it worked on my machine" isn't enough. LLM providers like OpenAI, Anthropic, or Google have strict rate limits-rules on how many requests you can send per minute. If you exceed these, your app will crash unless you have a retry strategy.

Furthermore, LLMs are computationally heavy. Sometimes a server simply gets overloaded and returns a 500-series error. Without a fallback strategy-switching to a smaller, faster model or a different provider entirely-your user is left staring at an error message. Building resilience directly into your code saves money, improves user experience, and prevents middle-of-the-night emergency bug fixes.

Step-by-step walkthrough

1. Setting up the environment

To handle retries elegantly in Python, the most popular library is tenacity. It allows you to wrap your functions with specific rules for when and how to try again. You will also need the library for your chosen LLM (we will use openai for this example).


pip install openai tenacity

2. Implementing Retries

The goal of a retry is to wait a moment and try again if a "transient" error occurs (like a network timeout). We use "Exponential Backoff," which means we wait longer and longer between each attempt so we don't overwhelm the server.

3. Implementing Fallbacks

A fallback is your "Plan B." If GPT-4 is down or too slow, you might want to automatically switch to a cheaper, faster model like GPT-4o-mini to ensure the user gets a response.

Code Example: Resilient LLM Call

The following script combines tenacity for retrying and a simple try-except block for the fallback.


import os
from openai import OpenAI
from tenacity import retry, stop_after_attempt, wait_exponential, retry_if_exception_type

client = OpenAI(api_key="YOUR_API_KEY")

# 1. Define the retry logic: Try 3 times, wait 2^x seconds between tries
@retry(
    stop=stop_after_attempt(3),
    wait=wait_exponential(multiplier=1, min=4, max=10),
    retry=retry_if_exception_type(Exception) 
)
def call_llm_with_retry(model, prompt):
    print(f"Attempting request with {model}...")
    response = client.chat.completions.create(
        model=model,
        messages=[{"role": "user", "content": prompt}]
    )
    return response.choices[0].message.content

def smart_llm_call(prompt):
    try:
        # Try the primary, high-quality model first
        return call_llm_with_retry("gpt-4o", prompt)
    except Exception as e:
        print(f"Primary model failed after retries. Switching to fallback. Error: {e}")
        # Fallback to a faster/cheaper model if the primary fails
        return call_llm_with_retry("gpt-4o-mini", prompt)

# Usage
result = smart_llm_call("Write a short poem about coding.")
print(result)

Common mistakes

  • Retrying on user errors: Do not retry if the error is a "400 Bad Request" (e.g., your prompt is too long). Retries only help with server errors (500s) or rate limits (429s).
  • Infinite loops: Always set a stop_after_attempt limit. Retrying forever will just burn through your API credits or hang your application.
  • Hardcoding API keys: Beginners often leave their API keys in the code. Always use environment variables or a .env file to keep your credentials safe.
  • Missing timeouts: Sometimes a request doesn't fail; it just hangs forever. Always set a timeout parameter in your API call to trigger a retry if the server is taking too long.
