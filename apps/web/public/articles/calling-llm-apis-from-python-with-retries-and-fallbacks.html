Calling LLM APIs from Python with retries and fallbacks

When building applications powered by Large Language Models, the connection between your code and the AI provider is often the weakest link. Unlike local functions that execute predictably, LLM APIs rely on network stability and the provider's server health. If you send too many requests at once or if the provider experiences a temporary hiccup, your application might crash. Learning to handle these interruptions gracefully is a fundamental skill for any AI developer.

Why it matters

In a production environment, reliability is just as important as the quality of the AI's response. Without a strategy for retries and fallbacks, your user might see an error message simply because a server was busy for a fraction of a second. Implementing these patterns ensures:

  • Resilience: Your app stays online even during minor API outages.
  • Cost Management: You can start with a premium model and fall back to a cheaper one if needed.
  • Rate Limit Handling: You can automatically wait and try again when you hit "429 Too Many Requests" errors.
  • User Experience: Smooth transitions between models prevent broken interfaces.

Step-by-step walkthrough

1. Setting up Retries with Tenacity

The most efficient way to handle retries in Python is using a library called tenacity. It allows you to wrap your API calls in a "retry" decorator that handles the logic of waiting and trying again.


import openai
from tenacity import retry, stop_after_attempt, wait_random_exponential

@retry(wait=wait_random_exponential(min=1, max=60), stop=stop_after_attempt(3))
def call_llm_with_retry(prompt):
    client = openai.OpenAI()
    return client.chat.completions.create(
        model="gpt-4o",
        messages=[{"role": "user", "content": prompt}]
    )

In this example, the code will try the request up to three times. It uses "exponential backoff," meaning it waits longer between each attempt to give the API provider time to recover.

2. Implementing a Fallback Mechanism

A fallback occurs when your primary model fails completely (even after retries), and your code automatically switches to a secondary model. This is useful if a specific model tier is experiencing downtime.


def robust_llm_call(prompt):
    try:
        # Try the primary, more expensive model first
        return call_llm_with_retry(prompt)
    except Exception as e:
        print(f"Primary model failed: {e}. Switching to fallback...")
        # Fallback to a faster, more available model
        client = openai.OpenAI()
        return client.chat.completions.create(
            model="gpt-3.5-turbo",
            messages=[{"role": "user", "content": prompt}]
        )

3. Combining Both Strategies

The most robust approach is to nest these functions. You attempt the primary model with retries; if it still fails after multiple attempts, you move to the except block and trigger the fallback model.

Common mistakes

  • Retrying on 400 errors: Do not retry if the error is a "400 Bad Request." This usually means your prompt is too long or your API key is invalid. Retrying will not fix a logic error in your code.
  • Ignoring timeouts: Sometimes an API doesn't return an error; it just hangs. Always set a timeout parameter in your request so your code doesn't wait forever.
  • Hardcoding API Keys: Beginner developers often leave their keys in the code. Always use a .env file and the os.getenv library to keep your credentials safe while testing retries.
  • Infinite Loops: If you don't set a stop_after_attempt limit, your code could get stuck in a loop, consuming resources and potentially costing you money.

One practice task

The Challenge: Create a Python script that attempts to summarize a short paragraph using a "Premium" model. If the API returns a rate limit error, it should retry twice. If it still fails, the script should automatically switch to a "Basic" model and print a message saying "Using backup model."

To simulate a failure for testing, you can temporarily change the model name to something that doesn't exist (like gpt-fake-model) to see if your fallback logic triggers correctly.
