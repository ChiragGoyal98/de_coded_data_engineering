Calling LLM APIs from Python with retries and fallbacks

Interacting with Large Language Models (LLMs) through APIs is a core skill for modern developers. However, unlike traditional local functions, API calls are subject to the unpredictability of the internet and the stability of the provider's servers. When you send a request to a model like GPT-4 or Claude, you are essentially making a long-distance phone call that can be dropped, busy, or timed out. Building a resilient integration requires more than just a simple request; it requires a strategy to handle these inevitable hiccups gracefully.

Why it matters

In a production environment, "it worked on my machine" isn't enough. LLM APIs are prone to specific types of failures that can break your application:

  • Rate Limiting: Most providers limit how many requests you can send per minute. Once you hit that limit, the API will reject your calls.
  • Server Overload: Popular models often experience high traffic, leading to "503 Service Unavailable" or "500 Internal Server Error" responses.
  • Network Latency: Sometimes the connection simply hangs, causing your application to wait indefinitely.
  • Cost and UX: A crashed script wastes development time, and a crashed app frustrates users. Implementing retries and fallbacks ensures your app keeps running smoothly without manual intervention.

Step-by-step walkthrough

To handle these issues, we will use a popular Python library called tenacity for retries and standard conditional logic for fallbacks.

Step 1: Install the necessary libraries

You will need the openai library (or your provider of choice) and tenacity.


pip install openai tenacity

Step 2: Implementing Retries

A "retry" tells your code to try the operation again if it fails. We use "Exponential Backoff," which means the code waits longer between each subsequent attempt to give the API server time to recover.


from openai import OpenAI
from tenacity import retry, stop_after_attempt, wait_random_exponential

client = OpenAI(api_key="your_api_key_here")

@retry(wait=wait_random_exponential(min=1, max=60), stop=stop_after_attempt(3))
def call_llm_with_retry(prompt):
    return client.chat.completions.create(
        model="gpt-3.5-turbo",
        messages=[{"role": "user", "content": prompt}]
    )

Step 3: Implementing Fallbacks

A "fallback" is a backup plan. If your primary model (e.g., GPT-4) fails even after several retries, you can switch to a cheaper or faster model (e.g., GPT-3.5) or a different provider entirely to ensure the user gets a response.


def call_with_fallback(prompt):
    try:
        # Attempt primary model with retries
        return call_llm_with_retry(prompt)
    except Exception as e:
        print(f"Primary model failed: {e}. Switching to fallback...")
        # Fallback logic: Use a different model
        return client.chat.completions.create(
            model="gpt-3.5-turbo",
            messages=[{"role": "user", "content": prompt}]
        )

Common mistakes

  • Retrying on Authentication Errors: Never retry if the API returns a 401 (Unauthorized) error. If your API key is wrong, trying 10 more times won't fix it; it will only get your IP temporarily flagged.
  • Infinite Loops: Always set a stop_after_attempt limit. Without it, a permanent outage at the provider could cause your script to run forever, consuming system resources.
  • Ignoring Specific Exceptions: Not all errors are created equal. You should ideally only retry on "Transient Errors" (like 429 Rate Limit or 500 Server Error) and fail immediately on "Client Errors" (like 400 Bad Request).
  • Silent Failures: If you use a fallback, make sure to log the error. If you don't, you might never realize your primary model is failing 90% of the time.

One practice task

The Scenario: You are building a weather bot.

Task: Write a Python function using tenacity that attempts to call an LLM to "summarize the weather."

  • Set the retry limit to 5 attempts.
  • If all 5 attempts fail, instead of letting the program crash, the function should return a hardcoded string: "The weather service is currently busy. Please try again later."
  • Test it by temporarily putting an invalid model name in your code to trigger the failure logic.
