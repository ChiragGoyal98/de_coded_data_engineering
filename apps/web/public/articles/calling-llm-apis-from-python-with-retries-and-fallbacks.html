Calling LLM APIs from Python with retries and fallbacks

Working with Large Language Model (LLM) APIs like OpenAI or Anthropic is a core skill for modern developers. However, these services are not always available or consistent. APIs can fail due to temporary network issues, high traffic, or rate limits. Learning how to handle these failures gracefully is the difference between a fragile script and a production-ready application.

Why it matters

LLM services are external dependencies. You cannot control their uptime, latency, or server load. If you write a simple script that makes a single request and it fails, your entire application crashes. This is particularly problematic for long-running tasks, such as processing hundreds of documents or running a chatbot for live users.

By implementing retries, you allow your code to wait a few seconds and try again when the server is overwhelmed. By implementing fallbacks, you provide a "Plan B." For example, if a high-end model like GPT-4o is unavailable, your code can automatically switch to a faster, cheaper model like GPT-4o-mini to ensure the service remains functional.

Step-by-step walkthrough

1. Handling Retries with Tenacity

The most efficient way to handle retries in Python is using a library called tenacity. It allows you to wrap your API calls in a decorator that manages "exponential backoff." This means the code waits progressively longer between each attempt (e.g., 1 second, then 2, then 4) to avoid spamming a struggling server.

2. Implementing Fallbacks

A fallback is a logic gate. You wrap your primary API call in a try-except block. If the primary call fails after all retry attempts, the except block catches the error and triggers a call to a different model or provider.

3. Practical Code Example

The following example uses the openai library and tenacity to create a resilient function.


import openai
from tenacity import retry, stop_after_attempt, wait_exponential

client = openai.OpenAI(api_key="YOUR_API_KEY")

@retry(wait=wait_exponential(min=1, max=10), stop=stop_after_attempt(3))
def call_primary_llm(prompt):
    # This will retry up to 3 times with increasing wait times
    return client.chat.completions.create(
        model="gpt-4o",
        messages=[{"role": "user", "content": prompt}]
    )

def robust_llm_call(prompt):
    try:
        return call_primary_llm(prompt)
    except Exception as e:
        print(f"Primary model failed: {e}. Switching to fallback...")
        # Fallback to a smaller, more reliable model
        return client.chat.completions.create(
            model="gpt-4o-mini",
            messages=[{"role": "user", "content": prompt}]
        )

# Usage
response = robust_llm_call("Explain quantum physics in one sentence.")
print(response.choices[0].message.content)

Common mistakes

  • Retrying on the wrong errors: Never retry a 401 Unauthorized or 400 Bad Request error. These are client-side issues (like an invalid API key or a typo in your code) that won't be fixed by trying again. Only retry 5xx (server errors) or 429 (rate limit) errors.
  • Infinite loops: Always set a stop_after_attempt limit. If the API provider is having a major outage, retrying forever will just burn your local resources and potentially get your IP flagged.
  • Ignoring the cost: If your fallback model is significantly more expensive than your primary model, an automated switch could lead to an unexpected bill. Always ensure your fallback model is budget-compatible.
  • Hardcoding keys: Beginners often paste their API keys directly into the code. Always use environment variables or a .env file to keep your credentials safe while testing retry logic.

One practice task

Create a Python script that attempts to call an LLM API. Use the tenacity library to implement a retry strategy that tries 5 times, but only if the error is a RateLimitError. If all 5 attempts fail, have the script write the prompt to a local file named failed_prompts.txt so that no data is lost.
