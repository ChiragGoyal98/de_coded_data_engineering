Calling LLM APIs from Python with retries and fallbacks

When you build an application powered by a Large Language Model (LLM), the code that connects your app to the AI is its most fragile point. Unlike local functions that execute instantly, API calls rely on the internet, server availability, and strict usage quotas. If the API provider experiences a momentary hiccup or you hit a rate limit, your entire application could crash if you haven't prepared for these interruptions.

Why it matters

Building production-ready AI applications requires a shift from "it works on my machine" to "it works even when things go wrong." Implementing retries and fallbacks is crucial for three main reasons:

  • Handling Rate Limits: Most providers limit how many requests you can send per minute. A retry logic allows your script to wait and try again automatically rather than failing.
  • Service Uptime: Even giants like OpenAI or Anthropic have brief outages. A fallback mechanism allows your app to switch to a different model (e.g., switching from GPT-4 to GPT-3.5 or Claude) to keep the service running.
  • Cost Management: You can use fallbacks to attempt a request with a cheaper model first, only escalating to a more expensive, powerful model if the first attempt fails or returns an error.

Step-by-step walkthrough

To handle these issues professionally in Python, we use a library called tenacity for retries and standard try-except blocks for fallbacks.

1. Setting up Retries

Instead of writing complex loops, tenacity allows you to use decorators to tell a function to try again if it fails.


import openai
from tenacity import retry, stop_after_attempt, wait_random_exponential

@retry(wait=wait_random_exponential(min=1, max=60), stop=stop_after_attempt(3))
def call_openai_with_retry(prompt):
    client = openai.OpenAI()
    return client.chat.completions.create(
        model="gpt-3.5-turbo",
        messages=[{"role": "user", "content": prompt}]
    )

In this snippet, wait_random_exponential is key. It prevents "thundering herd" problems by waiting a bit longer each time it fails, which is exactly what API providers prefer during rate limit issues.

2. Implementing Fallbacks

A fallback is your "Plan B." If your primary model is down or the retries fail, you catch the error and call a secondary function.


def robust_llm_call(prompt):
    try:
        # Attempt the primary call (with its own retries)
        return call_openai_with_retry(prompt)
    except Exception as e:
        print(f"Primary model failed: {e}. Switching to fallback.")
        # Fallback to a different model or provider
        return call_fallback_model(prompt)

def call_fallback_model(prompt):
    # Logic for a secondary model (e.g., a local Llama model or Anthropic)
    return "Fallback response: The primary service is currently unavailable."

Common mistakes

  • Retrying indefinitely: Never set your retries to infinite. If the API is truly down or your API key is invalid, your code will get stuck in a loop and potentially rack up unexpected compute costs.
  • Catching all errors: Do not retry on "Invalid Request" errors (like a 400 error). If your prompt is too long or your parameters are wrong, retrying won't fix it. Only retry on 429 (Rate Limit) or 500-series (Server Error) codes.
  • Ignoring Latency: Every retry adds time to the user's experience. If a call retries three times, the user might be waiting 30 seconds for a response. Always consider if a "System Busy" message is better than a long wait.

One practice task

Create a Python script that attempts to call an LLM API. Set the retry logic to attempt the call 5 times. If all 5 attempts fail, the script should print a "Maintenance Mode" message to the console instead of crashing with a Traceback error. For the purpose of the exercise, you can simulate a failure by using an incorrect API key.
