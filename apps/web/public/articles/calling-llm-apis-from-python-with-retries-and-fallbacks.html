Calling LLM APIs from Python with retries and fallbacks

When building applications with Large Language Models (LLMs) like GPT-4 or Claude, the first thing you notice is that they are not always reliable. Unlike a local function, an API call travels across the internet to a server that might be overloaded or experiencing temporary downtime. If your code is not prepared for these hiccups, your entire application will crash simply because a single request timed out or hit a rate limit. Learning to handle these interruptions gracefully is the difference between a hobby project and a professional-grade application.

Why it matters

In a production environment, "waiting and trying again" is a core strategy. LLM providers often impose Rate Limits, which restrict how many requests you can send per minute. Additionally, servers can experience "500 Internal Server Errors" during peak traffic.

Implementing retries ensures that temporary glitches don't break the user experience. Fallbacks take this a step further by providing a Plan B-such as switching to a smaller, faster model if the primary, more powerful model is unavailable. This combination ensures high availability and makes your software much more resilient to external factors you cannot control.

Step-by-step walkthrough

To handle these issues in Python, the most popular and "clean" way is using a library called tenacity. It allows you to add retry logic using decorators without cluttering your main logic.

1. Setting up Retries with Exponential Backoff

When an API fails, you shouldn't immediately try again. If the server is overloaded, hitting it again instantly makes the problem worse. Exponential backoff increases the wait time between each attempt.


from tenacity import retry, stop_after_attempt, wait_random_exponential
import openai

@retry(wait=wait_random_exponential(min=1, max=60), stop=stop_after_attempt(5))
def call_llm_with_retry(prompt):
    client = openai.OpenAI()
    return client.chat.completions.create(
        model="gpt-4o",
        messages=[{"role": "user", "content": prompt}]
    )

In this example, tenacity will try the function up to 5 times. The wait time will start small and grow randomly up to 60 seconds.

2. Implementing a Fallback Mechanism

A fallback is your safety net. If your primary model (like GPT-4) fails repeatedly, you can catch the error and try a different model (like GPT-4o-mini) or even a different provider (like Anthropic).


def robust_llm_call(prompt):
    try:
        # Attempt the premium model first
        return call_llm_with_retry(prompt)
    except Exception as e:
        print(f"Primary model failed: {e}. Switching to fallback...")
        # Fallback to a lighter, more available model
        client = openai.OpenAI()
        return client.chat.completions.create(
            model="gpt-4o-mini",
            messages=[{"role": "user", "content": prompt}]
        )

Common mistakes

  • Retrying on logic errors: Do not retry if the error is a 401 Unauthorized (wrong API key) or 400 Bad Request (invalid prompt). These will never succeed no matter how many times you try. Only retry on 429 Rate Limit or 5xx Server Errors.
  • Infinite loops: Always set a stop_after_attempt limit. Without it, your code might run forever, consuming resources and potentially costing you money if it eventually succeeds many times.
  • Not logging failures: If your system falls back to a cheaper model, you need to know about it. Always log when a fallback occurs so you can investigate if your primary provider is having long-term issues.

One practice task

Create a Python script that uses the tenacity library to call an LLM. Simulate a failure by temporarily disconnecting your internet or using an incorrect model name. Modify the retry decorator to log a message every time a retry attempt is made, so you can see the exponential backoff working in your terminal.
