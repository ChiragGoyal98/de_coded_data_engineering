Calling LLM APIs from Python with retries and fallbacks

When you start building applications with Large Language Models (LLMs), the first step is usually making a simple request to an API like OpenAI or Anthropic. However, production environments are rarely that straightforward. Servers go down, rate limits are reached, and connections drop. If your code does not account for these hiccups, your entire application will crash the moment an API provider experiences a slight delay. Building resilience into your Python scripts ensures that your app stays functional even when the external service is struggling.

Why Reliability Matters

API calls over the internet are inherently "flaky." When dealing with LLMs, this is amplified by two specific challenges:

  • Rate Limiting: Most providers limit how many requests you can make per minute. If you exceed this, the API will reject your request with a 429 error.
  • Timeouts and Latency: LLMs generate text token-by-token, which takes time. Sometimes the server takes too long to respond, causing the connection to time out.
  • Model Availability: Occasionally, a specific high-end model (like GPT-4) might be under heavy load or down, while a faster, smaller model (like GPT-3.5) remains available.

Without retries, a single failed request stops your program. Without fallbacks, a temporary outage becomes a permanent failure for your user.

Step-by-Step Walkthrough

To handle these issues gracefully, we use two main strategies: Retries (trying the same request again after a short wait) and Fallbacks (trying a different model or service if the first one fails).

1. Setting up the Environment

We will use the tenacity library, which is the industry standard for adding retry logic to Python functions.


pip install openai tenacity

2. Implementing Retries with Exponential Backoff

Exponential backoff means waiting longer between each subsequent retry. This prevents you from "spamming" an already overwhelmed server.


import openai
from tenacity import retry, wait_random_exponential, stop_after_attempt

client = openai.OpenAI(api_key="your_api_key")

@retry(wait=wait_random_exponential(min=1, max=60), stop=stop_after_attempt(5))
def call_llm_with_retry(prompt):
    return client.chat.completions.create(
        model="gpt-4",
        messages=[{"role": "user", "content": prompt}]
    )

3. Implementing a Fallback Mechanism

If the retries fail, you can wrap the function in a try-except block to switch to a "fallback" model. This ensures that the user still gets a response, even if it is from a slightly less capable model.


def robust_llm_call(prompt):
    try:
        # Try the primary, high-quality model first
        return call_llm_with_retry(prompt)
    except Exception as e:
        print(f"Primary model failed: {e}. Switching to fallback...")
        # Fallback to a cheaper/faster model
        return client.chat.completions.create(
            model="gpt-3.5-turbo",
            messages=[{"role": "user", "content": prompt}]
        )

Common Mistakes

  • Retrying on User Errors: Do not retry if the error is a 400 (Bad Request). If your prompt is formatted incorrectly, retrying it five times will yield the same error every time and waste your rate limit.
  • No Maximum Limit: Never set a retry loop to run infinitely. Always use a stop_after_attempt or a timeout to prevent your code from hanging forever.
  • Hardcoding API Keys: Beginners often leave their API keys directly in the code. Always use environment variables or a .env file to keep your credentials secure.
  • Ignoring Logging: When a retry happens, you should log it. If you don't, you might not realize your primary model is failing 90% of the time, leading to unexpected costs or performance drops.
