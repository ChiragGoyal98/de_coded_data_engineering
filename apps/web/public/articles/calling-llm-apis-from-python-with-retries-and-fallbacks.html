Calling LLM APIs from Python with retries and fallbacks

Integrating Large Language Models (LLMs) into your Python applications opens up incredible possibilities, from automated customer support to smart data analysis. However, external APIs are not always perfect. They can suffer from downtime, hit rate limits, or experience temporary network hiccups that can cause your application to crash if not handled correctly. Learning how to build a resilient connection is the bridge between a fragile script and a production-ready application.

Why it matters

When you rely on a third-party service like OpenAI, Anthropic, or Google Gemini, you are at the mercy of their uptime and your own internet stability. Implementing retries and fallbacks is essential for several reasons:

  • Handling Rate Limits: Most providers limit how many requests you can send per minute. Retries with "backoff" allow your code to wait and try again automatically.
  • Improved User Experience: Instead of showing an error message immediately, your app can silently try again or switch to a backup model, keeping the experience seamless.
  • Cost and Stability: Sometimes a high-end model might be temporarily unavailable. A fallback allows you to switch to a cheaper or more stable "lighter" model to keep the service running.

Step-by-step walkthrough

1. Setting up the environment

First, you need to install the necessary libraries. We will use the openai library for the API calls and tenacity, a popular Python library specifically designed for retrying tasks.


pip install openai tenacity

2. Implementing Retries

A retry mechanism attempts the same request again if it fails. However, you shouldn't just spam the server. We use "Exponential Backoff," which means the wait time increases between each failed attempt.

Using tenacity, we can wrap our function in a decorator that handles this logic:


from openai import OpenAI
from tenacity import retry, wait_exponential, stop_after_attempt

client = OpenAI(api_key="your_api_key")

@retry(wait=wait_exponential(min=1, max=10), stop=stop_after_attempt(3))
def call_llm(prompt):
    response = client.chat.completions.create(
        model="gpt-3.5-turbo",
        messages=[{"role": "user", "content": prompt}]
    )
    return response.choices[0].message.content

In this example, if the request fails, it will wait 1 second, then 2, then 4, and stop after 3 total attempts.

3. Adding Fallbacks

A fallback is your "Plan B." If the primary model fails even after retries, you catch the error and try a different model or provider.


def robust_llm_call(prompt):
    try:
        # Plan A: Try the primary model
        return call_llm(prompt)
    except Exception as e:
        print(f"Primary model failed: {e}. Switching to fallback...")
        # Plan B: Try a secondary, more reliable model
        response = client.chat.completions.create(
            model="gpt-4o-mini", # Often more available/faster
            messages=[{"role": "user", "content": prompt}]
        )
        return response.choices[0].message.content

Common mistakes

  • Retrying on the wrong errors: You should only retry on "transient" errors (like network timeouts or rate limits). If you have an "Authentication Error" (wrong API key), retrying 10 times will not fix it and will just waste time.
  • Infinite Loops: Always set a stop_after_attempt limit. Without it, your code might run forever if the service has a major outage, leading to high CPU usage or hung processes.
  • Hardcoding API Keys: Never put your keys directly in the code. Use environment variables or a .env file to keep your credentials safe while testing your retry logic.

One practice task

If all 5 attempts fail, instead of crashing, make the function return a pre-written "Safe Response" (e.g., "I'm sorry, I'm having trouble connecting right now. Please try again later.") so the user isn't left with a confusing error code.
