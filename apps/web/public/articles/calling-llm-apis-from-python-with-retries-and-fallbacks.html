Calling LLM APIs from Python with retries and fallbacks

When you start building applications with Large Language Models (LLMs) like GPT-4 or Claude, your code relies on an external server to provide answers. Unlike a local function that runs on your computer, these API calls happen over the internet. This means things can go wrong that are completely out of your control, such as a temporary internet flicker or the AI provider being overloaded with requests. If your code does not account for these hiccups, your entire application will crash the moment a single request fails.

Why it matters

Building a "production-ready" application means moving beyond code that only works under perfect conditions. LLM providers often impose rate limits, which restrict how many requests you can send per minute. Additionally, because these models require massive computing power, servers occasionally become overwhelmed and return "503 Service Unavailable" or "504 Gateway Timeout" errors.

Implementing retries and fallbacks ensures your application is resilient. A retry strategy allows the code to try the request again after a short delay, while a fallback strategy provides a "Plan B," such as switching to a cheaper or faster model if the primary one is down. This prevents a poor user experience and keeps your automation running smoothly.

Step-by-step walkthrough

1. Handling retries with Tenacity

The most efficient way to handle retries in Python is using a library called tenacity. It allows you to wrap your API calls with specific rules, such as "try five times" or "wait longer between each attempt" (known as exponential backoff).


import openai
from tenacity import retry, stop_after_attempt, wait_exponential

# This decorator tells the function to retry up to 3 times
# It waits 1 second, then 2, then 4 (exponentially)
@retry(stop=stop_after_attempt(3), wait=wait_exponential(multiplier=1, min=4, max=10))
def call_llm(prompt):
    client = openai.OpenAI(api_key="your_key_here")
    response = client.chat.completions.create(
        model="gpt-4",
        messages=[{"role": "user", "content": prompt}]
    )
    return response.choices[0].message.content

2. Implementing a Fallback

A fallback is your safety net. If the primary model (like GPT-4) is down or too slow, you can catch the error and try a different model (like GPT-3.5-Turbo or a model from a different provider like Anthropic).

To do this, wrap your primary call in a try...except block. If the primary call fails after all retry attempts, the code moves to the except block to try the backup model.

3. Combining both strategies

The best approach is to use a primary function with retries, and a wrapper function that handles the fallback logic. This ensures that you don't give up too early, but you also have a secondary plan if the primary provider has a major outage.

Common mistakes

  • Retrying on the wrong errors: Do not retry if the error is a "401 Unauthorized" (your API key is wrong) or "400 Bad Request" (your prompt is invalid). Retrying these will never work and will only waste time.
  • Infinite loops: Always set a stop_after_attempt limit. Without it, your code might try to call a broken API forever, potentially racking up unexpected costs or freezing your program.
  • No backoff delay: If you hit a rate limit and retry immediately, you will likely hit the limit again. Always use a delay that increases between attempts to give the server time to recover.
  • Ignoring the logs: If a fallback is triggered, you should log it. If you don't, you might never realize your primary model is failing 90% of the time.

One practice task

Create a Python script that attempts to call an LLM API. Set the retry limit to 2 attempts. If both attempts fail (you can simulate this by temporarily disconnecting your internet or using a fake API key), make the script print: "Primary model failed. Switching to backup model..." and return a hardcoded string as a "mock" fallback response.
