Calling LLM APIs from Python with retries and fallbacks

When you start building applications with Large Language Models, the first thing you learn is how to send a prompt and get a response. However, moving from a script that works once to an application that works every time requires handling the unpredictable nature of the internet. APIs can fail for many reasons, such as temporary server outages, network blips, or hitting rate limits. Learning how to handle these hiccups gracefully is what separates a prototype from a production-ready tool.

Why it matters

In a perfect world, an API would respond instantly every time. In reality, LLM providers often face heavy traffic. If your code isn't prepared for this, your entire application will crash the moment a provider experiences a one-second glitch.

  • Reliability: Retries allow your code to "self-heal" from temporary errors without bothering the user.
  • Cost Management: Fallbacks allow you to switch to a cheaper model if your primary, expensive model is unavailable.
  • User Experience: Instead of seeing a "Connection Error," users might just experience a slight delay while your system tries again or switches to a backup.

Step-by-step walkthrough

1. Handling Retries with Tenacity

The most common error you will encounter is a Rate Limit error (HTTP 429). Instead of writing complex loops, Python developers use a library called tenacity. It allows you to add "decorators" to your functions to retry them automatically.

You want to use "Exponential Backoff." This means if the first try fails, the script waits 1 second. If it fails again, it waits 2 seconds, then 4, and so on. This prevents you from "spamming" the API provider.

2. Implementing Fallbacks

A fallback is your "Plan B." If OpenAI is down, you might want to try Anthropic. If GPT-4 is over capacity, you might want to switch to the faster, more available GPT-3.5. This is usually handled with a simple try-except block wrapped around your main logic.

3. Putting it together

The following example demonstrates how to use the tenacity library to retry a call and a try block to switch models if the first one fails completely.


import openai
from tenacity import retry, wait_random_exponential, stop_after_attempt

# Define the retry logic: stop after 3 tries, wait exponentially
@retry(wait=wait_random_exponential(min=1, max=60), stop=stop_after_attempt(3))
def call_primary_llm(prompt):
    # This might fail if the API is busy
    return openai.ChatCompletion.create(model="gpt-4", messages=[{"role": "user", "content": prompt}])

def robust_llm_call(prompt):
    try:
        # Plan A: Try the high-quality model with retries
        return call_primary_llm(prompt)
    except Exception as e:
        print(f"Primary model failed after retries. Switching to fallback. Error: {e}")
        # Plan B: Use a cheaper/faster model as a backup
        return openai.ChatCompletion.create(model="gpt-3.5-turbo", messages=[{"role": "user", "content": prompt}])

Common mistakes

  • Retrying on the wrong errors: Never retry an error like "Invalid API Key" (401). No matter how many times you try, the key will still be wrong. Only retry on network timeouts or rate limits (429/500 series).
  • Infinite Loops: If you don't set a stop_after_attempt limit, your code might run forever, potentially costing you a lot of money if the API is partially working.
  • Ignoring the Fallback Logic: Sometimes the fallback model requires different prompting styles. Ensure your "Plan B" is compatible with the input you are sending.

One practice task

Try to write a script that attempts to call an LLM API. Use the tenacity library to make it retry exactly 5 times. If it still fails after 5 attempts, make the script print "System maintenance in progress, please try later" instead of crashing with a red error message.
