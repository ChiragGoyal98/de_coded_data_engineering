Calling LLM APIs from Python with retries and fallbacks

When building applications powered by Large Language Models (LLMs), the connection between your code and the AI provider is the most fragile link. Unlike traditional local functions, API calls travel over the internet to servers that may be overloaded, undergoing maintenance, or strictly limiting how many requests you can send per minute. If your Python script simply sends a request and expects a perfect response every time, your application will eventually crash. Building a "resilient" integration means preparing for these inevitable hiccups by teaching your code how to try again or switch to a backup plan.

Why it matters

Reliability is the difference between a professional tool and a hobby project. LLM providers like OpenAI, Anthropic, or Google often enforce rate limits, which are caps on how many tokens or requests you can process. When you hit these limits, the API returns an error. Similarly, "500-level" errors occur when the provider's server is temporarily overwhelmed.

Without retries, a single 1-second blip in connectivity could fail a long-running automation. Without fallbacks, an outage at one provider could take your entire service offline. Implementing these patterns ensures that your user experience remains smooth even when the underlying infrastructure is shaky.

Step-by-step walkthrough

To handle these issues gracefully, we use two main strategies: Exponential Backoff (retries with increasing wait times) and Fallbacks (switching to a different model or provider).

1. Setting up your environment

First, you will need the openai library and a specialized library for retries called tenacity. Tenacity is the industry standard for adding retry logic to Python functions using simple decorators.


pip install openai tenacity

2. Implementing Retries with Tenacity

The most effective way to retry is "exponential backoff." This means instead of retrying every second, you wait 1 second, then 2, then 4, and so on. This gives the API provider time to recover.

We use the @retry decorator to wrap our API call. We tell it to stop after a certain number of attempts and only retry when specific errors (like RateLimitError) occur.

3. Adding a Fallback Mechanism

A fallback is your "Plan B." If your primary model (e.g., GPT-4) is down or too busy, your code should catch that final failure and try a faster or cheaper model (e.g., GPT-3.5) to ensure the request is still fulfilled.

Code Example: Resilient API Call


import openai
from tenacity import retry, stop_after_attempt, wait_random_exponential, retry_if_exception_type

client = openai.OpenAI(api_key="your_api_key")

@retry(
    retry=retry_if_exception_type(openai.RateLimitError),
    wait=wait_random_exponential(min=1, max=60),
    stop=stop_after_attempt(5)
)
def call_llm_with_retry(model, prompt):
    return client.chat.completions.create(
        model=model,
        messages=[{"role": "user", "content": prompt}]
    )

def smart_llm_request(prompt):
    try:
        # Plan A: Try the powerful model with retries
        return call_llm_with_retry("gpt-4", prompt)
    except Exception as e:
        print(f"Primary model failed: {e}. Switching to Fallback...")
        # Plan B: Fallback to a different model
        return call_llm_with_retry("gpt-3.5-turbo", prompt)

Common mistakes

  • Retrying on the wrong errors: Never retry on a "401 Unauthorized" error. If your API key is wrong, retrying 10 times won't fix it; it will only get your IP temporarily flagged.
  • Infinite loops: Always set a stop_after_attempt limit. Without it, a permanent outage could cause your script to run forever, potentially racking up unexpected compute costs.
  • Hardcoding API keys: Beginners often paste their keys directly into the code. Always use environment variables or .env files to keep your credentials safe while testing your retry logic.
  • Ignoring the logs: If a fallback happens, you need to know about it. Always log when a retry occurs so you can monitor if your "Plan B" is being used more often than it should be.

One practice task

Create a Python script that uses a list of two different model names (e.g., "gpt-4o" and "gpt-3.5-turbo"). Write a loop that attempts to call the first model. If it fails after 3 retries, have the script automatically "pop" the first model from the list and try the next one. To test this without spending money, you can simulate a failure by passing an intentionally misspelled model name for the first attempt.
