Calling LLM APIs from Python with retries and fallbacks

When you build applications using Large Language Models (LLMs), your code relies on an external server to process data and return a response. This communication happens over the internet via an API. While these services are generally reliable, they are not perfect. Sometimes the network drops, or the provider is overwhelmed with too many requests at once. Instead of letting your application crash when this happens, you can write code that gracefully handles these hiccups.

Why it matters

In a production environment, reliability is everything. If an LLM API returns a "Rate Limit Exceeded" error or a temporary "503 Service Unavailable" message, a simple retry can often fix the issue without the user ever knowing there was a problem.

Fallbacks take this a step further by providing a "Plan B." For example, if your primary high-performance model is currently down, your code can automatically switch to a smaller, cheaper, or faster model to ensure the service remains online. Implementing these patterns prevents your app from being a single point of failure and improves the overall user experience.

Step-by-step walkthrough

1. Setting up the environment

To handle retries professionally in Python, the most common library used is tenacity. It allows you to add retry logic to any function using simple decorators. You will also need your LLM provider's library, such as openai.


pip install tenacity openai

2. Implementing Retries with Exponential Backoff

A common mistake is retrying immediately after a failure. If the server is overloaded, hitting it again instantly makes the problem worse. "Exponential backoff" solves this by increasing the wait time between each attempt.


from tenacity import retry, stop_after_attempt, wait_exponential
from openai import OpenAI

client = OpenAI(api_key="your_api_key")

@retry(wait=wait_exponential(min=1, max=60), stop=stop_after_attempt(5))
def call_llm(prompt):
    response = client.chat.completions.create(
        model="gpt-4",
        messages=[{"role": "user", "content": prompt}]
    )
    return response.choices[0].message.content

In this snippet:

  • wait_exponential starts with a 1-second wait and doubles it each time.
  • stop_after_attempt(5) ensures we don't loop forever.

3. Adding Fallback Logic

A fallback is a secondary action triggered when the primary action fails even after all retries. You can implement this using a standard try-except block.


def robust_llm_call(prompt):
    try:
        # Attempt the primary, high-quality model
        return call_llm(prompt)
    except Exception as e:
        print(f"Primary model failed: {e}. Switching to fallback...")
        # Fallback to a faster, cheaper model
        response = client.chat.completions.create(
            model="gpt-3.5-turbo",
            messages=[{"role": "user", "content": prompt}]
        )
        return response.choices[0].message.content

Common mistakes

  • Catching every error: Do not retry if the error is a "401 Unauthorized" (wrong API key) or a "400 Bad Request" (syntax error). These will never succeed on a retry. Only retry on network errors (timeouts) or rate limits (429).
  • Ignoring Jitter: If you have 1,000 users all retrying at exactly 1, 2, 4, and 8 seconds, you create "thundering herds" that crash servers. tenacity handles this by default, but always ensure your wait times have a bit of randomness.
  • Infinite Loops: Always set a stop_after_attempt limit. If the LLM provider is having a major multi-hour outage, your code should eventually give up and inform the user.

One practice task

The "Safety Wrapper" Challenge:

Write a Python function called get_summary(text).

  • It should attempt to use a primary LLM function with at least 3 retries.
  • If the primary function fails after all retries, it should return a hard-coded string: "System currently busy, please try again later."
  • Bonus: Add a print statement inside the retry logic to track how many attempts were made.
