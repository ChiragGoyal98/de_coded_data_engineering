Calling LLM APIs from Python with retries and fallbacks

When you build an application powered by Large Language Models (LLMs), your code relies on a connection to a remote server. Whether you are using OpenAI, Anthropic, or Google Gemini, these connections can occasionally fail due to network hiccups, rate limits, or server maintenance. Building a production-ready application requires more than just a simple request; it requires a strategy to handle these interruptions gracefully.

Why it matters

Reliability is the difference between a professional tool and a prototype. If your Python script crashes every time the API is busy, your users will lose trust. Furthermore, LLM providers often impose rate limits-restrictions on how many requests you can send per minute. If you don't handle these limits with retries, your application will stop working during peak usage. Fallbacks are equally important; if a high-end model like GPT-4 is experiencing an outage, having your code automatically switch to a lighter, faster model like GPT-4o-mini ensures that your service remains online.

Step-by-step walkthrough

Handling failures manually with loops and "if" statements can make your code messy. Instead, the standard approach in Python is to use dedicated libraries and structured error handling.

1. Implementing Retries with Tenacity

The most popular library for this is tenacity. It allows you to add "retry" logic to any function using decorators. You can define how many times to retry and how long to wait between attempts (known as backoff).


import openai
from tenacity import retry, stop_after_attempt, wait_exponential

# This decorator tells the function to retry up to 3 times
# It waits longer after each failure (exponential backoff)
@retry(stop=stop_after_attempt(3), wait=wait_exponential(multiplier=1, min=4, max=10))
def call_llm_with_retry(prompt):
    client = openai.OpenAI()
    response = client.chat.completions.create(
        model="gpt-4",
        messages=[{"role": "user", "content": prompt}]
    )
    return response.choices[0].message.content

2. Adding Fallback Logic

A fallback is your "Plan B." If your primary model fails even after multiple retries, you catch the error and attempt the request using a different model or provider.

3. Combining Both Strategies

In a real-world scenario, you wrap your retrying function inside a try-except block. If the first function exhausts all its retry attempts and still fails, the except block triggers the fallback model. This ensures maximum uptime for your application.

Common mistakes

  • Retrying on permanent errors: You should only retry on "transient" errors like timeouts or rate limits. If you have an "Invalid API Key" error (401), retrying 10 times won't fix it; it will just waste time.
  • Immediate retries: Sending a retry request the millisecond after a failure is often counterproductive. If the server is overloaded, "hammering" it immediately will likely result in another failure. Always use exponential backoff to give the server room to breathe.
  • Ignoring the cost: If your fallback model is significantly more expensive than your primary model, you might end up with an unexpected bill if your primary model goes down for an extended period.

One practice task

Write a Python script that attempts to summarize a paragraph of text. Your script should:

  • Try to use a primary model (e.g., "gpt-4").
  • Use tenacity to retry 2 times if it fails.
  • If the primary model still fails after 2 retries, catch the exception and successfully return a summary using a secondary model (e.g., "gpt-4o-mini").
