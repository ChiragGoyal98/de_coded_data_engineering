Calling LLM APIs from Python with retries and fallbacks

Building applications with Large Language Models (LLMs) often feels like magic when things work, but the reality of cloud-based APIs is that they are not always 100% reliable. When you send a request to a provider like OpenAI, Anthropic, or Google, several things can go wrong: the network might hiccup, the provider might be overloaded, or you might hit a rate limit. If your code isn't prepared to handle these interruptions, your entire application could crash, leading to a poor experience for your users.

Why it matters

Reliability is the bridge between a fun prototype and a production-ready tool. Implementing retries ensures that temporary issues, like a 503 Service Unavailable error, don't stop your program; instead, the code simply waits a moment and tries again. Fallbacks take this a step further by providing a "Plan B." If your primary, high-performance model (like GPT-4) is down or too slow, your system can automatically switch to a lighter, faster model (like GPT-4o-mini or Haiku) to ensure the user still gets a response. This combination maximizes uptime and makes your software feel robust and professional.

Step-by-step walkthrough

To handle these scenarios in Python, we generally use a combination of error handling and specialized libraries. One of the most popular tools for this is tenacity.

1. Setting up Retries

The goal of a retry is to attempt the same request multiple times with a slight delay. We use "exponential backoff," which means we increase the wait time between each attempt so we don't overwhelm the API provider.

2. Implementing Fallbacks

A fallback is a logic gate. If the retry logic fails after a certain number of attempts, or if a specific permanent error occurs, the code catches that exception and triggers a call to a different model or provider.

3. Combining both in Python

In the example below, we use the tenacity library to manage retries and a standard try-except block to manage the fallback.


import openai
from tenacity import retry, stop_after_attempt, wait_random_exponential

client = openai.OpenAI(api_key="YOUR_API_KEY")

# This decorator tells Python to retry this function if it fails
@retry(wait=wait_random_exponential(min=1, max=60), stop=stop_after_attempt(3))
def call_primary_model(prompt):
    return client.chat.completions.create(
        model="gpt-4-turbo",
        messages=[{"role": "user", "content": prompt}]
    )

def smart_llm_call(prompt):
    try:
        # Attempt the primary model with retries
        return call_primary_model(prompt)
    except Exception as e:
        print(f"Primary model failed: {e}. Switching to fallback...")
        # Fallback to a cheaper/faster model if primary fails
        return client.chat.completions.create(
            model="gpt-4o-mini",
            messages=[{"role": "user", "content": prompt}]
        )

response = smart_llm_call("Explain quantum physics in one sentence.")
print(response.choices[0].message.content)

Common mistakes

  • Retrying on the wrong errors: Don't retry if the error is "Invalid API Key" or "Context Window Exceeded." These are permanent errors that won't fix themselves with a retry. Only retry on network issues or rate limits (HTTP 429 or 500+).
  • Infinite loops: Always set a stop_after_attempt limit. Retrying forever will drain your resources and potentially lead to massive API bills if not monitored.
  • Ignoring the fallback's failure: Sometimes the fallback model might be down too. Ensure your code can handle a total failure gracefully by returning a helpful message to the user rather than a raw code error.

One practice task

Create a Python script that attempts to summarize a paragraph using an LLM. Use the tenacity library to retry the call 3 times. If all 3 attempts fail, instead of switching to another API, make the "fallback" return a pre-written string that says: "The AI is currently taking a nap. Please try again later." This will help you practice the structure of error handling without needing multiple API accounts.
