Calling LLM APIs from Python with retries and fallbacks

Building applications with Large Language Models (LLMs) is an exciting frontier, but it comes with a unique set of challenges. Unlike traditional local functions, an API call travels across the internet to a server that might be overloaded or experiencing temporary issues. If your code isn't prepared for these hiccups, your entire application might crash just because a single request timed out or hit a rate limit. Learning how to handle these failures gracefully is a fundamental skill for any developer working in the AI space.

Why it matters

When you call an LLM API, you are at the mercy of three main variables: your internet connection, the provider's server health, and your specific usage limits. Implementing retries and fallbacks ensures your application remains resilient.

  • Rate Limiting: Most providers like OpenAI or Anthropic limit how many requests you can send per minute. If you exceed this, the API returns a 429 error.
  • Transient Errors: Sometimes a server just flickers. A "503 Service Unavailable" error might happen once, but the very next request might succeed.
  • Cost and Performance: If a high-end model like GPT-4o is down or too slow, your system should automatically switch to a faster, cheaper "fallback" model like GPT-4o-mini to keep the user experience smooth.

Step-by-step walkthrough

To handle these issues, we use two main strategies: Retries (trying the same thing again after a short wait) and Fallbacks (trying a different model or method if the first one fails).

Step 1: Install the necessary library

While you can write your own loops to retry code, the Python community uses a library called tenacity. It is the industry standard for adding retry logic to functions.


pip install tenacity openai

Step 2: Implement Exponential Backoff

If an API is overloaded, hitting it again immediately will likely fail. We use "exponential backoff," which means we wait a little longer after each failed attempt (e.g., 1s, 2s, 4s).

Step 3: Set up the Fallback Logic

We wrap our API call in a function. If the retries fail, we catch the exception and call a secondary, more reliable (or cheaper) model.

Code Example: Resilient API Call


import os
from openai import OpenAI
from tenacity import retry, stop_after_attempt, wait_exponential

client = OpenAI(api_key="YOUR_API_KEY")

# This decorator tells Python to retry this function up to 3 times
# waiting 2^x seconds between hits.
@retry(wait=wait_exponential(multiplier=1, min=2, max=10), stop=stop_after_attempt(3))
def call_primary_model(prompt):
    print("Attempting call to GPT-4o...")
    return client.chat.completions.create(
        model="gpt-4o",
        messages=[{"role": "user", "content": prompt}]
    )

def smart_llm_call(prompt):
    try:
        # Try the primary model first
        return call_primary_model(prompt)
    except Exception as e:
        print(f"Primary model failed after retries: {e}")
        print("Switching to fallback model: GPT-4o-mini...")
        # Fallback to a different model if primary fails completely
        return client.chat.completions.create(
            model="gpt-4o-mini",
            messages=[{"role": "user", "content": prompt}]
        )

# Usage
response = smart_llm_call("Explain quantum physics in one sentence.")
print(response.choices[0].message.content)

Common mistakes

  • Infinite Loops: Not setting a stop_after_attempt limit. This can lead to your program running forever and potentially costing you a lot of money if the error isn't temporary.
  • Catching All Errors: You should ideally only retry on specific errors (like RateLimitError or Timeout). Retrying a "401 Unauthorized" error is pointless because your API key won't magically become valid on the second try.
  • Ignoring Latency: Every retry adds seconds to the user's wait time. If your app is user-facing, keep your retry counts low (2 or 3 attempts) to avoid a frustratingly slow interface.

One practice task

Create a Python script that attempts to call an LLM API. Use the tenacity library to retry the call only if it encounters a Timeout error. If the call fails 3 times, instead of crashing, make the script print: "System is currently busy, please try again later." This helps you practice separating "retryable" errors from "final" failures.
