Calling LLM APIs from Python with retries and fallbacks

When you start building AI-powered applications, the first step is usually connecting your Python code to a Large Language Model (LLM) like GPT-4 or Claude. This is typically done via an API request. While it sounds straightforward, the internet is unpredictable. APIs can get busy, your internet connection might flicker, or you might hit a rate limit. Knowing how to handle these interruptions gracefully is what separates a prototype from a professional application.

Why it matters

In a production environment, reliability is everything. If your application sends a request and the LLM provider is momentarily overloaded, your app shouldn't just crash or show an error message to the user.

Implementing retries allows your code to "try again" automatically after a short pause, which often solves issues caused by temporary network congestion or rate limits. Fallbacks take this a step further: if your primary, high-powered model (like GPT-4) is completely unavailable, your code can automatically switch to a secondary model (like GPT-3.5 or an open-source alternative) to ensure the user still gets a response.

Step-by-step walkthrough

1. Setting up the environment

First, you need the right tools. While you can write your own retry loops, the Python community largely uses a library called tenacity. It is designed to handle retries elegantly using decorators.


pip install openai tenacity

2. Implementing Retries with Tenacity

The most effective way to retry is using "exponential backoff." This means the wait time between retries increases (e.g., 1 second, then 2, then 4) to avoid overwhelming the API server.

3. Creating a Fallback Mechanism

A fallback is essentially a "Plan B." We wrap our main API call in a try-except block. If the retries fail on the primary model, we catch that error and trigger a second function that calls a different model.

Code Example: Reliable LLM Call

The following example demonstrates how to use the tenacity library to retry a request up to three times before falling back to a different model.


import openai
from tenacity import retry, stop_after_attempt, wait_exponential

client = openai.OpenAI(api_key="your_api_key")

@retry(wait=wait_exponential(multiplier=1, min=2, max=10), stop=stop_after_attempt(3))
def call_primary_model(prompt):
    # This will retry up to 3 times if it fails
    return client.chat.completions.create(
        model="gpt-4",
        messages=[{"role": "user", "content": prompt}]
    )

def safe_llm_request(prompt):
    try:
        return call_primary_model(prompt)
    except Exception as e:
        print(f"Primary model failed: {e}. Switching to fallback...")
        # Fallback to a cheaper/faster model
        return client.chat.completions.create(
            model="gpt-3.5-turbo",
            messages=[{"role": "user", "content": prompt}]
        )

response = safe_llm_request("Explain quantum physics in one sentence.")
print(response.choices[0].message.content)

Common mistakes

  • Retrying on the wrong errors: Don't retry if the error is a "400 Bad Request." If your prompt is formatted incorrectly, retrying 10 times won't fix it; it will only waste time and money. Only retry on server errors (500 series) or rate limits (429).
  • Infinite loops: Always set a stop_after_attempt limit. Without it, if an API provider goes down for an hour, your script might run forever, potentially racking up compute costs.
  • Ignoring the cost: Remember that every retry is a new API call. If you are using a very expensive model, a high retry limit can lead to unexpected bills.
  • Hardcoding API keys: Never put your API keys directly in the code. Use environment variables or a .env file to keep your credentials safe.

One practice task

Create a script that attempts to summarize a paragraph of text using an LLM. Set the retry logic to wait exactly 2 seconds between attempts and stop after 2 failures. If both attempts fail, the "fallback" should return a pre-written string that says: "The service is currently busy, please try again later," instead of calling a second model.
