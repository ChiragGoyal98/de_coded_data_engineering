Calling LLM APIs from Python with retries and fallbacks

Working with LLM APIs is a foundational skill for modern developers, but relying on a single connection can be risky. When you send a request to a provider like OpenAI or Anthropic, things can go wrong: the server might be busy, your internet might flicker, or you might hit a rate limit. To build a production-ready application, you need to implement strategies that make your code resilient to these interruptions. This guide will show you how to handle these errors gracefully using Python.

Why it matters

In a perfect world, APIs would work 100% of the time. In reality, Large Language Models (LLMs) are resource-intensive, and their APIs frequently return errors.

  • Rate Limiting: Most providers limit how many requests you can send per minute. If you exceed this, your code will crash unless you have a retry strategy.
  • Transient Errors: Sometimes a server just times out. Retrying the request a second later often fixes the problem.
  • Model Availability: If GPT-4 is down, having your code automatically switch to a fallback model like GPT-3.5 or Claude ensures your application stays functional.
  • Cost Control: You can use a fallback strategy to try a cheaper model first and only move to an expensive one if the first attempt fails.

Step-by-step walkthrough

To handle these issues efficiently, we use a library called tenacity for retries and a simple try-except structure for fallbacks.

1. Setting up Retries

A "retry" tells your code to try the same request again if it fails. We use "Exponential Backoff," which means the code waits longer between each attempt (e.g., wait 1s, then 2s, then 4s) to avoid overwhelming the server.

2. Implementing Fallbacks

A "fallback" is your Plan B. If the primary model fails after all retry attempts, the code catches the error and tries a different model or provider entirely.

3. The Implementation

The following example uses the tenacity library to manage retries and a standard function to handle the fallback.


import openai
from tenacity import retry, stop_after_attempt, wait_exponential

# Replace with your actual API key
client = openai.OpenAI(api_key="your_api_key")

@retry(wait=wait_exponential(multiplier=1, min=2, max=10), stop=stop_after_attempt(3))
def call_primary_model(prompt):
    """Tries to call the high-end model with retries."""
    return client.chat.completions.create(
        model="gpt-4",
        messages=[{"role": "user", "content": prompt}]
    )

def smart_llm_call(prompt):
    """Main function that handles the fallback logic."""
    try:
        # Try the expensive/primary model first
        return call_primary_model(prompt)
    except Exception as e:
        print(f"Primary model failed: {e}. Switching to fallback...")
        # Fallback to a faster/cheaper model
        return client.chat.completions.create(
            model="gpt-3.5-turbo",
            messages=[{"role": "user", "content": prompt}]
        )

# Usage
response = smart_llm_call("Explain quantum physics in one sentence.")
print(response.choices[0].message.content)

Common mistakes

  • Retrying on 401 Errors: Don't retry if the error is "Unauthorized" or "Invalid API Key." Retrying won't fix a wrong password; it just wastes time and resources.
  • Infinite Loops: Always set a stop_after_attempt limit. Without it, your script might run forever if the API provider has a major outage.
  • Ignoring Latency: Every retry adds time to your user's wait. If your app needs to be "real-time," keep your retry counts low (2 or 3 attempts max).
  • Hardcoding Keys: Never hardcode your API keys in the script. Use environment variables or a .env file.

Use the tenacity library to retry the call 3 times, and then use a fallback block to print a message saying: "Primary model unavailable, using local backup logic instead." This will help you visualize exactly how the code moves from a failing primary attempt to a successful fallback.
