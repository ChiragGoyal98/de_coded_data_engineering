Calling LLM APIs from Python with retries and fallbacks

Building applications with Large Language Models (LLMs) requires a shift in how we think about stability. Unlike traditional databases or internal services, LLMs are hosted behind external APIs that can be unpredictable. When you send a request to a provider like OpenAI or Anthropic, several things can go wrong: the network might drop, the server might be overloaded, or you might hit a rate limit. To build a production-ready application, your Python code must be resilient enough to handle these hiccups without crashing.

Why it matters

Reliability is the difference between a prototype and a product. If your application crashes every time an API returns a 503 error, users will quickly lose trust. Implementing retries ensures that temporary network glitches or brief server overloads don't break your workflow. Meanwhile, fallbacks provide a safety net; if your primary, high-performance model is down or too busy, your code can automatically switch to a secondary model to keep the service running. This layered approach minimizes downtime and provides a much smoother user experience.

Step-by-step walkthrough

1. Set up your environment

To handle retries elegantly, the Python community often uses a library called tenacity. It allows you to add retry logic to any function using decorators. You will also need an LLM client, such as the openai library.


pip install openai tenacity

2. Implementing retry logic

Retrying a request isn't just about doing it again; it's about doing it smartly. If a server is overloaded, hitting it again immediately will only make the problem worse. We use "exponential backoff," which means we wait longer between each subsequent attempt.


from openai import OpenAI
from tenacity import retry, stop_after_attempt, wait_random_exponential

client = OpenAI()

@retry(wait=wait_random_exponential(min=1, max=60), stop=stop_after_attempt(3))
def call_llm_with_retry(prompt):
    return client.chat.completions.create(
        model="gpt-4o",
        messages=[{"role": "user", "content": prompt}]
    )

3. Creating a fallback mechanism

A fallback mechanism acts as a Plan B. If the primary function fails after all retry attempts, we catch the exception and try a different model or provider. This is useful for maintaining uptime even during major service outages.


def robust_llm_call(prompt):
    try:
        # Attempt the primary model with retries
        return call_llm_with_retry(prompt)
    except Exception as e:
        print(f"Primary model failed: {e}. Switching to fallback...")
        # Plan B: Use a cheaper or more available model
        return client.chat.completions.create(
            model="gpt-3.5-turbo",
            messages=[{"role": "user", "content": prompt}]
        )

Common mistakes

  • Retrying on 4xx errors: If the API returns a 401 (Unauthorized) or 400 (Bad Request), retrying won't help. These are client-side errors that require a code or configuration change, not a retry.
  • Missing timeout settings: Some API calls can hang indefinitely. Always ensure your underlying HTTP client has a reasonable timeout set so your application doesn't stay frozen.
  • Infinite retries: Never set your retry logic to "forever." If the service is truly down, you will consume system resources and potentially rack up unexpected logs or costs.
  • Ignoring rate limits: While retries help with rate limits, the best practice is to track your usage and slow down your requests before the API forces you to stop.

One practice task

Create a Python script that attempts to summarize a paragraph using an expensive "flagship" model. Use tenacity to retry the request 3 times if it fails. If all three attempts fail, write a fallback block that performs the same summary using a smaller, faster model (like gpt-4o-mini or a local Llama model). Print which model eventually provided the successful response to your console.
