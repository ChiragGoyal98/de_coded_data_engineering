Calling LLM APIs from Python with retries and fallbacks

When you build applications using Large Language Model (LLM) APIs like OpenAI, Anthropic, or Google Gemini, you are relying on external servers that you do not control. Sometimes these servers get overwhelmed, leading to rate limit errors, or they might experience temporary downtime. If your Python script isn't prepared for these hiccups, your entire application could crash or hang indefinitely. Learning how to handle these interruptions gracefully is a fundamental skill for any developer working with AI.

Why it matters

In a production environment, reliability is just as important as the quality of the AI's response. LLM APIs are prone to specific types of failures: transient network errors, rate limiting (too many requests at once), and model timeouts. If a user is waiting for a response and the API fails, a simple retry mechanism can fix the issue in milliseconds without the user ever knowing there was a problem. Furthermore, fallbacks-switching to a different model if the primary one is down-ensure that your app remains functional even during major outages.

Step-by-step walkthrough

To manage these issues, we will use the openai library for the API calls and a popular library called tenacity to handle the retry logic.

1. Setting up the Environment

First, install the necessary libraries using pip. The tenacity library is the industry standard for adding retry behavior to any Python function.


pip install openai tenacity

2. Implementing Retries with Exponential Backoff

Exponential backoff is a strategy where you wait longer between each successive retry. This prevents you from spamming a server that is already struggling.


from openai import OpenAI
from tenacity import retry, stop_after_attempt, wait_exponential

client = OpenAI(api_key="your_api_key_here")

@retry(wait=wait_exponential(min=1, max=60), stop=stop_after_attempt(5))
def call_llm(prompt):
    response = client.chat.completions.create(
        model="gpt-3.5-turbo",
        messages=[{"role": "user", "content": prompt}]
    )
    return response.choices[0].message.content

In this snippet, the @retry decorator tells Python to try the function again if it fails. It starts with a 1-second wait, doubles it each time, but never waits more than 60 seconds, and gives up after 5 attempts.

3. Implementing a Fallback Mechanism

A fallback is your "Plan B." If GPT-4 is unavailable, you might want to try a smaller, faster model like GPT-3.5 or a different provider entirely.


def robust_llm_call(prompt):
    try:
        # Attempt primary model
        return call_llm(prompt)
    except Exception as e:
        print(f"Primary model failed: {e}. Switching to fallback...")
        # Fallback logic
        response = client.chat.completions.create(
            model="gpt-3.5-turbo",
            messages=[{"role": "user", "content": prompt}]
        )
        return response.choices[0].message.content

Common mistakes

  • Retrying on user errors: Don't retry if the error is a "400 Bad Request." This usually means your code or prompt is wrong; retrying won't fix it and will only waste your API credits.
  • Infinite loops: Always set a stop_after_attempt limit. Without it, your script might run forever if the API service has a prolonged outage.
  • Ignoring logs: If a retry happens, you should log it. If you don't, you might have a "silent failure" where your app feels slow to users, but you don't know why because you aren't seeing the internal errors.

One practice task

If it fails after 3 tries, the script should automatically catch the error and attempt the second model in the list. Print which model eventually provided the successful response.
