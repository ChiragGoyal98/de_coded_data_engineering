Calling LLM APIs from Python with retries and fallbacks

Building applications with Large Language Models (LLMs) requires moving beyond simple script execution to robust system design. When you connect to services like OpenAI, Anthropic, or Google Gemini via their Python SDKs, you are relying on a remote server. These servers can sometimes be overloaded, experience temporary outages, or hit rate limits. To build a production-ready application, your code needs to be resilient enough to handle these hiccups without crashing or leaving the user hanging.

Why it matters

In a local environment, a failed API call is a minor annoyance. In a real-world application, it can lead to a broken user experience or data loss. Implementing retries and fallbacks is crucial for several reasons:

  • Handling Rate Limits: APIs often have "Tokens Per Minute" (TPM) or "Requests Per Minute" (RPM) limits. A retry strategy allows your code to wait and try again once the window resets.
  • Service Stability: Even the most reliable providers have "hiccups" or 503 Service Unavailable errors. Automated retries can bypass these brief outages.
  • Cost and Availability: If a premium model like GPT-4o is down or too slow, a fallback strategy allows your system to automatically switch to a cheaper, faster model like GPT-4o-mini to maintain service continuity.
  • User Experience: Instead of showing an error message, your application stays functional by silently resolving the issue in the background.

Step-by-step walkthrough

To handle these issues gracefully, we use two main patterns: Retries (doing the same thing again) and Fallbacks (doing something else if the first thing fails). We will use the tenacity library, which is the industry standard for retries in Python.

1. Setting up the environment

First, you need to install the necessary libraries. You will need the OpenAI SDK and Tenacity.


pip install openai tenacity

2. Implementing basic retries

The goal of a retry is to wait a few seconds and try again when a specific error occurs. We use "exponential backoff," which means we wait longer after each failed attempt to avoid spamming the server.


import openai
from tenacity import retry, stop_after_attempt, wait_random_exponential, retry_if_exception_type

client = openai.OpenAI(api_key="your_api_key")

@retry(
    retry=retry_if_exception_type(openai.RateLimitError),
    wait=wait_random_exponential(min=1, max=60),
    stop=stop_after_attempt(3)
)
def call_llm(prompt):
    return client.chat.completions.create(
        model="gpt-4o",
        messages=[{"role": "user", "content": prompt}]
    )

In this snippet, @retry tells Python to rerun the function up to 3 times if a RateLimitError occurs, waiting a random amount of time between 1 and 60 seconds between tries.

3. Adding a fallback model

If the retries fail (perhaps the model is completely down), we want to fall back to a different model. We can wrap our primary function in a try-except block.


def safe_llm_call(prompt):
    try:
        # Attempt the primary, high-quality model
        return call_llm(prompt)
    except Exception as e:
        print(f"Primary model failed: {e}. Switching to fallback.")
        # Fallback to a faster, more available model
        return client.chat.completions.create(
            model="gpt-4o-mini",
            messages=[{"role": "user", "content": prompt}]
        )

Common mistakes

  • Retrying on every error: You should only retry on "transient" errors (like network timeouts or rate limits). Do not retry if the error is a BadRequestError (e.g., your prompt was too long), as the result will never change.
  • No maximum limit: Never set a retry to run infinitely. If a service is down for an hour, an infinite loop will waste resources and potentially lock your thread.
  • Ignoring the logs: If your application is constantly hitting the fallback model, you might have an underlying configuration issue or a depleted API balance. Always log when a fallback occurs.
  • Short timeouts: LLMs take time to generate text. Setting a connection timeout that is too aggressive might trigger a retry before the model has even finished "thinking."

One practice task

Create a Python script that attempts to summarize a paragraph of text using the model name gpt-expensive-fake-model (which doesn't exist). Use a try-except block to catch the error and successfully provide a summary using a real model like gpt-4o-mini instead. This will simulate a "Model Not Found" or "Service Down" scenario.
