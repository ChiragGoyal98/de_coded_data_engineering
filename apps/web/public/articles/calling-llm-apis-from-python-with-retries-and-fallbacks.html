Calling LLM APIs from Python with retries and fallbacks

Building applications with Large Language Models often involves connecting to external servers via an API. While these services are powerful, they are not always reliable. Network hiccups, temporary server overloads, or hitting rate limits can cause your Python script to crash unexpectedly. Learning how to handle these interruptions gracefully by implementing retries and fallbacks is a fundamental skill for any developer working with AI.

Why it matters

When you move from a local script to a production app, "happy path" coding-assuming everything will work perfectly-is dangerous. LLM APIs are particularly prone to issues for three reasons:

  • Rate Limiting: Most providers restrict how many requests you can send per minute. If you exceed this, the API will reject your call with a 429 error.
  • Server Latency: LLMs are computationally heavy. Sometimes the server takes too long to respond, leading to a timeout.
  • Service Outages: Even giants like OpenAI or Anthropic experience downtime. If your app relies on a single model, an outage means your app is dead.

Implementing retries ensures that temporary glitches don't break your app, while fallbacks ensure that if one model fails, a secondary model can take over.

Step-by-step walkthrough

1. Setting up the Environment

To handle retries professionally, we use a library called tenacity. It allows you to add "retry logic" to any function using decorators. You will also need the openai library (though these concepts apply to any LLM provider).


pip install openai tenacity

2. Implementing Retries with Exponential Backoff

A "retry" tells Python to try the request again if it fails. "Exponential backoff" means waiting longer between each subsequent attempt (e.g., wait 1s, then 2s, then 4s) so you don't overwhelm the server.

3. Adding Fallback Logic

A fallback is your "Plan B." If the primary model (like GPT-4) fails repeatedly, the code should catch that final error and try a different, often cheaper or more stable model (like GPT-4o-mini).

Example Code

Here is a robust way to call an LLM API using these patterns:


import openai
from tenacity import retry, stop_after_attempt, wait_random_exponential, retry_if_exception_type

client = openai.OpenAI(api_key="your_api_key_here")

# Define which errors are worth retrying (e.g., Rate Limits or Server Errors)
@retry(
    wait=wait_random_exponential(min=1, max=60), 
    stop=stop_after_attempt(3),
    retry=retry_if_exception_type((openai.RateLimitError, openai.APIConnectionError))
)
def call_llm_with_retry(model, prompt):
    print(f"Attempting request with {model}...")
    response = client.chat.completions.create(
        model=model,
        messages=[{"role": "user", "content": prompt}]
    )
    return response.choices[0].message.content

def safe_llm_call(prompt):
    try:
        # Try the primary, high-quality model first
        return call_llm_with_retry("gpt-4", prompt)
    except Exception as e:
        print(f"Primary model failed: {e}. Switching to fallback...")
        # Fallback to a different model if the primary fails 3 times
        return call_llm_with_retry("gpt-3.5-turbo", prompt)

# Usage
result = safe_llm_call("Explain quantum physics in one sentence.")
print(f"Final Result: {result}")

Common mistakes

  • Retrying on Authentication Errors: If your API key is wrong (401 error), retrying 100 times won't fix it. Only retry on "transient" errors like 429 (Rate Limit) or 500/503 (Server Error).
  • Infinite Retries: Never set a retry loop to run indefinitely. If the service is actually down, your code will hang forever and potentially rack up a massive bill once the service returns.
  • Ignoring the Logs: If a fallback occurs, make sure you log it. If you don't, you might not realize your primary model has been failing for days.

One practice task

Modify the example code provided above to include a third fallback option. If "gpt-4" fails and "gpt-3.5-turbo" also fails, have the function return a hardcoded string like "The AI is currently busy, please try again later" instead of crashing the program.
