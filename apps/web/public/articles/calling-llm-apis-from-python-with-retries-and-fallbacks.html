Calling LLM APIs from Python with retries and fallbacks

Introduction

Building an application with Large Language Models (LLMs) involves more than just sending a prompt and receiving a response. Because these models are hosted on remote servers, your code is at the mercy of internet stability, provider downtime, and strict rate limits. If you do not account for these interruptions, your application will crash the moment an API provider experiences a slight hiccup or when your usage spikes. Implementing retries and fallbacks ensures that your code is resilient and can recover from common network errors without manual intervention.

Why it matters

Reliability is the cornerstone of any professional software. When using LLM APIs, several factors can break your connection. Rate limits are perhaps the most common; providers like OpenAI or Anthropic restrict how many requests you can send per minute. Additionally, large models often suffer from high latency or occasional 500-level server errors.

Without a retry mechanism, a single "Rate limit exceeded" error terminates your script. Without a fallback mechanism, a total outage of your primary model provider leaves your users with a broken tool. By automating these processes, you improve the user experience, maintain service uptime, and ensure that your application can handle high-traffic periods gracefully.

Step-by-step walkthrough

To handle these issues in Python, the most effective approach is to use a library specifically designed for retries, such as tenacity, combined with a standard try-except block for fallbacks.

1. Setting up retries with Exponential Backoff

A simple retry (trying again immediately) often fails because it hits the API before the rate limit "cool down" period has passed. Instead, we use "Exponential Backoff," which increases the waiting time between each attempt.

  • Install the necessary library: pip install tenacity openai
  • Decorate your function with retry logic to handle specific exceptions.

2. Implementing a Fallback

A fallback is your "Plan B." If your preferred model (like GPT-4) is unavailable or too busy, your code should automatically catch that error and attempt the request using a secondary model (like GPT-4o-mini or a local model).

3. The Code Example

The following example demonstrates how to retry a request up to three times with increasing delays, and then switch to a secondary model if all retries fail.


import openai
from tenacity import retry, stop_after_attempt, wait_random_exponential, retry_if_exception_type

client = openai.OpenAI(api_key="YOUR_API_KEY")

# Retry logic: Wait 1-20s between hits, stop after 3 tries
@retry(
    wait=wait_random_exponential(min=1, max=20),
    stop=stop_after_attempt(3),
    retry=retry_if_exception_type(openai.RateLimitError)
)
def call_primary_llm(prompt):
    return client.chat.completions.create(
        model="gpt-4",
        messages=[{"role": "user", "content": prompt}]
    )

def smart_llm_call(prompt):
    try:
        # Attempt the primary model with retries
        return call_primary_llm(prompt)
    except Exception as e:
        print(f"Primary model failed: {e}. Switching to fallback...")
        # Fallback to a faster/cheaper model
        return client.chat.completions.create(
            model="gpt-4o-mini",
            messages=[{"role": "user", "content": prompt}]
        )

Common mistakes

  • Retrying on every error: You should only retry on errors that might be temporary (like rate limits or server timeouts). Do not retry on "Authentication Errors" or "Invalid Request Errors," as those require code changes to fix.
  • Infinite loops: Never set a retry to run indefinitely. If an API provider is down for an hour, your script will hang forever. Always set a stop_after_attempt limit.
  • Hard-coding API keys: Beginners often paste their keys directly into the script. Always use environment variables or a .env file to keep your credentials secure while testing your retry logic.
  • Ignoring logs: If your code is silently retrying and eventually succeeding, you might not realize you are hitting rate limits constantly. Always log your retry attempts so you can monitor the health of your integration.
