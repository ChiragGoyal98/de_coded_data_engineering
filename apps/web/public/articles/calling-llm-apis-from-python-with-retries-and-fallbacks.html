Calling LLM APIs from Python with retries and fallbacks

When building applications with Large Language Models (LLMs), the initial focus is often on crafting the perfect prompt. However, once you move from a local script to a real-world application, you quickly realize that the connection between your code and the API is the most fragile link. APIs can be slow, they can hit rate limits, or they might simply go offline for a few minutes. If your code is not prepared for these hiccups, your entire application will crash the moment a single request fails.

Why it matters

In a professional development environment, we aim for "resiliency." This means designing your software to survive and recover from common failures. When working with LLMs, resiliency matters for three main reasons:

  • Rate Limiting: API providers like OpenAI or Anthropic limit how many requests you can make per minute. If you exceed this, the API will reject your call.
  • Transient Errors: Sometimes a server is overloaded or a network packet gets lost. These are temporary issues that usually disappear if you simply try again a second later.
  • High Availability: If a specific model (like GPT-4) is experiencing high latency or an outage, having a "fallback" to a different model (like GPT-3.5 or a Claude model) ensures your user still gets an answer.

Step-by-step walkthrough

To handle these issues effectively in Python, we use two main techniques: Retries (doing it again) and Fallbacks (doing something else).

1. Implementing Retries with Tenacity

While you could write your own "while" loops to retry a failed call, the industry standard is to use a library called tenacity. It allows you to add "decorators" to your functions that handle the timing and logic of retrying automatically.

The most important concept here is "Exponential Backoff." Instead of retrying every 1 second (which might worsen a rate-limit issue), backoff means waiting longer between each attempt (1s, 2s, 4s, 8s).

2. Implementing Fallbacks

A fallback is your "Plan B." If the primary model fails after all retry attempts are exhausted, the code should catch the error and try a different, often cheaper or faster, model to ensure the application remains functional.

3. Code Example

Here is a concise example using the openai and tenacity libraries to handle a request with both retries and a fallback.


import openai
from tenacity import retry, stop_after_attempt, wait_exponential, retry_if_exception_type

# Setup the retry logic: retry 3 times with exponential wait
@retry(
    retry=retry_if_exception_type(openai.RateLimitError),
    stop=stop_after_attempt(3),
    wait=wait_exponential(multiplier=1, min=4, max=10)
)
def call_primary_model(prompt):
    client = openai.OpenAI()
    return client.chat.completions.create(
        model="gpt-4",
        messages=[{"role": "user", "content": prompt}]
    )

def smart_llm_call(prompt):
    try:
        # Try the primary model with retries
        return call_primary_model(prompt)
    except Exception as e:
        print(f"Primary model failed: {e}. Switching to fallback...")
        # Fallback to a different model if primary fails
        client = openai.OpenAI()
        return client.chat.completions.create(
            model="gpt-3.5-turbo",
            messages=[{"role": "user", "content": prompt}]
        )

Common mistakes

  • Retrying everything: Do not retry errors like "Authentication Failed" (401). If your API key is wrong, retrying 10 times won't fix it; it will only waste time. Only retry 429 (Rate Limit) and 500-level (Server) errors.
  • Fixed intervals: Avoid retrying every 1 second exactly. If a thousand users all retry at the exact same 1-second interval, it creates a "thundering herd" that keeps the API server crashed.
  • No logging: When a fallback occurs, make sure you log it. If you don't, you might never realize your primary model is failing 50% of the time.

One practice task

Create a Python script that attempts to call an LLM API. Use the tenacity library to configure a retry strategy that waits a minimum of 2 seconds and a maximum of 5 seconds between attempts, but stops entirely after 5 failed tries. To test it without spending money, try running it with an intentional typo in your model name (e.g., "gpt-4-typo") and watch how the retry logic triggers in your console.
