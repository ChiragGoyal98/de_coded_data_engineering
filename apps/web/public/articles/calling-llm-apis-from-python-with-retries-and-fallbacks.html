Calling LLM APIs from Python with retries and fallbacks

When building applications powered by Large Language Models (LLMs), your code relies on a stable connection to a remote server. Unlike local functions, API calls can fail for many reasons: the provider might be overloaded, your internet might flicker, or you might hit a rate limit. To build a production-ready application, you need to handle these interruptions gracefully so your user doesn't just see a "Connection Error" message.

Why it matters

Reliability is the difference between a toy project and a professional tool. LLM providers like OpenAI or Anthropic often experience "transient errors," which are temporary glitches that resolve themselves in seconds. If your code stops immediately upon seeing an error, you are missing out on a successful response that was just a millisecond away.

Furthermore, LLMs are expensive and subject to strict rate limits. Implementing a retry strategy ensures you don't waste your quota on failed attempts, while a fallback strategy ensures that if your primary model (like GPT-4) is down, your application can automatically switch to a secondary, more available model (like GPT-3.5 or a local Llama model) to keep the service running.

Step-by-step walkthrough

1. Setting up the environment

First, you need a way to manage retries without writing messy loops. The most popular Python library for this is tenacity. It allows you to add retry logic to any function using "decorators."


pip install tenacity openai

2. Implementing Retries

A retry strategy tells your code to "try again" if a specific error occurs. You should use exponential backoff, which means the wait time between retries increases (1s, 2s, 4s, etc.). This prevents you from spamming the API server and potentially getting banned.

3. Implementing Fallbacks

A fallback is your "Plan B." In Python, this is usually handled with a try-except block. If the primary function fails after all retry attempts, the except block catches the final error and triggers a call to a different model or returns a pre-written "safe" response.

4. Putting it together

Here is a concise example using tenacity to handle retries and a standard Python block for the fallback logic.


import openai
from tenacity import retry, stop_after_attempt, wait_exponential

# This decorator tells Python to retry up to 3 times
# It waits 1 second, then 2, then 4 between tries
@retry(stop=stop_after_attempt(3), wait=wait_exponential(multiplier=1, min=4, max=10))
def call_primary_llm(prompt):
    print("Attempting to call Primary Model...")
    # This would be your actual API call
    return openai.ChatCompletion.create(model="gpt-4", messages=[{"role": "user", "content": prompt}])

def smart_llm_call(prompt):
    try:
        return call_primary_llm(prompt)
    except Exception as e:
        print(f"Primary failed after retries: {e}")
        print("Switching to Fallback Model...")
        # Fallback to a cheaper/faster model
        return openai.ChatCompletion.create(model="gpt-3.5-turbo", messages=[{"role": "user", "content": prompt}])

Common mistakes

  • Retrying on every error: You should only retry on "retryable" errors like timeouts or 500-series server errors. If you have a syntax error or an invalid API key, retrying 10 times will not fix it and will only waste time.
  • Immediate retries: If the server is overloaded, hitting it again instantly will likely cause another failure. Always use a "wait" or "backoff" period.
  • Infinite loops: Never set a retry to run forever. Always define a stop_after_attempt limit to ensure your program eventually moves on or alerts you to the problem.
  • Ignoring the fallback's failure: Remember that your fallback model can also fail. Always have a final "Plan C"-usually a graceful error message for the user.
