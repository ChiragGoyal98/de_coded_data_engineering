Calling LLM APIs from Python with retries and fallbacks

Large Language Models are becoming the backbone of modern applications, but they are not perfect. When you connect to an API like OpenAI or Anthropic, you are relying on an external service that can experience hiccups. A simple request might work nine times out of ten, but that one failure can crash your entire program if you are not prepared. Learning how to handle these interruptions gracefully is a fundamental skill for any developer working with AI.

Why it matters

Reliability is the difference between a prototype and a production-ready application. LLM APIs often face high demand, leading to three common issues:

  • Rate Limiting: Most providers restrict how many requests you can send per minute. If you exceed this, you get a 429 error.
  • Server Overload: Sometimes the AI provider's servers are simply too busy to handle your request, resulting in a 500-series error.
  • Network Instability: Brief flickers in your internet connection can interrupt a data transfer mid-stream.

Without retries, your application stops. Without fallbacks, your user receives an error message instead of an answer. Implementing these patterns ensures your app remains functional even when things go wrong on the provider's end.

Step-by-step walkthrough

To handle these issues effectively, we use two main strategies: Exponential Backoff (retries) and Model Switching (fallbacks).

1. Implementing Retries with Tenacity

Instead of writing complex loops, we can use a Python library called tenacity. It allows us to add a "decorator" to our functions that tells Python to try again if the function fails.

We use exponential backoff, which means the script waits longer between each attempt (e.g., 2 seconds, 4 seconds, 8 seconds). This gives the API provider time to recover and prevents you from spamming their servers.

2. Implementing Fallbacks

A fallback is your "Plan B." If your primary model (like GPT-4) is down or too slow, your code should automatically catch that failure and attempt the request using a different, often cheaper model (like GPT-3.5 or a local model).

3. Putting it together

Below is a concise example using the OpenAI library and Tenacity.


import os
from openai import OpenAI
from tenacity import retry, stop_after_attempt, wait_exponential

client = OpenAI(api_key="YOUR_API_KEY")

# This decorator tells the function to retry 3 times with increasing wait times
@retry(stop=stop_after_attempt(3), wait=wait_exponential(multiplier=1, min=2, max=10))
def call_llm_with_retry(model, prompt):
    print(f"Attempting request with {model}...")
    return client.chat.completions.create(
        model=model,
        messages=[{"role": "user", "content": prompt}]
    )

def robust_llm_call(prompt):
    try:
        # Try the premium model first
        return call_llm_with_retry("gpt-4", prompt)
    except Exception as e:
        print(f"GPT-4 failed after retries. Switching to fallback. Error: {e}")
        # Fallback to a different model if the first one fails completely
        return call_llm_with_retry("gpt-3.5-turbo", prompt)

# Usage
response = robust_llm_call("Explain quantum physics in one sentence.")
print(response.choices[0].message.content)

Common mistakes

  • Infinite Retries: Never set your retry limit to infinite. If the API is truly down, your script will hang forever and potentially drain your API credits if it eventually succeeds many times.
  • Retrying Every Error: You should only retry on "retryable" errors like timeouts or rate limits. Do not retry if the error is a "401 Unauthorized" (your API key is wrong) or a "400 Bad Request" (your prompt is formatted incorrectly).
  • Ignoring Costs: If your fallback model is significantly more expensive than your primary model, a massive failure could result in an unexpected bill. Always know the price difference between your Plan A and Plan B.

One practice task

Create a script that attempts to summarize a paragraph of text. Implement a retry strategy that waits exactly 5 seconds between attempts (instead of exponential backoff) and stops after 4 attempts. For the fallback, if the API fails, have the function return a pre-written string that says: "The AI is currently resting. Please try again later." instead of calling a second model.
