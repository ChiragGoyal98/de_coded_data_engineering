Calling LLM APIs from Python with retries and fallbacks

When building applications with Large Language Models (LLMs), we often rely on external APIs like OpenAI, Anthropic, or Google Gemini. While these services are powerful, they are not perfect. Network hiccups, rate limits, and server-side timeouts can cause your application to crash if you do not handle them properly. Learning how to build resilient code is a core skill for any developer working in the AI space.

Why it matters

In a production environment, "happy path" coding-where you assume everything will work perfectly-is a recipe for failure. LLM APIs are particularly prone to issues for two main reasons:

  • Rate Limiting: Most providers restrict how many requests you can send per minute. If you exceed this, the API will temporarily block you.
  • Transient Errors: These are temporary glitches on the server side or in the network. A request might fail now but succeed if you try again in two seconds.

Without retries and fallbacks, your user sees an error message, and your application looks unprofessional. By implementing these patterns, you ensure your app stays "up" even when the API provider is having a bad day.

Step-by-step walkthrough

To handle these issues gracefully in Python, the most popular approach is using a library called tenacity for retries, combined with standard Python try-except blocks for fallbacks.

1. Setting up Retries with Tenacity

The tenacity library allows you to wrap your API calls in a "retry" decorator. This tells Python: "If this function fails, wait a bit and try again."

We typically use Exponential Backoff. This means the wait time increases after every failure (e.g., wait 1 second, then 2, then 4), which prevents you from spamming a server that is already struggling.

2. Implementing a Fallback

A fallback is your "Plan B." If the primary model (like GPT-4) is down or keeps failing after several retries, you catch that error and call a different, often cheaper or faster model (like GPT-4o-mini or a local Llama model) to fulfill the request.

3. Putting it into code

Here is a concise example showing both strategies. You will need to pip install openai tenacity.


import openai
from tenacity import retry, stop_after_attempt, wait_exponential

client = openai.OpenAI(api_key="your_api_key")

# The retry decorator handles temporary glitches
@retry(wait=wait_exponential(multiplier=1, min=2, max=10), stop=stop_after_attempt(3))
def call_primary_llm(prompt):
    return client.chat.completions.create(
        model="gpt-4o",
        messages=[{"role": "user", "content": prompt}]
    )

def safe_llm_call(prompt):
    try:
        # Attempt the primary call with retries
        return call_primary_llm(prompt)
    except Exception as e:
        print(f"Primary model failed after retries. Switching to fallback. Error: {e}")
        # Fallback to a smaller, faster model
        return client.chat.completions.create(
            model="gpt-4o-mini",
            messages=[{"role": "user", "content": prompt}]
        )

# Usage
response = safe_llm_call("Explain quantum physics in one sentence.")
print(response.choices[0].message.content)

Common mistakes

  • Infinite Loops: Not setting a stop_after_attempt limit. If the API is truly down, your code will run forever, potentially costing you money or crashing your local machine.
  • Retrying "Dead" Errors: Some errors should not be retried. For example, if your API key is invalid (401 Unauthorized), retrying 5 times won't fix it. Only retry on 429 (Rate Limit) or 500-series (Server Error) codes.
  • Ignoring Logs: If you don't log when a fallback happens, you might not realize your primary model is failing 90% of the time, leading to a degraded experience for your users without you knowing.

One practice task

Try to modify the code example above to include a third fallback. Create a function where if the first model fails, it tries a second model, and if that also fails, it returns a hardcoded "canned response" (e.g., "I'm sorry, I'm having trouble connecting right now. Please try again later.") instead of crashing the program.
