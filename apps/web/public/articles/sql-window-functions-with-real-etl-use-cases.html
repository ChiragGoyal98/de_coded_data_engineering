SQL Window Functions with Real ETL Use Cases

SQL window functions are often the "aha!" moment for many data beginners. While standard aggregate functions like SUM or AVG collapse multiple rows into a single result, window functions perform calculations across a set of table rows that are somehow related to the current row. The most important distinction is that window functions do not group the result into a single output row; instead, the rows retain their separate identities. This allows you to see the individual data points alongside their calculated aggregates.

Why Window Functions Matter in ETL

In the world of Extract, Transform, Load (ETL), window functions are indispensable tools for data cleaning and transformation. They are the primary way data engineers handle deduplication, which involves identifying and removing duplicate records by ranking them based on a timestamp. They also simplify complex analytical tasks, such as calculating month-over-month growth, finding the difference between a current and previous transaction, or creating running totals for financial reports. Without window functions, these tasks would require cumbersome self-joins that are difficult to read and slow to execute.

Step-by-Step Walkthrough

To understand how a window function works, you need to break down its specific syntax, which typically follows this pattern: FUNCTION() OVER (PARTITION BY ... ORDER BY ...).

1. The OVER Clause

The OVER clause is what signals to SQL that you are using a window function rather than a standard aggregate. If you leave the parentheses empty, the "window" is simply the entire dataset.

2. PARTITION BY

This acts like a GROUP BY but for the window. It divides the result set into partitions. For example, if you partition by customer_id, the function will calculate values separately for each customer. When the customer_id changes, the calculation starts over.

3. ORDER BY

Inside the window, the order of rows matters for many functions. If you are calculating a running total or a rank, you must tell SQL which column determines the sequence (e.g., order_date).

4. Real-World ETL Example: Deduplication

One of the most common ETL use cases is selecting the "latest" record for a user when the source system sends multiple updates. By using ROW_NUMBER(), we can assign a unique number to each record within a group and then filter for the first one.


SELECT 
    user_id, 
    email, 
    updated_at,
    ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY updated_at DESC) as rank_id
FROM raw_users_table
-- In a real ETL pipeline, you would wrap this in a CTE 
-- and filter WHERE rank_id = 1

Common Mistakes to Avoid

  • Using Window Functions in WHERE: You cannot use a window function directly in a WHERE clause because window functions are processed after the filtering stage. To filter based on a window result (like our rank_id above), you must use a Subquery or a Common Table Expression (CTE).
  • Confusing RANK() and DENSE_RANK(): If two rows have the same value, RANK() will skip the next number (1, 2, 2, 4), while DENSE_RANK() will not (1, 2, 2, 3). Choosing the wrong one can lead to "missing" data in your reports.
  • Forgetting the ORDER BY: For functions like LEAD, LAG, or ROW_NUMBER, forgetting the ORDER BY clause within the window will lead to unpredictable results because SQL does not guarantee a default row order.

Practice Task

Imagine you have a table called daily_sales with columns sale_date and amount. Write a query using the SUM() window function to create a third column called running_total that adds up the sales from the first date up to the current row's date.

Hint: Use ORDER BY sale_date inside your OVER clause without a PARTITION BY.
