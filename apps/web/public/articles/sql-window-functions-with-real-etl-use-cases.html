SQL Window Functions with Real ETL Use Cases

In the world of data engineering and analysis, SQL window functions are often described as a superpower. Unlike standard aggregate functions that group rows into a single output, window functions allow you to perform calculations while keeping all your individual records visible. This capability is essential for building data pipelines where you need to compare a specific row against a set of related data points, such as calculating a running total or finding the difference between today's and yesterday's sales.

Why it Matters in ETL

In Extract, Transform, Load (ETL) processes, your goal is often to clean and enrich data. Standard SQL aggregates like SUM or AVG combined with GROUP BY collapse your data, which means you lose the granular details of individual transactions.

Window functions are critical for ETL for three main reasons:

  • Deduplication: Identifying and removing duplicate records by ranking them based on a timestamp.
  • Delta Calculations: Comparing the current row to the previous row to find growth rates or changes in status.
  • Running Totals: Creating cumulative sums for financial reporting without needing complex self-joins that slow down performance.

Step-by-Step Walkthrough

The "Window" in window functions refers to the set of rows the function operates on. You define this window using the OVER() clause.

1. The Basic Syntax

Every window function follows this pattern:

SELECT column, FUNCTION() OVER (PARTITION BY column_a ORDER BY column_b) FROM table

  • PARTITION BY: This divides the data into logical groups (like "folders").
  • ORDER BY: This determines the sequence of rows within those groups.

2. Ranking Data for Deduplication

One of the most common ETL tasks is keeping only the "latest" record for a user. We use ROW_NUMBER() for this.


SELECT 
    user_id, 
    status, 
    updated_at,
    ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY updated_at DESC) as rank_order
FROM user_updates;

In this example, the row with rank_order = 1 is the most recent update for each user.

3. Calculating Running Totals

To see how revenue grows over time, we use SUM() as a window function. By providing an ORDER BY inside the OVER() clause, SQL knows to add the current row to the sum of all previous rows.


SELECT 
    sale_date, 
    amount,
    SUM(amount) OVER (ORDER BY sale_date) as running_total
FROM daily_sales;

4. Comparing Across Rows with LAG

If you need to know if a price went up or down compared to the previous day, use LAG(). This "looks back" at the previous row in the partition.


SELECT 
    product_id, 
    price,
    LAG(price) OVER (PARTITION BY product_id ORDER BY change_date) as previous_price
FROM price_history;

Common Mistakes

  • Using Window Functions in WHERE: You cannot use a window function directly in a WHERE clause. Because window functions are calculated after the filtering phase, you must use a Subquery or a Common Table Expression (CTE) to filter by a ranked value.
  • Confusing RANK vs DENSE_RANK: RANK() will skip numbers if there is a tie (1, 2, 2, 4), while DENSE_RANK() will not (1, 2, 2, 3).
  • Omitting ORDER BY: For functions like SUM() or ROW_NUMBER(), omitting the ORDER BY clause inside the window will lead to unpredictable results or a sum of the entire partition rather than a running total.

Practice Task

Suppose you have a table named subscriptions with columns customer_id, plan_type, and start_date.

Goal: Write a query that shows each customer's current plan and their "previous" plan using the LAG() function.

  • Use PARTITION BY customer_id to group the history by user.
  • Use ORDER BY start_date to ensure you are looking at the plans in chronological order.
  • Name the new column previous_plan_type.
