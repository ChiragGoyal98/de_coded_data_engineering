SQL Window Functions with Real ETL Use Cases

SQL window functions are one of the most powerful tools in a data engineer's toolkit. Unlike standard aggregate functions like SUM or AVG, which collapse multiple rows into a single result, window functions allow you to perform calculations across a set of rows while still preserving the individual identity of each row. Imagine being able to see a specific transaction and its contribution to the monthly total in the same line; that is the magic of window functions.

Why it matters in ETL

In the world of Data Engineering and ETL (Extract, Transform, Load), data is rarely clean. You often deal with duplicate records, out-of-order events, or the need to calculate trends over time. Window functions are essential for these tasks because:

  • Deduplication: You can identify the "latest" version of a record in a staging table using ranking functions.
  • Running Totals: They allow you to calculate cumulative sums for financial reporting without complex self-joins.
  • Gap Analysis: You can compare a current row's value with the previous row (using LAG) to find missing data or calculate time differences.
  • Efficiency: They are often more performant than subqueries or self-joins for complex analytical tasks.

Step-by-step walkthrough

To understand how these work, you need to master the OVER clause, which defines the "window" of data the function looks at.

1. The Basic Syntax

The standard structure of a window function is:

FUNCTION_NAME() OVER (PARTITION BY column_a ORDER BY column_b)

  • PARTITION BY: This divides the result set into groups (like GROUP BY, but without collapsing rows).
  • ORDER BY: This defines the sequence of rows within each partition.

2. Common ETL Use Case: Deduplication

Suppose you have a table of user profile updates where a user might have five different entries, but you only want the most recent one. You can use ROW_NUMBER() to rank them by date.


SELECT 
    user_id, 
    email, 
    updated_at,
    ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY updated_at DESC) as rank_order
FROM staging_users

In your ETL pipeline, you would then simply filter for rank_order = 1 to get the cleanest, most recent data.

3. Calculating Running Totals

If you need to show a customer's balance growing over time, you use SUM() as a window function. By providing an ORDER BY inside the window, SQL knows to add values cumulatively rather than all at once.

Common mistakes

  • Confusing RANK() vs ROW_NUMBER(): ROW_NUMBER() always gives unique numbers (1, 2, 3). RANK() will give the same number to tied values (1, 2, 2, 4), which can cause issues if you expect a single "top" row.
  • Forgetting the ORDER BY: For functions like LEAD, LAG, or ROW_NUMBER, the order is critical. If you omit it, the results will be unpredictable.
  • Performance overhead: While powerful, applying window functions over millions of rows without proper indexing or partitioning in your database can slow down your ETL jobs.
  • Filtering in the same step: You cannot use a window function result in a WHERE clause of the same query. You must use a Subquery or a Common Table Expression (CTE) to filter the results.

Practice task

Imagine you have a table called sales_data with columns store_id, sale_date, and amount.

Task: Write a query that shows every sale record, but adds a fourth column called store_total that displays the total sum of all sales for that specific store.

Hint: Use SUM(amount) and PARTITION BY store_id, but do not use an ORDER BY inside the window if you want the grand total for the store rather than a running total.
