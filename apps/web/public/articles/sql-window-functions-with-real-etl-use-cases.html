SQL Window Functions with Real ETL Use Cases

Window functions are a specialized class of SQL operations that perform calculations across a set of table rows related to the current row. Unlike standard aggregate functions like SUM or AVG, which collapse multiple rows into a single result, window functions keep the original rows intact while adding the calculation as a new column. This unique behavior makes them indispensable for building data pipelines and performing complex analysis without losing the granularity of the source data.

Why it matters

In ETL (Extract, Transform, Load) processes, data engineers often need to transform raw, messy data into a clean, analytical format. Standard SQL can handle basic filtering, but window functions excel at tasks that would otherwise require complex self-joins or inefficient temporary tables.

For instance, if you are processing a stream of user logs where the same record might be sent twice, you can use window functions to identify and remove the duplicate based on a timestamp. They are also vital for financial reporting, such as calculating "Year-to-Date" totals or finding the difference in price between today's entry and yesterday's. By using window functions, your code becomes more readable and often performs better in modern data warehouses like Snowflake, BigQuery, or PostgreSQL.

Step-by-step walkthrough

To master window functions, you need to understand the three main components of the OVER clause, which defines the "window" of data the function looks at.

1. The Syntax Breakdown

The general structure looks like this:

FUNCTION() OVER (PARTITION BY column_a ORDER BY column_b)

  • PARTITION BY: This groups your data into buckets (similar to GROUP BY), but keeps the individual rows.
  • ORDER BY: This determines the sequence of rows within each bucket.
  • The Function: Common choices include ROW_NUMBER(), RANK(), SUM(), or LEAD().

2. ETL Case: Deduplicating Data

A common ETL challenge is "Late Arriving Data" or duplicate records. Imagine a table called stg_orders where an order might appear twice if the system retried a sync. To keep only the most recent version of each order, we use ROW_NUMBER().


SELECT 
    order_id, 
    status, 
    updated_at
FROM (
    SELECT 
        order_id, 
        status, 
        updated_at,
        ROW_NUMBER() OVER (PARTITION BY order_id ORDER BY updated_at DESC) as row_num
    FROM stg_orders
) ranked_data
WHERE row_num = 1;

In this example, the window function partitions the data by order_id and sorts each group by updated_at (newest first). By filtering for row_num = 1 in the outer query, we effectively "deduplicate" the dataset.

3. ETL Case: Calculating Running Totals

For a sales dashboard, you might need a running total of revenue per day. By using SUM() with a window function, you can add a column that accumulates values as it moves down the list.

  • Function: SUM(amount)
  • Window: ORDER BY transaction_date
  • Result: Every row shows the sum of itself and all previous rows.

Common mistakes

  • Forgetting the ORDER BY: If you use a ranking function like ROW_NUMBER() or RANK() without an ORDER BY clause inside the OVER section, the database will assign numbers arbitrarily, leading to inconsistent results.
  • Confusing RANK() vs DENSE_RANK(): If two rows have the same value (a tie), RANK() will skip the next number (1, 2, 2, 4), while DENSE_RANK() will not (1, 2, 2, 3). Using the wrong one can skew your reporting.
  • Over-partitioning: Creating too many partitions on a massive dataset can lead to performance bottlenecks. Always ensure the columns used in PARTITION BY are relevant to your business logic.

One practice task

Suppose you have a table called employee_salaries with the columns: department_id, employee_name, and salary.

The Task: Write a query that shows each employee's name and salary, but also includes a third column called dept_avg_salary that shows the average salary for that employee's specific department.

Hint: Use the AVG() function combined with PARTITION BY department_id.
