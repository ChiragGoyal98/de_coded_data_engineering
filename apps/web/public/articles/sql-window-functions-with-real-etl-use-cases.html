SQL Window Functions with Real ETL Use Cases

In the world of data engineering and Extract, Transform, Load (ETL) processes, we often need to perform calculations that involve multiple rows without actually collapsing those rows into a single summary. While standard aggregate functions like SUM or AVG condense a group of data into one result, window functions allow us to look at the "neighborhood" of a specific row while keeping the individual data points intact. This ability to maintain row-level detail while calculating broader statistics is what makes window functions a staple in any developer's toolkit.

Why Window Functions Matter in ETL

In a typical ETL pipeline, your goal is to clean, reshape, and enrich data before it reaches a warehouse. Standard SQL queries often fall short when you need to answer complex questions such as "What was the price change compared to the previous day?" or "Which of these three duplicate records is the most recent?"

Without window functions, solving these problems usually requires complex self-joins or temporary tables, which are slow and difficult to read. Window functions provide a cleaner, more efficient syntax to handle deduplication, running totals, and time-series analysis directly within your transformation layer.

Step-by-Step Walkthrough

To understand window functions, you need to master three main components: the OVER() clause, PARTITION BY, and ORDER BY.

1. The Anatomy of a Window Function

The OVER() clause is what tells SQL you are performing a window calculation. Inside it, you define the "window" or the subset of data the function should look at.

  • PARTITION BY: This divides the result set into groups (like a GROUP BY, but without collapsing rows).
  • ORDER BY: This defines the logical sequence of rows within each partition.

2. Deduplicating Data with ROW_NUMBER()

One of the most common ETL tasks is removing duplicate entries. If a system sends the same user record twice, you can use ROW_NUMBER() to rank them by a timestamp and keep only the latest one.


SELECT 
    user_id, 
    email, 
    updated_at,
    ROW_NUMBER() OVER(PARTITION BY user_id ORDER BY updated_at DESC) as rank
FROM raw_users_table;

In this example, every user gets a unique number starting from 1 for their most recent record. In your next ETL step, you would simply filter for rows where rank = 1.

3. Comparing Values with LAG() and LEAD()

In data analysis, we often need to see how a value has changed. LAG() looks at the previous row, while LEAD() looks at the following row. This is essential for calculating month-over-month growth or identifying status changes in a log file.

4. Creating Running Totals

If you need to calculate a cumulative sum of sales over a period of time, you use SUM() combined with an ORDER BY inside the window. This tells SQL to add the current row's value to the sum of all preceding rows in that partition.

Common Mistakes

  • Confusing PARTITION BY with GROUP BY: Remember that GROUP BY reduces the number of rows in your output, while PARTITION BY keeps every row visible.
  • Forgetting the ORDER BY: Functions like ROW_NUMBER() or LAG() rely entirely on sequence. If you forget to specify an order, your results will be unpredictable.
  • Performance Overhead: While powerful, window functions can be resource-intensive on massive datasets (billions of rows). Always try to filter your data as much as possible using a WHERE clause before applying the window.
  • Filtering on the Window Alias: You cannot use a window function alias (like rank) in the WHERE clause of the same query. You must wrap the query in a Subquery or a Common Table Expression (CTE) first.

Practice Task

Imagine you have a table named store_sales with columns store_id, sale_date, and amount.

Goal: Write a query that shows each sale, but also includes a column showing the total sales for that specific store to date (a running total).

Hint: You will need to use SUM(amount) as your function, partition by the store, and order by the date to ensure the sum accumulates correctly.
