SQL Window Functions with Real ETL Use Cases

SQL is the backbone of data engineering, but many beginners hit a wall when they need to perform complex calculations without losing the detail of individual rows. Standard aggregation using the GROUP BY clause is great for summaries, but it collapses your data into a single row per group. Window functions solve this by allowing you to perform calculations across a specific set of table rows-the "window"-while still returning every single record in your original dataset.

Why it matters

In the world of ETL (Extract, Transform, Load), data is rarely clean or perfectly formatted. You might encounter duplicate records from a source system, or you might need to calculate a running total for a financial report. Window functions are essential because:

  • They allow for advanced data cleaning, such as identifying the most recent record in a set of duplicates.
  • They enable trend analysis by comparing the current row to the previous or next row.
  • They improve performance by handling complex logic within the database engine rather than requiring external processing scripts.
  • They keep your code readable and maintainable compared to complex self-joins.

Step-by-step walkthrough

To master window functions, you need to understand the basic syntax: FUNCTION() OVER (PARTITION BY ... ORDER BY ...). Let's break this down through three common ETL scenarios.

1. Deduplicating Data with ROW_NUMBER()

One of the most frequent ETL tasks is removing duplicate entries. Suppose you have a table where a user clicked "Submit" twice, creating two rows for one transaction. You want to keep only the earliest one.


SELECT 
    transaction_id, 
    user_id, 
    amount,
    ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY transaction_time ASC) as row_num
FROM transactions;

In this example:

  • PARTITION BY user_id tells SQL to group the rows by each user.
  • ORDER BY transaction_time sorts them chronologically within that group.
  • ROW_NUMBER() assigns a 1 to the first record, a 2 to the second, and so on. In your ETL script, you would simply filter for where row_num = 1.

2. Comparing Trends with LAG() and LEAD()

In data transformation, you often need to see how a value changed compared to the previous day. The LAG() function "looks back" at the previous row in the sequence.

  • LAG(sales_amount) fetches the value from the row above.
  • LEAD(sales_amount) fetches the value from the row below.

3. Running Totals with SUM()

If you want to see a cumulative sum of sales over a month, you can use a standard aggregate function as a window function. By adding the ORDER BY clause inside the OVER() parentheses, SQL knows to add the current row's value to the sum of all previous rows.

Common mistakes

  • Mixing up Group By and Partition By: Remember that GROUP BY reduces the number of rows returned, while PARTITION BY keeps all original rows and simply adds the calculation to each row.
  • Forgetting the ORDER BY: For functions like ROW_NUMBER() or SUM() (as a running total), the order is critical. Without it, the database assigns numbers or sums in a random order, leading to inconsistent results.
  • Using Window Functions in WHERE clauses: You cannot use a window function directly in a WHERE clause. You must first calculate the window function in a Subquery or a Common Table Expression (CTE), then filter the results of that CTE.
  • Performance on Large Windows: If you partition by a column with very few unique values on a massive dataset, the "window" becomes too large for memory. Always ensure your partitioning logic aligns with your data distribution.

One practice task

Imagine you are working with a table named employee_salaries which has three columns: department_id, employee_name, and salary.

The Task: Write a query that shows every employee's name and salary, but also adds a third column called dept_rank that ranks employees by their salary (highest to lowest) within their specific department.

Hint: Use the RANK() OVER() function and partition by the department.
