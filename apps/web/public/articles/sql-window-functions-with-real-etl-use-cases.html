SQL Window Functions with Real ETL Use Cases

In the world of data engineering and analysis, SQL window functions stand out as a powerful way to perform complex calculations across sets of rows that are related to the current row. Unlike regular aggregate functions that group rows into a single output, these functions allow you to retain the individual row details while still computing values like running totals, rankings, or moving averages. They are essential tools for anyone looking to transition from basic data querying to more advanced data transformation tasks.

Why it matters

In ETL (Extract, Transform, Load) pipelines, we rarely just move data from point A to point B. We often need to clean it or add context. Window functions are the "Swiss Army Knife" for these transformations because they solve problems that are otherwise difficult or computationally expensive to handle with standard joins or subqueries.

For example, if you need to remove duplicate records, you can't easily do that with a simple GROUP BY. If you need to see how much a customer's spending has increased compared to their last visit, a window function makes it a one-line task. They allow for "row-aware" calculations, which are vital for building clean, analytical datasets.

Step-by-step walkthrough

To master window functions, you need to understand the three main components of the OVER() clause, which defines the "window" of data the function looks at.

1. The Syntax

The basic structure looks like this:

FUNCTION() OVER (PARTITION BY column1 ORDER BY column2)

  • PARTITION BY: This divides the data into buckets (like grouping).
  • ORDER BY: This defines the sequence of rows within those buckets.

2. Ranking and Deduplication

The most common ETL use case for window functions is deduplication. If a source system sends multiple updates for the same ID, you might only want the most recent one. Using ROW_NUMBER(), you can assign a unique rank to every row within a group and then filter for the first one.

3. Value Offsets (LAG and LEAD)

In financial or clickstream data, you often need to compare a current row to a previous one. LAG() looks at the row above, while LEAD() looks at the row below. This is perfect for calculating the time elapsed between two user actions or the change in a stock price.

4. Running Totals

Instead of collapsing all rows into a single sum, you can use SUM() as a window function to see a balance grow over time.


SELECT 
    order_date, 
    sale_amount,
    SUM(sale_amount) OVER (ORDER BY order_date) AS running_total
FROM sales_data;

Common mistakes

  • Using Window Functions in WHERE: You cannot use a window function directly in a WHERE clause because they are processed after the filtering happens. To filter by a rank, you must wrap your query in a Common Table Expression (CTE) or a subquery.
  • Confusing Rank Types: ROW_NUMBER() always gives a unique number (1, 2, 3). RANK() gives the same number to ties but skips the next (1, 2, 2, 4). DENSE_RANK() gives the same number to ties without skipping (1, 2, 2, 3). Choosing the wrong one can lead to "missing" data in your reports.
  • Omitting ORDER BY: For functions like SUM() or LAG(), forgetting the ORDER BY clause inside the OVER() bracket will result in the function looking at the entire partition as an unordered pile, often leading to unexpected results.

One practice task

Suppose you have a table named employee_salaries with columns department, employee_name, and salary.

The Goal: Write a query that shows every employee's name and salary, but also adds a column called dept_highest_salary which shows the maximum salary found in that specific employee's department.

Hint: Use the MAX() function combined with the OVER() and PARTITION BY clauses.
