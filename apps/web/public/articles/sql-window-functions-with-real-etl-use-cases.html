SQL Window Functions with Real ETL Use Cases

If you have been working with SQL for a while, you are likely familiar with aggregate functions like SUM() and AVG(). These functions take a group of rows and collapse them into a single result. However, in data engineering and ETL (Extract, Transform, Load) processes, we often need to perform calculations across a set of rows while still keeping the individual rows visible. This is where window functions come into play. A window function performs a calculation across a set of table rows that are somehow related to the current row, acting like a sliding window that moves through your dataset.

Why it matters in ETL

In the world of ETL, window functions are not just a "nice-to-have" feature; they are essential for data cleaning and transformation. When moving data from a source system to a data warehouse, you frequently encounter issues like duplicate records, out-of-order logs, or the need to calculate trends over time.

Without window functions, solving these problems usually requires complex self-joins or subqueries, which are difficult to read and slow to execute. Window functions allow you to handle tasks like deduplication, calculating running totals, and finding the "previous" value in a sequence with much cleaner code and better performance.

Step-by-step walkthrough

To use a window function, you need to understand the three main components of its syntax: the function itself, the OVER clause, and the optional PARTITION BY and ORDER BY clauses.

1. The OVER Clause

The OVER clause is what defines the "window" of rows the function will operate on. Even if you leave it empty, as in COUNT(*) OVER(), it tells SQL to treat the entire result set as the window without collapsing the rows.

2. PARTITION BY (Grouping)

Think of PARTITION BY as the "Group By" for window functions. It divides the result set into partitions. For example, if you are processing sales data, you might partition by store_id so that the calculation starts over for every new store.

3. ORDER BY (Sequencing)

This defines the order of rows within each partition. This is crucial for functions that depend on sequence, such as calculating a running total or identifying the most recent record in a log.

ETL Use Case: Deduplication

A common ETL task is removing duplicate entries where only the most recent record is valid. We can use ROW_NUMBER() to rank records by a timestamp and then filter for the first one.


SELECT 
    order_id, 
    customer_id, 
    status, 
    updated_at
FROM (
    SELECT 
        *,
        ROW_NUMBER() OVER(PARTITION BY order_id ORDER BY updated_at DESC) as rank_id
    FROM raw_orders_table
) 
WHERE rank_id = 1;

In this example, the window function assigns a '1' to the most recent update for every order_id. The outer query then filters out the older versions (where rank_id is greater than 1), leaving us with a clean, unique dataset.

Common mistakes

  • Confusing RANK() and DENSE_RANK(): If two rows have the same value in the ORDER BY column, RANK() will skip the next number in the sequence (e.g., 1, 2, 2, 4), whereas DENSE_RANK() will not (e.g., 1, 2, 2, 3). Using the wrong one can lead to logic errors in reporting.
  • Forgetting the ORDER BY in Running Totals: If you use SUM(amount) OVER(PARTITION BY user_id), you will get the total sum for that user on every row. If you want a running total (row by row), you must include ORDER BY date.
  • Filtering in the same query: You cannot use a window function result in a WHERE clause in the same query block. You must use a Subquery or a Common Table Expression (CTE) as shown in the code example above.

One practice task

Imagine you are working with a table called daily_revenue with columns log_date and revenue_amount.

The Task: Write a query that calculates a running total of revenue across all dates, ordered by the date.

Hint: Use the SUM() function with an OVER clause that includes an ORDER BY, but no PARTITION BY.
