Introduction

Window functions are one of the most powerful tools in a data engineer's SQL toolkit. Unlike traditional aggregate functions that collapse rows into a single summary value, window functions allow you to perform calculations across a set of rows while still keeping the individual details of each row intact. This makes them indispensable for building complex data pipelines where you need to compare a current record with its neighbors or rank items within specific categories without losing the original data structure.

Why it matters in ETL

In Extract, Transform, Load (ETL) processes, your primary goal is often to clean data and prepare it for analysis. Window functions solve several common data engineering challenges:

  • Deduplication: Identifying and removing duplicate records by ranking rows based on timestamps.
  • Trend Analysis: Calculating month-over-month growth or year-to-date totals.
  • Data Quality: Spotting anomalies by comparing a current value to a moving average.
  • Sessionization: Grouping user actions into distinct sessions based on time gaps.

Without window functions, solving these problems usually requires complex self-joins or temporary tables, which can significantly slow down your pipelines and make your code harder to maintain.

Step-by-step walkthrough

To master window functions, you need to understand the three main parts of the syntax: the function itself, the PARTITION BY clause, and the ORDER BY clause.

1. The Basic Syntax

The general structure looks like this:

FUNCTION() OVER (PARTITION BY column_a ORDER BY column_b)

  • PARTITION BY: This divides your data into "windows" or groups.
  • ORDER BY: This defines the sequence of rows within each window.

2. Ranking Rows (Deduplication Case)

Suppose you have a table where the same user ID appears multiple times due to a bug in the source system. You only want the most recent record. You can use ROW_NUMBER() to rank them by date.


SELECT 
    user_id, 
    email, 
    updated_at,
    ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY updated_at DESC) as row_num
FROM raw_users;

In an ETL pipeline, you would wrap this in a subquery and filter where row_num = 1 to get a clean list of unique users.

3. Comparing Values (Growth Tracking Case)

The LAG() and LEAD() functions allow you to look at the previous or next row in the result set. This is perfect for calculating how much sales increased compared to the previous day.


SELECT 
    sale_date,
    revenue,
    LAG(revenue) OVER (ORDER BY sale_date) as previous_day_revenue
FROM daily_sales;

4. Running Totals

If you need a cumulative sum of sales throughout the month, you use SUM() as a window function by omitting the GROUP BY and using the OVER clause instead.


SELECT 
    sale_date,
    revenue,
    SUM(revenue) OVER (ORDER BY sale_date) as running_total
FROM daily_sales;

Common mistakes

  • Confusing RANK() and ROW_NUMBER(): ROW_NUMBER() always gives unique numbers (1, 2, 3), while RANK() will give the same number to tied values (1, 2, 2, 4). Using the wrong one can lead to "ghost" duplicates in your cleaned data.
  • Performance overhead: Window functions are calculated in memory. Applying multiple window functions over millions of rows without proper indexing or filtering can cause your ETL jobs to time out or crash.
  • Forgetting ORDER BY: Many window functions, like LAG or SUM (as a running total), require a specific order to make sense. If you forget the ORDER BY inside the OVER clause, the results will be unpredictable.

Practice task

Scenario: You are managing a fleet of delivery trucks. You have a table called truck_logs with columns: truck_id, delivery_date, and miles_driven.

The Task: Write a query that shows each truck's ID and delivery date, along with a column showing the total miles that specific truck has driven up to that date (a running total per truck).

Hint: You will need to partition the data so the total resets for each truck.
