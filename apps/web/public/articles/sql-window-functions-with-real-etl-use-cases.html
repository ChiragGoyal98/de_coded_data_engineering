SQL Window Functions with Real ETL Use Cases

In the world of data engineering, SQL is the primary language for transforming raw data into meaningful insights. While basic queries help you filter and aggregate data, window functions allow you to perform advanced calculations across sets of rows that are related to the current row. Unlike a standard GROUP BY clause, which collapses your data into a summary, window functions keep all your individual rows intact while adding a new layer of calculated information.

Why it matters

In ETL (Extract, Transform, Load) pipelines, data is rarely perfect. You often encounter duplicate records, missing sequences, or the need to calculate historical trends. Window functions are essential because they:

  • Remove Duplicates: They can identify the "latest" version of a record in a dataset.
  • Calculate Running Totals: They allow you to track cumulative sums or averages over time without complex joins.
  • Handle Ranking: They help you find the "top N" items within specific categories, such as the highest-selling product per region.
  • Improve Performance: Using a window function is often much faster and more readable than writing a correlated subquery or a self-join.

Step-by-step walkthrough

1. Understanding the OVER clause

Every window function is defined by the OVER clause. This tells the database, "Stop looking at the table as a whole and start looking at a specific window of rows."

2. Dividing data with PARTITION BY

Think of PARTITION BY as the "Group By" of window functions. It divides the result set into smaller buckets. For example, if you partition by store_id, the calculation starts over every time the store ID changes.

3. Sequencing with ORDER BY

Inside your window, you often need a specific order. If you are calculating a running total, you need to tell SQL to add the numbers based on a date or transaction_id.

4. Real ETL Use Case: Deduplication

One of the most common ETL tasks is keeping only the most recent record for a specific ID. In this example, we use ROW_NUMBER() to rank transactions for each user by date, so we can later filter for the number 1 record.


SELECT 
    order_id, 
    customer_id, 
    order_date,
    ROW_NUMBER() OVER(
        PARTITION BY customer_id 
        ORDER BY order_date DESC
    ) as record_rank
FROM orders;

Common mistakes

  • Using window functions in the WHERE clause: You cannot use a window function result directly in a WHERE clause. You must wrap the query in a Common Table Expression (CTE) or a subquery and filter the results from there.
  • Confusing RANK() and DENSE_RANK(): If two rows have the same value, RANK() will skip the next number in the sequence (e.g., 1, 1, 3), while DENSE_RANK() will not (e.g., 1, 1, 2).
  • Forgetting the ORDER BY: For functions like LEAD(), LAG(), or ROW_NUMBER(), the order of the rows is critical. Omitting the ORDER BY inside the OVER clause will lead to unpredictable results.

One practice task

Imagine you have a table called daily_revenue with columns sale_date and amount. Write a query that creates a new column showing a "running total" of the revenue. This means for every row, the new column should show the sum of the current day's amount plus all previous days' amounts. (Hint: Use SUM(amount) OVER(...) with an ORDER BY on the date).
