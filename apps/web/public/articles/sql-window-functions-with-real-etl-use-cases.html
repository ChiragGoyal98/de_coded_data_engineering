In the world of SQL, window functions are often seen as an advanced topic, but they are actually straightforward once you grasp the core concept. These functions perform calculations across a set of rows that are somehow related to the current row. While a standard aggregate function like SUM() rolls multiple rows into one, a window function keeps the original rows while adding the calculated value into a new column. This makes them indispensable for data transformation tasks where context matters.

Why it matters

In Data Engineering and ETL (Extract, Transform, Load) pipelines, we rarely just want to see a grand total. We usually need to answer more complex questions like: "What is the running total of sales per month?" or "What was the price difference compared to yesterday?"

Without window functions, solving these problems often requires messy self-joins or complex subqueries that are hard to read and slow to execute. Window functions allow you to perform "analytical" math efficiently, making your ETL scripts cleaner and significantly faster. They are particularly useful for:

  • Deduplication: Identifying the latest record in a set of duplicates.
  • Trend Analysis: Calculating moving averages or year-over-year growth.
  • Data Quality: Checking if timestamps are in the correct chronological order.

Step-by-step walkthrough

To use a window function, you need to understand the OVER() clause. This clause defines the "window" of data the function will look at.

1. The Basic Syntax

The syntax generally looks like this:

FUNCTION() OVER (PARTITION BY column_a ORDER BY column_b)

  • PARTITION BY: This divides the result set into groups (like GROUP BY).
  • ORDER BY: This defines the sequence of rows within each group.

2. Ranking Rows (Deduplication)

A common ETL task is keeping only the most recent record for a specific ID. We use ROW_NUMBER() for this. It assigns a unique integer to each row within a partition.


SELECT 
    user_id, 
    transaction_date, 
    amount,
    ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY transaction_date DESC) as rank
FROM transactions;

In this example, the row with rank = 1 will always be the most recent transaction for every user. In an ETL pipeline, you would wrap this in a subquery and filter for WHERE rank = 1.

3. Calculating Running Totals

If you want to see how revenue grows over time without losing individual transaction details, you can use SUM() as a window function.


SELECT 
    order_date, 
    daily_revenue,
    SUM(daily_revenue) OVER (ORDER BY order_date) as running_total
FROM daily_sales;

4. Comparing Across Rows (Lead and Lag)

ETL processes often require comparing a current value to a previous one (e.g., did the temperature rise since the last sensor reading?).

  • LAG(): Pulls data from a previous row.
  • LEAD(): Pulls data from a subsequent row.

Common mistakes

  • Confusing PARTITION BY with GROUP BY: Remember that PARTITION BY does not reduce the number of rows in your output; it just organizes how the function calculates values.
  • Forgetting ORDER BY: For functions like ROW_NUMBER() or RANK(), forgetting the ORDER BY clause inside the OVER() bracket will result in non-deterministic (random) assignments.
  • Performance overhead: While faster than self-joins, running multiple window functions on millions of rows can be memory-intensive. Always try to filter your data as much as possible before applying them.

One practice task

The Scenario: You have a table called web_logs with columns user_id, page_name, and timestamp.

Your Task: Write a query that shows each page a user visited, along with the name of the previous page they were on. (Hint: Use the LAG() function and partition by the user).

This is a classic "path analysis" task used in data engineering to understand how users navigate through a website. Give it a try in your SQL editor!
