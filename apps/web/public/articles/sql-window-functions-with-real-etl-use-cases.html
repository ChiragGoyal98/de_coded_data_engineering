SQL Window Functions with Real ETL Use Cases

In the world of data engineering and analysis, SQL window functions often feel like a magic trick. While standard aggregate functions like SUM or AVG collapse your data into a single row, window functions allow you to perform complex calculations while keeping your original row-level detail intact. Think of it as looking through a sliding window that moves across your dataset, allowing you to see specific subsets of data without losing sight of the individual records.

Why Window Functions Matter in ETL

In ETL (Extract, Transform, Load) pipelines, window functions are essential for cleaning and transforming data before it hits a data warehouse. Without them, tasks like identifying the most recent record in a set of duplicates or calculating a running total would require messy self-joins and subqueries that slow down performance.

Window functions provide a cleaner, more readable way to:

  • Deduplicate data by ranking records by a timestamp.
  • Calculate growth metrics, such as month-over-month revenue.
  • Assign unique IDs to groups of related data.
  • Compare a specific row's value against an average of its category.

Step-by-Step Walkthrough

To understand how these functions work, you need to master the OVER() clause, which defines the "window" of rows the function will operate on.

1. The Basic Syntax

Every window function follows this structure: FUNCTION() OVER (PARTITION BY column ORDER BY column). The PARTITION BY part tells SQL how to group the data, and ORDER BY tells it how to sort the data within those groups.

2. Ranking Data for Deduplication

A common ETL task is keeping only the "latest" record for a user. We use ROW_NUMBER() to assign a unique integer to rows within a partition.


SELECT 
    user_id, 
    order_date, 
    amount,
    ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY order_date DESC) as rank_order
FROM sales_data;

In this example, the data is grouped by user_id. Within each user group, the rows are sorted by order_date from newest to oldest. The most recent order gets a rank_order of 1.

3. Calculating Running Totals

If you need to see how revenue accumulates over time, you use SUM() as a window function. By omitting PARTITION BY but including ORDER BY, the "window" grows row by row, adding the current value to all previous values.

4. Navigating Rows with LAG and LEAD

In ETL, you often need to compare the current row to the previous one (e.g., "How much did this price change since the last update?"). LAG() looks at the previous row, while LEAD() looks at the next one. This prevents the need for complex joins.

Common Mistakes

  • Confusing GROUP BY with PARTITION BY: Remember that GROUP BY reduces the number of rows in your output. PARTITION BY does not; it simply defines the scope for the calculation while keeping all original rows.
  • Forgetting ORDER BY in Ranking Functions: Functions like ROW_NUMBER() or RANK() require an ORDER BY clause. If you leave it out, the database won't know which row should be "first," leading to unpredictable results.
  • Performance Overload: While powerful, applying window functions over millions of rows with complex partitions can be resource-intensive. Always ensure your "Partition By" columns are indexed if performance starts to lag.

Practice Task

Imagine you have a table called web_traffic with columns session_id, page_url, and timestamp.

Task: Write a query to find the first page visited in every session.

Hint: Use ROW_NUMBER(), partition by the session, and order by the timestamp. Filter the results where the row number equals 1.
