SQL Window Functions with Real ETL Use Cases

In the world of data engineering and analysis, SQL is the foundation upon which most data pipelines are built. While basic operations like filtering and joining are essential, window functions represent a significant step up in your ability to transform data efficiently. Unlike standard aggregate functions-which group multiple rows into a single result-window functions perform calculations across a set of table rows that are related to the current row. This allows you to keep the details of every individual record while still performing complex calculations like rankings, moving averages, or running totals.

Why Window Functions Matter in ETL

In ETL (Extract, Transform, Load) processes, window functions are indispensable for data quality and business logic. When you are transforming raw data into a clean, usable format, you often need to look "ahead" or "behind" a specific record.

For example, if you are processing financial transactions, you might need to calculate a running balance for an account or identify the time elapsed between two consecutive purchases. Without window functions, these tasks would require complex, slow self-joins. Window functions handle these operations elegantly, making your SQL code more readable and significantly faster to execute.

Step-by-Step Walkthrough

To use a window function, you need to understand the three main components of the OVER() clause: PARTITION BY, ORDER BY, and the function itself.

1. The Basic Syntax

The general structure looks like this:

FUNCTION_NAME() OVER (PARTITION BY column1 ORDER BY column2)

  • PARTITION BY: Divides the result set into partitions (groups). The function is applied to each partition separately.
  • ORDER BY: Defines the order of rows within each partition.

2. Use Case: Deduplication with ROW_NUMBER()

One of the most common ETL tasks is removing duplicate records. Imagine a table where an API sent the same order twice. You can use ROW_NUMBER() to identify and remove the extras.


SELECT 
    order_id, 
    customer_id, 
    order_date,
    ROW_NUMBER() OVER (PARTITION BY order_id ORDER BY order_date DESC) as row_num
FROM raw_sales_data;

In this example, if there are two rows with the same order_id, the one with the latest order_date gets row_num = 1. In your ETL script, you would simply filter for rows where row_num = 1.

3. Use Case: Comparing Records with LAG()

If you want to find the growth in sales compared to the previous day, you use LAG(). This function allows you to pull a value from the previous row into the current row.

4. Use Case: Running Totals with SUM()

In a data warehouse, you might need a cumulative sum of revenue throughout a month. By using SUM(revenue) OVER (ORDER BY transaction_date), SQL adds each day's revenue to the sum of all previous days' revenue without collapsing the rows into a single total.

Common Mistakes

  • Confusing PARTITION BY with GROUP BY: A GROUP BY clause collapses your rows. A PARTITION BY keeps all original rows visible while performing the calculation.
  • Forgetting the ORDER BY clause: For functions like ROW_NUMBER() or LAG(), the order is critical. Without it, the "previous" row or the "first" row is essentially random, leading to unpredictable data.
  • Performance overhead: While window functions are faster than self-joins, using them on millions of rows without proper indexing or partitioning in your database can still slow down your pipeline.

Practice Task

Suppose you have a table named web_traffic with columns user_id, session_timestamp, and pages_viewed.

The Task: Write a query that shows every session for every user, but also adds a column called previous_session_time that shows the timestamp of the user's immediate prior session. Use LAG() to solve this. This is a common pattern used to calculate session duration or user retention.
