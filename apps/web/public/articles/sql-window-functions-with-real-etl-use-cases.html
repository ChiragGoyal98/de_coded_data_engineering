SQL Window Functions with Real ETL Use Cases

SQL is often thought of as a tool for simple data retrieval or basic grouping. However, as data engineering requirements become more complex, especially in ETL pipelines, you often need to perform calculations that depend on other rows without losing the granularity of your original data. This is where window functions come into play. Unlike a standard GROUP BY clause which collapses multiple rows into a single summary row, a window function allows every individual row to remain visible while still providing access to surrounding data for calculations.

Why Window Functions Matter in ETL

In the world of Extract, Transform, Load (ETL), data is rarely perfect. You might receive duplicate records from an API, or you might need to calculate a "running total" of sales for a dashboard. Traditionally, developers tried to solve these problems using complex self-joins or correlated subqueries, which are notoriously slow on large datasets.

Window functions are essential because they:

  • Provide better performance by traversing the data once rather than multiple times.
  • Keep your code readable and maintainable.
  • Enable advanced analytical transforms, such as identifying the "first" or "last" event in a sequence, which is a staple in clickstream and financial data processing.

Step-by-Step Walkthrough

To use a window function, you need to understand the basic syntax: FUNCTION() OVER (PARTITION BY ... ORDER BY ...). The "Window" is the specific set of rows the function looks at for each calculation.

1. Deduplication with ROW_NUMBER()

One of the most common ETL tasks is removing duplicate records. Imagine a scenario where a system sends multiple updates for the same Order ID, and you only want the most recent one.

  • PARTITION BY: This groups the data (e.g., by Order ID).
  • ORDER BY: This sorts the data within that group (e.g., by Update Timestamp descending).

SELECT order_id, status, update_time
FROM (
    SELECT 
        order_id, 
        status, 
        update_time,
        ROW_NUMBER() OVER (PARTITION BY order_id ORDER BY update_time DESC) as row_num
    FROM raw_orders
) ranked_data
WHERE row_num = 1;

2. Calculating Running Totals

If you are building a financial report, you might need a daily cumulative sum of revenue. Instead of grouping by date (which would only give you the total for that specific day), you use a window function.

  • Use SUM(revenue) OVER (ORDER BY transaction_date). This tells SQL to add the current row's revenue to the sum of all previous rows.

3. Comparing Current and Previous Rows with LAG()

In ETL, we often need to calculate the "delta" or change between two points in time. For example, how long did a ticket stay in "In Progress" before moving to "Done"?

  • LAG() looks at the row immediately preceding the current one.
  • LEAD() looks at the row immediately following the current one.

Common Mistakes

Even experienced developers trip up on these three points:

  • Forgetting the ORDER BY: For functions like ROW_NUMBER() or RANK(), the order is mandatory. Without it, the "first" row is chosen randomly, leading to inconsistent data.
  • Using Window Functions in WHERE: You cannot use a window function directly in a WHERE clause (e.g., WHERE ROW_NUMBER() = 1). You must use a Subquery or a Common Table Expression (CTE) as shown in the code example above.
  • Confusing ROW_NUMBER, RANK, and DENSE_RANK: ROW_NUMBER always gives a unique number (1, 2, 3). RANK gives the same number to ties but skips the next (1, 2, 2, 4). DENSE_RANK gives the same number to ties but does not skip (1, 2, 2, 3).

Practice Task

Scenario: You have a table called sensor_readings with columns sensor_id, reading_time, and temperature. Due to a technical glitch, some sensors sent multiple readings at the exact same second.

Task: Write a query using a CTE and a window function to find the average temperature for each sensor, but only include the very first reading recorded for each sensor_id based on the reading_time.

Hint: Use a CTE to assign a row number to each reading per sensor, filter for the first row, and then perform your average calculation on that filtered set.
