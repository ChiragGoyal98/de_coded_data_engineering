SQL Window Functions with Real ETL Use Cases

In the world of data engineering and analysis, window functions represent a significant leap from basic queries to advanced data transformation. While traditional aggregate functions like SUM or AVG collapse multiple rows into a single result, window functions allow you to perform calculations across a specific set of rows while still maintaining the individual identity of every record. This makes them a vital tool for anyone working with data pipelines, as they provide the context needed to understand how a single data point relates to its neighbors without the need for complex, slow-performing self-joins.

Why Window Functions Matter in ETL

In Extract, Transform, Load (ETL) processes, we rarely deal with static, isolated rows. We often need to answer questions like: "Is this a duplicate record?", "What was the previous price of this product?", or "What is the running total of sales for this region?"

Using standard SQL grouping for these tasks is often impossible because grouping hides the individual row details. Window functions solve this by creating a "window" of data that the function can see while processing the current row. For an ETL developer, this means cleaner code, better performance on large datasets, and the ability to handle complex logic-like sessionization or deduplication-directly within the SQL transformation layer.

Step-by-Step Walkthrough

To master window functions, you need to understand the three main components of the OVER() clause, which defines the "window."

1. The Partition (PARTITION BY)

This acts like a GROUP BY but for the window. It divides the result set into partitions. For example, if you partition by category_id, the calculation starts over for every new category.

2. The Order (ORDER BY)

This defines the sequence of rows within each partition. This is crucial for functions that depend on position, such as calculating a running total or finding the "most recent" record.

3. The Function

Common functions include ROW_NUMBER() (for numbering rows), RANK() (for finding top items), and LAG()/LEAD() (for looking at previous or next rows).

Real ETL Use Case: Deduplication

Imagine a landing table where an API pushed duplicate user records. You only want to keep the most recent update for each user.


WITH RankedUpdates AS (
    SELECT 
        user_id, 
        email, 
        updated_at,
        ROW_NUMBER() OVER (
            PARTITION BY user_id 
            ORDER BY updated_at DESC
        ) as rank_id
    FROM raw_users_table
)
SELECT user_id, email, updated_at
FROM RankedUpdates
WHERE rank_id = 1;

In this example, PARTITION BY user_id groups the rows by user, and ORDER BY updated_at DESC ensures the newest record gets rank_id = 1. By filtering for rank_id = 1 in the outer query, we effectively remove all older duplicates.

Common Mistakes

  • Using Window Functions in WHERE Clauses: You cannot use a window function directly in a WHERE clause because they are processed after the filtering stage. To filter based on a window result, you must use a Common Table Expression (CTE) or a subquery, as shown in the example above.
  • Forgetting the ORDER BY: For functions like RANK() or LEAD(), the order is essential. Forgetting it will lead to unpredictable results or errors.
  • Mixing up RANK() and DENSE_RANK(): If two rows have the same value, RANK() will skip the next number (1, 2, 2, 4), while DENSE_RANK() will not (1, 2, 2, 3). Choosing the wrong one can lead to "missing" data in your ETL logic.

Practice Task

Suppose you have a table called monthly_sales with columns region, sale_month, and revenue.

The Task: Write a query that shows each region's revenue for every month, but also includes a column showing the previous month's revenue for that same region.

Hint: Use the LAG() function and remember to partition by the region so you don't accidentally compare sales from two different locations!
