SQL Window Functions with Real ETL Use Cases

Window functions are one of the most powerful tools in a data engineer's SQL toolkit. Unlike traditional aggregate functions that collapse rows into a single result, window functions allow you to perform calculations across a set of rows while still preserving the details of each individual record. This makes them indispensable for complex data transformations where you need to compare a row's value against its neighbors or a specific group without losing the context of the original dataset.

Why it matters in ETL

In the world of Extract, Transform, Load (ETL), data is rarely perfect or pre-summarized. You often encounter raw logs or transactional data that require sophisticated reshaping before they land in a data warehouse.

Window functions are essential for ETL because they:

  • Handle Deduplication: They help identify and remove duplicate records by ranking entries based on timestamps.
  • Maintain Row Context: You can calculate a running total or a moving average while keeping every individual transaction visible.
  • Perform Time-Series Analysis: They allow you to compare the current row's value to the previous row (e.g., comparing today's sales to yesterday's) without complex self-joins.
  • Improve Performance: In many cases, a single window function can replace multiple subqueries or joins, making your ETL scripts cleaner and faster.

Step-by-step walkthrough

To use a window function, you need to understand the OVER clause. This clause defines the "window" of rows the function will operate on.

1. The Basic Syntax

The standard structure looks like this:

FUNCTION() OVER (PARTITION BY column_a ORDER BY column_b)

  • PARTITION BY: This divides the result set into groups (like a GROUP BY but without collapsing rows).
  • ORDER BY: This defines the sequence of rows within each partition.

2. Ranking Rows for Deduplication

One of the most common ETL tasks is keeping only the most recent record for a specific ID. We use ROW_NUMBER() for this.


SELECT 
    user_id, 
    status, 
    updated_at,
    ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY updated_at DESC) as rank
FROM raw_user_data;

In an ETL pipeline, you would wrap this in a subquery and filter where rank = 1 to ensure you only load the latest status for each user.

3. Comparing Trends with LAG and LEAD

ETL processes often require calculating growth. The LAG() function looks at the row "above" the current one.

  • LAG(column): Fetches data from a previous row.
  • LEAD(column): Fetches data from a subsequent row.

This is perfect for calculating Month-over-Month (MoM) revenue growth without needing to join the table to itself.

4. Running Totals

If you need to calculate a cumulative sum of sales over time, you use SUM() as a window function. By providing an ORDER BY inside the OVER clause without a PARTITION BY, SQL calculates a total that grows with every row.

Common mistakes

Even experienced developers trip up on these three areas when first using window functions:

  • Confusing PARTITION BY with GROUP BY: Remember that GROUP BY reduces the number of rows returned. A window function never changes the number of rows; it only adds a calculated value to each existing row.
  • Forgetting ORDER BY in Ranking: Functions like ROW_NUMBER() or RANK() require a logical order to work. If you omit the ORDER BY, the ranking will be non-deterministic (essentially random).
  • Filtering in the same SELECT: You cannot use a window function result in a WHERE clause in the same query block. Because of the SQL Order of Operations, the WHERE clause is processed before the window function. You must use a Subquery or a Common Table Expression (CTE) to filter by window results.

One practice task

Scenario: You have a table called monthly_inventory with columns warehouse_id, product_id, check_date, and stock_count.

Task: Write a query that shows each product's current stock_count and creates a new column showing the stock_count from the previous check date for that same product at that specific warehouse.

Hint: You will need to use the LAG() function and partition by two different columns to ensure the "previous" value belongs to the correct product and location.
