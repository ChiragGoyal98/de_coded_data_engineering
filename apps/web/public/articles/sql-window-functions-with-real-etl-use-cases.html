SQL window functions are a powerful addition to your data transformation toolkit, allowing you to perform calculations across a set of table rows that are somehow related to the current row. While standard aggregate functions like SUM or AVG collapse multiple rows into a single result, window functions perform the calculation while keeping all original rows visible in the output. This capability is essential for data engineers who need to process streams of information without losing the granular detail of each individual record.

Why it matters

In the world of ETL (Extract, Transform, Load), data is rarely perfect. You often encounter challenges like duplicate records, the need for chronological tracking, or comparing a value to its predecessor. Traditionally, solving these problems required complex self-joins or multiple temporary tables, which are hard to read and slow to execute.

Window functions provide a cleaner, more efficient syntax for:

  • Identifying and removing duplicate data.
  • Creating running totals for financial reporting.
  • Comparing month-over-month performance.
  • Ranking items within specific categories.

Step-by-step walkthrough

The core of every window function is the OVER clause. This clause defines the "window" of data the function will look at. It generally consists of two main parts: PARTITION BY and ORDER BY.

1. Partitioning the data

Think of PARTITION BY as a way to group your data into buckets. If you are analyzing sales data for multiple stores, partitioning by store_id tells SQL to perform the calculation separately for each store rather than for the whole table.

2. Ordering within the window

The ORDER BY clause inside the window function determines the sequence in which the calculation is processed. This is vital for functions that rely on chronology, such as calculating a running total or identifying the "latest" record.

3. Example: Deduplicating Records

A common ETL task is keeping only the most recent entry for a user when the source system sends duplicate updates. We use ROW_NUMBER() to assign a unique incrementing integer to rows within a partition.


WITH RankedUpdates AS (
  SELECT 
    user_id, 
    email, 
    updated_at,
    ROW_NUMBER() OVER (
      PARTITION BY user_id 
      ORDER BY updated_at DESC
    ) as row_num
  FROM raw_users_table
)
SELECT user_id, email, updated_at
FROM RankedUpdates
WHERE row_num = 1;

In this example, the data is partitioned by user_id. Within each user's bucket, the rows are ordered by updated_at in descending order. The most recent record gets row_num = 1, making it easy to filter out older duplicates.

Common mistakes

  • Using window functions in the WHERE clause: You cannot use a window function directly in a WHERE clause because the window calculation happens after the filtering stage. You must use a Subquery or a Common Table Expression (CTE) as shown in the example above.
  • Forgetting ORDER BY in running totals: If you use a function like SUM(amount) OVER (PARTITION BY user_id), it will give you the total sum for the entire partition in every row. If you want a running total that grows row by row, you must include ORDER BY date.
  • Confusing RANK vs. DENSE_RANK vs. ROW_NUMBER: These functions handle "ties" differently. ROW_NUMBER always gives a unique number, while RANK might skip numbers if there is a tie (e.g., 1, 2, 2, 4), and DENSE_RANK will not skip numbers (e.g., 1, 2, 2, 3).

One practice task

Suppose you have a table called monthly_revenue with columns region, month, and revenue. Write a query that uses the LAG() function to show each region's revenue alongside the revenue from the previous month. This is the first step in calculating month-over-month growth in an ETL pipeline.
