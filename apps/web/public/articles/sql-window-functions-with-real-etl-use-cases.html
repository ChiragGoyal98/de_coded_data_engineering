SQL Window Functions with Real ETL Use Cases

SQL window functions are often seen as an advanced topic, but they are essential tools for anyone working with data. Imagine you want to calculate a running total of sales or find the previous day's temperature for every row in your dataset. Standard aggregate functions like SUM or AVG would collapse your rows into a single summary. Window functions, however, allow you to perform these calculations while keeping every individual row visible in your result set. This window into your data provides a powerful way to analyze trends and patterns without losing the context of the original records.

Why it matters in ETL

In the world of Extract, Transform, Load (ETL), data is rarely perfect. You often encounter duplicate records, out-of-order events, or the need to calculate growth metrics over time. Window functions solve these problems more efficiently than complex subqueries or self-joins.

Using window functions in your transformation layer makes your code:

  • Readable: It expresses the logic of "comparing this row to the previous one" directly.
  • Performant: Database engines are highly optimized for windowing operations compared to nested loops.
  • Maintainable: It reduces the need for temporary tables or multiple passes over the same dataset.

Step-by-step walkthrough

The secret to mastering window functions is understanding the OVER() clause. This clause defines the "window" of rows the function will look at.

1. The Basic Syntax

Every window function follows this pattern:

FUNCTION_NAME() OVER (PARTITION BY column_a ORDER BY column_b)

  • PARTITION BY: This divides the data into logical groups (like categories or user IDs).
  • ORDER BY: This defines the sequence of rows within those groups.

2. Use Case: Deduplicating Data

In ETL, you might receive multiple updates for the same order. To keep only the most recent one, we use ROW_NUMBER(). This assigns a unique integer to rows within a partition.


SELECT 
    order_id, 
    status, 
    updated_at,
    ROW_NUMBER() OVER (PARTITION BY order_id ORDER BY updated_at DESC) as row_num
FROM raw_sales_data

In this example, if order_id 101 has three updates, the one with the latest updated_at gets row_num = 1. In your ETL pipeline, you would simply filter for where row_num = 1.

3. Use Case: Calculating Running Totals

To see how revenue grows day-by-day, you can use SUM() as a window function. By omitting the PARTITION BY but including an ORDER BY, the window grows row-by-row.


SELECT 
    sale_date, 
    daily_revenue,
    SUM(daily_revenue) OVER (ORDER BY sale_date) as running_total
FROM daily_sales

4. Use Case: Change Detection with LAG

If you need to know if a price changed from the previous day, LAG() is your best friend. It "looks back" a specified number of rows.

  • LAG(price) gets the price from the previous row.
  • LEAD(price) gets the price from the next row.

Common mistakes

Even experienced developers trip over these three common hurdles:

  • Forgetting the ORDER BY: For ranking functions like ROW_NUMBER() or RANK(), the ORDER BY inside the OVER clause is mandatory. Without it, the database doesn't know which row should be "first."
  • Confusing RANK() vs. DENSE_RANK(): If two rows have the same value, RANK() will leave a gap in the numbering (1, 2, 2, 4), while DENSE_RANK() will not (1, 2, 2, 3).
  • Filtering in the same step: You cannot use a window function result in a WHERE clause in the same query block. You must wrap the query in a Common Table Expression (CTE) or a subquery and then filter the results.

Practice task

The Scenario: You have a table called user_logins with columns user_id and login_timestamp. Some users log in multiple times a day.

The Goal: Write a query that identifies the first login of all time for every user.

Hint: Use ROW_NUMBER(), partition the data by the user, and sort the time in ascending order. Once you have the row numbers, filter for the records where the number equals one.
