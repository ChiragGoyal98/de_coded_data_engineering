SQL Window Functions with Real ETL Use Cases

In the world of data engineering, you often need to perform calculations that involve multiple rows without collapsing them into a single result. While standard aggregate functions like SUM or COUNT group data together, window functions allow you to look at a window of records while keeping every individual row visible in your output. This unique capability makes them indispensable for cleaning data and creating complex transformations during the ETL (Extract, Transform, Load) process.

Why Window Functions Matter in ETL

Data engineers spend a significant amount of time cleaning "dirty" data. Standard SQL queries can tell you the total sales for a month, but they struggle when you need to find the specific timestamp of a user's very first purchase or identify duplicate records based on a specific sequence.

Window functions solve these problems by providing context. In an ETL pipeline, they are used to:

  • Deduplicate data by ranking entries and picking the "best" one.
  • Calculate running totals for financial reporting.
  • Compare values between the current row and the previous row (e.g., finding the time elapsed between two events).
  • Perform sessionization, which involves grouping user actions into discrete visits.

Step-by-Step Walkthrough

To master window functions, you need to understand the three core components of the syntax: the Function, the PARTITION BY clause, and the ORDER BY clause.

1. The Basic Syntax

The general structure looks like this:

FUNCTION() OVER (PARTITION BY column_a ORDER BY column_b)

  • FUNCTION(): This is the calculation you want to perform (e.g., ROW_NUMBER, SUM, or LEAD).
  • PARTITION BY: This tells the database how to group the rows. It is like a "GROUP BY" that doesn't collapse the rows.
  • ORDER BY: This defines the sequence of rows within each partition.

2. Identifying Duplicates with ROW_NUMBER()

One of the most common ETL use cases is removing duplicate records. Imagine a table where a user's profile was updated multiple times, but you only want the most recent version.


SELECT 
    user_id, 
    email, 
    updated_at,
    ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY updated_at DESC) as rank_order
FROM user_updates;

In this example, the "window" is defined by the user_id. Within that window, rows are ordered by the update time. The most recent record gets a rank_order of 1. During the "Load" phase of your ETL, you can simply filter for rows where rank_order = 1.

3. Comparing Trends with LAG() and LEAD()

In data transformation, you often need to see how a value changed compared to the record before it. The LAG() function pulls data from a previous row into the current row.

This is perfect for calculating "Time Since Last Action." If you partition by session_id and order by timestamp, LAG(timestamp) will give you the time of the previous click, allowing you to calculate the duration between them.

4. Running Totals with SUM()

Unlike a standard aggregate SUM, a windowed SUM keeps the individual rows and adds a column showing the cumulative total. By using SUM(amount) OVER (ORDER BY transaction_date), you create a running balance that updates with every new row.

Common Mistakes

  • Filtering in the WHERE clause: You cannot use a window function directly in a WHERE clause. Because window functions are processed late in the SQL execution order, you must wrap your query in a Common Table Expression (CTE) or a subquery to filter by the results (e.g., to filter for rank_order = 1).
  • Forgetting the ORDER BY: Functions like ROW_NUMBER() or LEAD() require a specific order to make sense. If you omit the ORDER BY inside the OVER clause, the results will be unpredictable.
  • Confusing RANK() and ROW_NUMBER(): ROW_NUMBER() always gives unique numbers (1, 2, 3). RANK() will give the same number to tied values (1, 1, 3), which might lead to keeping more duplicates than intended in an ETL process.

Practice Task

Imagine you have a table called monthly_revenue with columns region, month, and revenue.

Task: Write a query that shows each region's revenue for every month, but also includes a column showing the revenue from the previous month for that same region.

Hint: Use the LAG() function and remember to partition by the region to ensure you aren't comparing Revenue in New York to Revenue in London.
