Understanding how to manipulate data across rows is a fundamental skill for any aspiring data engineer. Window functions are a powerful feature in SQL that allow you to perform calculations across a specific set of table rows related to the current row. While aggregate functions like SUM or AVG usually collapse rows into a single summary, window functions keep the original row structure intact. This means you can see individual record details alongside computed values like running totals or rankings, making them indispensable for data transformation tasks.

Why it matters

In ETL (Extract, Transform, Load) pipelines, data rarely arrives in a perfectly clean state. You might encounter duplicate records, or you may need to calculate business metrics like "month-over-month growth" or "cumulative spend."

Without window functions, solving these problems requires complex self-joins or multiple nested subqueries. This makes your SQL code harder to read, difficult to debug, and often slower to execute. Window functions provide a clean, declarative syntax to handle these scenarios directly within your transformation layer, leading to more efficient data processing and clearer logic for your team.

Step-by-step walkthrough

To use a window function, you need the OVER() clause. This clause defines the "window" of data the function will look at. There are three main components you can use inside it:

  • PARTITION BY: This divides the result set into groups (like a GROUP BY, but without collapsing rows).
  • ORDER BY: This sorts the data within each partition.
  • Frame Clause: This defines the boundaries of the window (e.g., "from the start of the partition to the current row").

Case 1: Deduplication using ROW_NUMBER()

One of the most common ETL tasks is selecting the "latest" version of a record from a staging table that contains updates.


SELECT 
    order_id, 
    status, 
    updated_at,
    ROW_NUMBER() OVER (PARTITION BY order_id ORDER BY updated_at DESC) as rank_order
FROM staging_orders;

In this example, PARTITION BY order_id groups the rows by the specific order. ORDER BY updated_at DESC ensures the most recent update gets the number 1. You can then wrap this in a subquery to filter where rank_order = 1.

Case 2: Running Totals using SUM()

To calculate a cumulative sum of sales over time, you use an aggregate function with an ORDER BY inside the OVER() clause.


SELECT 
    sale_date, 
    amount,
    SUM(amount) OVER (ORDER BY sale_date) as running_total
FROM sales;

Case 3: Finding Deltas with LAG()

If you need to compare the current row's value to the previous row (e.g., to see if a price increased), use LAG().


SELECT 
    product_id, 
    price,
    LAG(price) OVER (PARTITION BY product_id ORDER BY effective_date) as previous_price
FROM price_history;

Common mistakes

  • Confusing ROW_NUMBER, RANK, and DENSE_RANK: ROW_NUMBER always gives unique numbers. RANK provides the same number for ties but skips the next number (1, 2, 2, 4). DENSE_RANK provides the same number for ties but does not skip (1, 2, 2, 3). Using the wrong one can lead to "missing" rows in your final dataset.
  • Forgetting ORDER BY: Many window functions, like LEAD, LAG, or running totals, require a specific order to make sense. If you omit it, the results will be unpredictable.
  • Performance Overhead: While efficient, using window functions on massive datasets without proper partitioning can be slow. Always ensure your PARTITION BY columns align with your data distribution.

One practice task

Imagine you have a table called web_traffic with columns session_id, timestamp, and page_url.

The Task: Write a query to find the "previous page" visited within the same session. Use a window function to create a new column called last_page_visited that shows the URL of the page the user was on just before the current row, ordered by the timestamp. Keep the results grouped by session_id.
