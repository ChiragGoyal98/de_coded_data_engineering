SQL Window Functions with Real ETL Use Cases

SQL window functions are a powerful feature that allows you to perform calculations across rows related to the current one. Unlike standard aggregate functions, which collapse multiple rows into a single result, window functions keep the individual rows intact while adding context from the surrounding data. This makes them indispensable for data engineers and analysts who need to transform raw data into meaningful insights during the ETL process.

Why it matters in ETL

In the world of Extract, Transform, Load (ETL), data is rarely perfect or ready for analysis in its raw state. Window functions provide a surgical way to clean and enrich data without losing the original record detail.

  • Data Deduplication: In many data pipelines, source systems might send duplicate records. Window functions like ROW_NUMBER() help identify and filter out these extras based on a timestamp.
  • Trend Analysis: Calculating month-over-month growth or year-to-date totals is impossible with simple GROUP BY statements if you want to keep the daily detail.
  • Sessionization: For web traffic data, window functions can help identify the start and end of user sessions by looking at the time difference between consecutive clicks.

Step-by-step walkthrough

To use a window function, you need to understand the three main components of the OVER() clause: PARTITION BY, ORDER BY, and the function itself.

1. The Basic Syntax

The general structure looks like this:

FUNCTION() OVER (PARTITION BY column_name ORDER BY column_name)

2. Deduplicating Data with ROW_NUMBER()

Imagine you have a table where the same transaction was recorded twice because of a system glitch. You want to keep only the latest entry.


SELECT 
    transaction_id, 
    customer_id, 
    amount, 
    transaction_time
FROM (
    SELECT 
        *,
        ROW_NUMBER() OVER (PARTITION BY transaction_id ORDER BY transaction_time DESC) as row_num
    FROM raw_sales_data
) 
WHERE row_num = 1;

In this example, PARTITION BY transaction_id groups the rows by their ID, and ORDER BY transaction_time DESC ensures the most recent record is assigned row_num = 1.

3. Calculating Running Totals

A common ETL task is creating an "accumulated sales" column for a dashboard. By using SUM() as a window function, you can add up values as you move down the table.

  • SUM(amount) OVER (PARTITION BY customer_id ORDER BY transaction_date)
  • This tells SQL: "Add up the amounts for this specific customer, following the chronological order of their purchases."

4. Comparing Rows with LAG() and LEAD()

To calculate growth, you need to see the "previous" row's value. LAG() reaches back to the previous row, while LEAD() looks ahead. This is vital for calculating the delta between two events in a pipeline.

Common mistakes

  • Confusing PARTITION BY with GROUP BY: Remember that PARTITION BY does not reduce the number of rows in your output; it only defines how the window function "sees" groups of data.
  • Forgetting ORDER BY: For functions like ROW_NUMBER(), LAG(), or RANK(), the order is essential. Without it, the results will be unpredictable.
  • Performance Overhead: Running window functions on millions of rows without a proper index on the columns used in PARTITION BY can significantly slow down your ETL jobs.
  • Misunderstanding RANK vs DENSE_RANK: If two rows have the same value, RANK() will skip the next number (e.g., 1, 2, 2, 4), while DENSE_RANK() will not (e.g., 1, 2, 2, 3).

Practice task

Suppose you have a table called monthly_revenue with columns region, month, and revenue.

The Task: Write a query that shows each region's revenue for the current month alongside the revenue from the previous month.

Hint: You will need to use the LAG() function and partition the data by region to ensure you aren't comparing revenue from two different locations.
