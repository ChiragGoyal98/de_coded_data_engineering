Window functions might sound like something out of a futuristic operating system, but in the world of data engineering, they are essential tools for processing rows of data. Unlike standard aggregate functions that collapse rows into a single result, window functions perform calculations across a set of table rows that are related to the current row. This allows you to keep the detail of every record while still performing complex math across groups, making your data transformations much more flexible.

Why it matters

In ETL (Extract, Transform, Load) pipelines, data is rarely perfect. You often encounter duplicate records, out-of-order events, or the need to compare a current value against a previous one. Window functions solve these problems elegantly.

Without them, you would often have to write complex self-joins or subqueries that slow down your database and make your code hard to read. By using window functions, you can handle deduplication, ranking, and running totals in a single pass over the data. This efficiency is critical when processing millions of records in a production data warehouse.

Step-by-step walkthrough

To understand how these functions work, you need to understand the three main parts of their syntax: the function itself, the PARTITION BY clause, and the ORDER BY clause.

1. The Core Syntax

The basic structure looks like this: FUNCTION() OVER (PARTITION BY column_a ORDER BY column_b).

  • PARTITION BY: This divides the data into buckets (like a GROUP BY, but without collapsing rows).
  • ORDER BY: This determines the sequence of rows within those buckets.

2. Identifying Duplicates with ROW_NUMBER()

A common ETL task is removing duplicate entries. Suppose you have a table where a user's email was captured multiple times, and you only want the most recent one. 


SELECT 
    user_id, 
    email, 
    created_at,
    ROW_NUMBER() OVER (PARTITION BY email ORDER BY created_at DESC) as row_num
FROM user_logs;

In this example, ROW_NUMBER() assigns a unique number to each row starting at 1 for each unique email address. Because we ordered by created_at DESC, the most recent record gets row_num = 1. In the next step of your ETL, you simply filter for rows where row_num = 1.

3. Comparing Records with LAG()

Another real-world use case is tracking changes. If you want to see how much a customer's spending increased compared to their last visit, you use LAG(). This function "looks back" at the previous row's value within your partition.

Common mistakes

  • Using them in the WHERE clause: You cannot use a window function directly in a WHERE clause. Because of how SQL processes data, the window function happens after the filtering. To filter based on a window function result, you must wrap the query in a Common Table Expression (CTE) or a subquery.
  • Forgetting the ORDER BY: For functions like ROW_NUMBER() or RANK(), forgetting the ORDER BY clause inside the OVER() parentheses will lead to unpredictable results because the database won't know which row should be "first."
  • Mixing up RANK and DENSE_RANK: If two rows have the same value, RANK() will skip the next number (e.g., 1, 1, 3), whereas DENSE_RANK() will not (e.g., 1, 1, 2).

One practice task

Imagine you have a table called store_sales with columns store_id, sale_date, and amount.

The Task: Write a query that shows every sale, but also includes a column called running_total that calculates the sum of all sales for that specific store up to that date.

Hint: Use the SUM() function as a window function combined with PARTITION BY store_id and ORDER BY sale_date.
